# 리뷰 스레드 코멘트 템플릿

GitHub PR에 리뷰 지적을 남길 때 사용한다. 지적 하나당 스레드 하나이며, **반드시 해당 파일의 diff 라인에 인라인 스레드로** 단다. PR 본문(대화) 코멘트로 지적을 남기지 않는다.

## 형식

```
[{우선순위}] {한 줄 요청 — 무엇을 해달라는 것인지}

**문제 상황**: {현재 코드·문서가 실제로 어떤 상태인지. 파일·라인·문구를 구체적으로 인용한다}

**영향**: {이 상태로 병합되면 무엇이 깨지거나 확인 불가능해지는지. 계약·정책 위반이면 어느 문서의 어느 조항인지 밝힌다}

**개선 제안**: {요청하는 변경. 가능하면 대체할 구체적인 문구나 명령을 제시한다}
```

## 우선순위

| 값 | 기준 |
|---|---|
| `P1` | 병합을 막아야 하는 결함. 재현 가능한 버그, 보안 결함, 데이터 손실, 계약 위반 |
| `P2` | 병합 전 고쳐야 하는 문제. 문서·정책 모순, 검증 불가능한 완료 보고, 범위 서술 불일치 |
| `P3` | 고치면 좋은 문제. 역추적성 누락, 서술 정확성, 표현 정정 |

## 앵커 규칙

- 지적 대상 파일이 diff에 있으면 그 파일의 해당 라인에 단다.
- 대상이 PR 본문 서술이라도, 그 서술의 근거가 되는 변경 파일 라인에 앵커를 잡는다.
- 어느 변경 파일에도 앵커를 잡을 수 없는 지적(예: 브랜치 전략)만 PR 리뷰 요약 본문에 쓴다. 이 경우 요약 본문에 "인라인 앵커 없음"과 그 이유를 함께 적는다.

## 금지

- 재현 시나리오나 근거 문서 없이 취향을 지적하지 않는다.
- 한 스레드에 여러 지적을 묶지 않는다. 요청 단위로 분리해야 요청자가 개별로 해결 처리할 수 있다.
- 자리표시자를 남긴 채 게시하지 않는다.
