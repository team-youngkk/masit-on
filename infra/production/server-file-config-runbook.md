# 제3자 SSH 앱 서버 파일 설정 운영 런북

## 1. 적용 범위와 실행 상태

2026-09-06 사용자가 승인한 ADR-SEC-001 예외에 따라 제3자 SSH 앱 서버의 설정·비밀 관리 절차를 정의한다. 구현은 별도 담당자가 수행하며, 이 문서만으로 구현·서버 전환·백업·복원·배포 성공을 판정하지 않는다. 기존 AWS IAM 정책·인스턴스 프로파일·SSM 값·Redis 서버 자원의 분리나 삭제는 이 절차에 포함하지 않는다.

앱 기동·재기동·배포는 IAM Role·IMDS·SSM·KMS·S3 비밀 조회·ACM에 의존하지 않아야 한다. 필수 파일 누락 시 AWS 조회나 빈 기본값으로 우회하지 않는다. 기존 AWS 전용 Redis 부트스트랩의 ADR-SEC-002는 별도 경계다.

## 2. 파일과 접근 권한

| 대상 | 내용과 관리 규칙 |
|---|---|
| `/etc/masiton/app.env` | DB·Redis·메일 endpoint/포트, DB 사용자명, 기능 설정 등 비밀이 아닌 값만 저장한다. root 소유로 두고 관리자 외 쓰기를 금지한다. 셸 코드나 명령 치환을 넣지 않고 구현이 지원하는 설정 형식을 사용한다. Redis가 공인 endpoint인 경우 `REDIS_ALLOWED_PUBLIC_HOSTS`에 승인한 주소를 명시해야 하며, `REDIS_HOST`와 일치하지 않는 공인 주소는 배포 preflight가 거부한다. |
| `/etc/masiton/secrets` | Spring configtree 속성명별 파일로 비밀번호·API 키·JWT 서명 키·메일 자격 증명 등을 저장한다. 배포 bundle·이미지·Git에서 제외한다. |
| `/etc/nginx/tls/masiton.click.fullchain.pem` | 기존 Nginx 설정이 참조하는 인증서 체인. 도메인·체인·만료를 확인한다. |
| `/etc/nginx/tls/masiton.click.key` | 대응하는 TLS 개인 키. root 소유 `0600`을 사용하고 앱 컨테이너에 전달하지 않는다. |

비밀 디렉터리·파일은 root가 관리하고, 실제 앱 실행 UID/GID에 필요한 탐색·읽기만 부여한다. 예를 들어 전용 읽기 그룹을 사용하는 경우 디렉터리 `0750`, 파일 `0640`으로 두되 그 그룹의 다른 호스트 사용자가 없는지 확인한다. 숫자 UID/GID를 추정하지 말고 배포 이미지와 호스트에서 대조한다. 일반 사용자·다른 컨테이너에 읽기를 허용하거나 앱에 호스트 파일 쓰기를 허용하지 않는다. 비밀 마운트는 반드시 읽기 전용이며 프론트엔드에는 필요하지 않은 비밀을 마운트하지 않는다.

root, sudo 또는 Docker 관리자 권한 보유자는 파일·컨테이너 비밀을 읽을 수 있다. 이 방식은 관리자로부터 비밀을 숨기거나 호스트 저장 데이터를 암호화하지 않는다. 실제 값은 터미널 출력·명령 인수·셸 이력·로그·CI artifact·이슈·문서에 남기지 않는다. `app.env`를 컨테이너 환경으로 전달할 때도 비밀 파일의 값을 환경 변수로 펼치지 않는다.

필수 파일명과 기능별 조건부 키는 배포 대상의 `app-secrets-render.sh`, `app-run.sh`, production 설정 및 검사 구현을 대조해 확정한다. JWT 키 쌍과 key ID, DB·Redis 비밀번호, 메일 자격 증명·발신 설정, action-mail 키와 rate-limit 키를 빠뜨리지 않는다. 선택 기능은 활성화할 때 필요한 키까지 준비하고, 비활성 기능의 키 누락과 필수 키 누락을 구분한다.

## 3. 최초 준비와 중지 전 점검

1. 대상 호스트·SSH host key·운영자 권한을 확인하고 위 경로를 준비한다. 앱 비밀을 CI로 전송하지 않고 운영자가 승인된 보안 경로로 서버에 배치한다.
2. 기존 서비스·이미지 digest·스크립트·systemd unit·Nginx 설정의 복구 대상을 확인한다. 파일 설정을 지원하지 않는 이전 산출물은 AWS 없이 복구할 수 있다고 가정하지 않는다. 첫 전환에는 실제 실행 가능한 복구 방법을 확보한다.
3. 서비스가 실행 중인 상태에서 후보 설정 형식, 필수 값, 포트·endpoint, 비밀 파일 존재·비어 있지 않음·소유권·권한 및 실제 앱 UID/GID의 읽기를 검사한다. 안전하지 않은 경로·심볼릭 링크를 통한 경계 이탈도 거부해야 한다. 값은 출력하지 않는다.
4. 로컬 TLS 파일의 유효성·키 쌍 일치·도메인·만료와 후보 Nginx 설정을 검사한다. 인증서가 없거나 유효하지 않으면 배포를 중단한다. 배포가 ACM에서 인증서를 가져오거나 발급·갱신 작업을 대신 실행하지 않는다.
5. 두 이미지 digest pull, 후보 산출물 무결성 확인, 이전 실행 산출물 백업, 설정·비밀·TLS preflight가 모두 성공한 뒤에만 활성 파일 교체 및 서비스 중지를 허용한다. 누락·권한 오류 검사 실패 시 기존 서비스와 활성 파일을 유지해야 한다. systemd의 재시작 후 `ExecStartPre`만으로 이 순서를 충족했다고 보지 않는다.

검사 스크립트의 정확한 호출 방법은 구현과 대조한다. 필요한 preflight가 구현되지 않았거나 구 버전이 비밀 디렉터리를 삭제·SSM으로 재생성한다면 해당 산출물로 전환하지 않는다.

## 4. 배포와 롤백

기존 Docker Hub digest + SSH 배포 경로, 승인·품질 게이트와 수동 재배포를 유지한다. 배포 중 `/etc/masiton/app.env`, `/etc/masiton/secrets`, 로컬 TLS 파일을 bundle로 덮어쓰거나 삭제하지 않는다. TLS 발급·갱신 도구와 스케줄은 운영자가 별도로 관리하고 만료 전 갱신 결과를 확인한다.

배포 후 backend ready, `db`·`mail`·`redis` dependency health, frontend 응답, runtime health, Nginx HTTPS smoke와 `/internal/**` 외부 차단을 확인한다. 실패·중단 시 이전 이미지·스크립트·unit·Nginx 설정을 복구하고 복구 후 backend/frontend health를 다시 확인한다. 실패를 성공으로 바꾸거나 원래 오류를 숨기지 않는다.

코드 롤백은 비밀 교체나 DB 마이그레이션을 자동으로 되돌리지 않는다. 이전 코드와 새 설정·비밀의 호환성을 먼저 확인한다. 폐기된 자격 증명이나 새 키로 암호화된 데이터를 읽지 못하는 구성을 복구 대상으로 선택하지 않는다.

## 5. 서버 밖 암호화 백업과 복원

운영자는 최초 전환 전과 설정·비밀 교체 때마다 복원 가능한 백업을 확보한다. 이 설정 백업은 PostgreSQL·Redis 데이터 백업을 대체하지 않는다.

1. 설정·비밀 파일과 소유권·모드, 대응 이미지 digest·설정 버전을 일관된 복구 단위로 묶는다. TLS 개인 키를 포함하면 같은 비밀 보호 기준을 적용한다.
2. 운영자가 승인한 인증된 암호화 도구로 암호화한 뒤 서버와 분리된 저장소에 전송한다. 새 외부 서비스는 이 문서만으로 도입하지 않는다. 평문 archive를 호스트 디스크나 CI 산출물에 남기지 않고 스트림 또는 접근 제한된 임시 메모리 경로를 사용한다.
3. 복호화 개인 키·암호는 서버 및 백업 저장소와 분리해 승인된 운영자가 접근할 수 있게 보관한다. 서버 상실 시에도 백업과 복호화 수단을 확보할 수 있어야 한다.
4. 원격 객체의 존재·크기·암호문 checksum을 확인하고, 격리된 복구 경로에서 실제 복호화·파일 완전성·권한 복원까지 검증한다. 암호문 업로드 성공만으로 복원 성공을 기록하지 않는다. 점검에 실제 외부 API 호출은 필요하지 않다.
5. 일시·담당자·백업 버전·암호문 checksum·저장 위치 식별자·복원 결과를 비밀값 없이 기록한다. 보존 기간과 삭제 책임자를 정하고, 교체 후 최소한 검증된 최신 복구본을 확보하기 전에 기존 복구본을 폐기하지 않는다.

복원 시 서비스를 먼저 중지하지 말고 별도 보호 경로에 복호화해 파일·권한·버전 호환성을 점검한다. 3절의 preflight와 실행 가능한 롤백 준비 후 교체·기동하고 4절의 health를 확인한다. 임시 평문은 검증 종료 후 제거한다. 저장소·복호화 수단·보존 정책·복원 증거가 준비되지 않았다면 백업 항목은 미완료다.

## 6. 수동 비밀 교체

1. 대상 키, 소비 서비스, 교체 사유·담당자·실행 시점, 기존 자격 증명의 유효 기간과 복구 가능성을 기록한다. 유출 의심 시에는 폐기할 값을 복구본으로 재사용하지 않는다.
2. 보호된 후보 경로에서 새 파일을 준비하고 5절의 암호화 백업을 확보한다. 값을 셸 인수나 로그에 노출하지 않는다.
3. DB·Redis·메일·외부 제공자의 자격 증명 변경과 앱 소비 순서를 조정한다. 이중 자격 증명을 지원하지 않으면 중단 가능성과 복구 방법을 정한다. JWT 및 action-mail 키 교체는 기존 토큰·메일 링크 영향, 임시 입력 암호화 키는 미종결 작업의 구키 필요 여부를 확인한다.
4. 후보 파일과 권한을 preflight한 뒤 파일을 안전하게 교체하고 영향을 받는 컨테이너를 다시 기동한다. 이미 마운트된 파일이나 configtree가 즉시 다시 읽힌다고 가정하지 않는다. 기존 배포와 동시 수행하지 않는다.
5. health와 해당 인증·기능을 검증한 뒤 기존 키 참조가 끝났는지 확인하고 제공자 측 구키를 폐기한다. 교체·복구 결과를 비밀값 없이 기록하고 최신 암호화 백업을 갱신한다. 키 교체 주기와 다음 점검일은 운영자가 정해 기록한다.

## 7. 증거와 완료 판정

| 항목 | 남길 증거 | 이 문서 작성 시 상태 |
|---|---|---|
| 파일 설정 및 중지 전 preflight | 구현 검사 결과와 실패 시 기존 서비스 유지 확인 | 미검증 |
| AWS 없는 앱 기동·재기동 | 대상 호스트에서 AWS 조회 없이 기동한 결과 | 미검증 |
| 배포·실패·중단 롤백 | 대상 digest, 실행 결과와 복구 후 health | 미검증 |
| 서버 밖 암호화 백업·복원 | 원격 백업 식별자, checksum, 복원 결과 | 미검증 |
| 수동 교체·로컬 TLS 갱신 | 수행자·시각·검증 결과·다음 점검일 | 미검증 |
| 기존 IAM 분리 여부 | 별도 AWS 상태 확인이 필요한 항목 | 이 작업 범위 밖·미확인 |

실제 수행한 항목만 증거와 함께 갱신한다. 테스트 통과·설계 승인·문서 작성은 운영 배포나 백업 완료 증거가 아니다.
