# 맛잇온 2차 확장 Workstream

## 1. 목적

이 문서는 2차 확장 기능을 독립적으로 인수 가능한 WS-09~WS-13으로 나누고 한 명의 최종 책임자와 다른 기본 리뷰어를 배정한다. 도메인 소유와 교차 의존은 [2차 확장 도메인 경계](second-expansion-domain-boundaries.md)를 따른다.

## 2. 확정 배정

| Workstream | 사용자·운영 가치 | 관련 요구사항 | 최종 책임자 | 기본 리뷰어 | 상태 |
|---|---|---|---|---|---|
| [WS-09](#4-ws-09-개인-컬렉션) 개인 컬렉션 | 목적별 비공개 맛집 목록 관리 | `FR-COLLECTION-001`~`006` | 박진영 | 김인안 | 확정 |
| [WS-10](#5-ws-10-인기-맛집) 인기 맛집 | 설명 가능한 현재 찜 기반 공개 탐색 | `FR-POPULAR-001` | 양성훈 | 박진영 | 확정 |
| [WS-11](#6-ws-11-관리자-큐레이션) 관리자 큐레이션 | 관리자가 편집한 주제별 공개 목록 | `FR-CURATION-001`~`004` | 김인안 | 양성훈 | 확정 |
| [WS-12](#7-ws-12-제보신고-검토) 제보·신고 검토 | 회원 접수부터 실제 조치 완료까지 추적 | `FR-SUBMISSION-001`~`003`, `FR-REPORT-001`~`003` | 김인안 | 이우람 | 확정 |
| [WS-13](#8-ws-13-사용자-알림) 사용자 알림 | 처리 상태 변화와 읽음 확인 | `FR-NOTIFICATION-001`~`004` | 이우람 | 김인안 | 확정 |

김인안은 관리자 인증·데이터 조치 연속성이 큰 WS-11과 WS-12를 함께 맡는다. 두 Workstream의 일정이 겹치면 공개 탐색을 제공하는 WS-11을 먼저 완료하고 WS-12 관리자 큐를 통합한다.

## 3. 배정 근거와 공통 책임

| 결정 | 근거 |
|---|---|
| 박진영 → WS-09 | WS-06의 찜·최근 기록, 데이터 정합성과 탈퇴 처리 연속성 |
| 양성훈 → WS-10 | WS-01 공개 Restaurant 조회·정렬·성능 및 탐색 화면 연속성 |
| 김인안 → WS-11·WS-12 | WS-04 관리자 인증·데이터 등록과 WS-05 회원 인증 계약 연속성 |
| 이우람 → WS-13 | 공통 아키텍처·인프라 조율과 상태-알림 정합성·장애 경계 책임 |

- Orchestration 코드는 별도 Workstream이 독점하지 않는다. 교차 유스케이스의 최종 사용자 가치를 소유한 WS가 구현·테스트를 책임한다.
- 공유 orchestration 계약 변경은 이우람이 구조를 리뷰하고 영향받는 제공 WS 책임자가 데이터·규칙을 리뷰한다.
- 핵심 데이터·Flyway 변경은 기존 정책대로 박진영과 영향받는 WS 책임자의 승인을 받는다.

## 4. WS-09 개인 컬렉션

### 책임

- 회원별 컬렉션 생성·이름 변경·삭제·조회
- 맛집 추가·제거, 상한·중복·정렬과 소유권
- Restaurant 공개 상태와 회원 탈퇴 정리 연계

### 의존성과 완료 경계

- WS-05 Member identity, WS-06 개인화 생명주기, WS-01·WS-02 공개 Restaurant 계약을 사용한다.
- Collection과 Curation 모델을 공유하지 않는다.
- `FR-COLLECTION-*`, `BR-COLLECTION-*`, 개인정보·동시성 인수 테스트가 통과하면 완료한다.

## 5. WS-10 인기 맛집

### 책임

- 현재 찜 수 기반 상위 20개 공개 맛집 조회
- 최소 1개, 전체 기간, 찜 수 내림차순·ID 오름차순
- 실시간 PostgreSQL 집계의 정확성과 공개 조회 성능

### 의존성과 완료 경계

- WS-06 Favorite 읽기 계약과 WS-01 Restaurant 공개 판정을 사용한다.
- Favorite 원본을 변경하거나 배치·캐시·별도 집계 생명주기를 선행 구현하지 않는다.
- `FR-POPULAR-001`, `BR-POPULAR-*`, 성능·안정 정렬 검증이 통과하면 완료한다.

## 6. WS-11 관리자 큐레이션

### 책임

- 큐레이션 초안 등록·편집·게시/비게시
- 구성 20개, 수동 순서, 메인 노출 최대 5개
- 비공개·삭제 맛집의 공개 숨김과 관리자 경고

### 의존성과 완료 경계

- WS-04 관리자 인증과 WS-01 Restaurant 공개 판정을 사용한다.
- Collection Aggregate를 재사용하지 않는다.
- `FR-CURATION-*`, `BR-CURATION-*`, 관리자 권한·감사 이력과 공개 반영 검증이 통과하면 완료한다.

## 7. WS-12 제보·신고 검토

### 책임

- 회원 제보·신고 등록 및 본인 조회
- 중복·일일 합산 제한, 입력 보안과 보존
- 관리자 검토 상태 전이, 사유, 감사 이력과 실제 데이터 조치 확인

### 의존성과 완료 경계

- WS-05 회원 인증, WS-04 관리자 인증·대상 도메인 명령과 WS-13 알림 생성 계약을 사용한다.
- `ACCEPTED`와 실제 조치 후 `COMPLETED`를 분리하고 신고 자동 숨김을 구현하지 않는다.
- `FR-SUBMISSION-*`, `FR-REPORT-*`와 관련 BR·NFR 검증 및 WS-13 원자성 통합이 통과하면 완료한다.

## 8. WS-13 사용자 알림

### 책임

- 네 처리 상태 알림의 고유 생성
- 최신 목록, 정확한 미읽음 수, 개별·전체 읽음
- 90일/최신 200개 보존과 탈퇴 정리

### 의존성과 완료 경계

- WS-05 Member identity와 WS-12 상태 전이 계약을 사용한다.
- WS-12가 호출하는 명령과 같은 DB 트랜잭션에 참여하되 Participation 상태를 직접 변경하지 않는다.
- `FR-NOTIFICATION-*`, `BR-NOTIFICATION-*`, 원자성·권한·보존 테스트가 통과하면 완료한다.

## 9. 통합 순서

1. WS-05·WS-06 회원·인증·찜 계약과 Restaurant 공개 판정의 선행 상태를 확인한다.
2. [E2-T01 기준선 확인](../08-planning/expansion-2-task-breakdown.md) 뒤 `E2-T02` 공통 스키마·권한·생명주기 기반을 먼저 병합한다.
3. WS-09 컬렉션, WS-10 인기 집계와 WS-12 제보·신고 접수는 공통 기반 뒤 병렬 구현한다.
4. WS-11 큐레이션은 관리자 인증과 공개 Restaurant 계약으로 독립 구현한다. 인기와 같은 화면에 배치할 때만 카드 응답·로딩·빈 상태·오류 표현을 WS-10과 먼저 합의한다.
5. WS-12는 회원 접수·본인 조회 뒤 관리자 검토·실제 조치 상태 전이를 연결한다. 제보 또는 신고 `RECEIVED → IN_REVIEW → ACCEPTED → COMPLETED` 한 흐름을 첫 통합 대상으로 삼는다.
6. WS-13은 상태 전이·알림 고유 키·트랜잭션 계약과 테스트를 미리 준비할 수 있지만, 실제 알림 저장 연결은 WS-12 관리자 상태 전이가 동작한 뒤 수행한다.
7. 공개 상태 변경이 컬렉션·인기·큐레이션에서 일관된지 확인하고 생명주기·보안·성능·교차 인수 회귀를 순서대로 수행한다.

## 10. 변경 규칙

- Workstream마다 최종 책임자는 한 명이며 자신의 변경을 단독 승인하지 않는다.
- 인기와 큐레이션을 다시 합치거나 Collection과 Curation 모델을 공유하려면 도메인 경계와 PRD를 먼저 재승인한다.
- 새 최상위 패키지는 이 문서가 아니라 모듈·패키지 설계와 ADR에서 승인한다.
- WS-11·WS-12의 병행 부담이 통합을 2영업일 이상 막으면 관리자 화면 공통 작업은 양성훈, 데이터 계약 검증은 박진영이 우선 지원한다.
