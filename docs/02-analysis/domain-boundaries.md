# 맛잇온 도메인 경계

## 1. 문서 목적

이 문서는 맛잇온 1차 MVP의 기능 요구사항과 비즈니스 규칙을 기준으로 업무 책임의 경계를 정의한다. 이후 MVP 작업 분해, 역할 배정, API 계약, 데이터 모델링과 모듈 구조 설계는 이 경계를 입력으로 사용한다.

도메인은 데이터 저장 단위나 화면 단위가 아니라 같은 업무 규칙과 변경 이유를 공유하는 책임 단위다. 현재 단계에서는 클래스, 패키지, 테이블, API URL과 물리 배포 단위를 정하지 않는다. 구현 형태는 하나의 애플리케이션 안에서 경계를 지키는 모듈형 모놀리스를 우선한다.

근거 문서는 다음과 같다.

- `docs/00-overview/glossary.md`

## 2. 도메인 분리 원칙

- 같은 비즈니스 규칙과 변경 이유를 공유하는 책임을 같은 도메인에 둔다.
- 화면에 함께 표시되거나 같은 저장소를 참조한다는 이유만으로 같은 도메인에 두지 않는다.
- 기본 정보의 소유와 관계의 소유를 구분한다. Restaurant, Creator, Video는 각 기본 정보를 소유하고 Visit는 이들 사이의 검증된 방문 관계를 소유한다.
- 조회 조합과 변경 권한을 구분한다. 다른 도메인의 정보를 조회해 조합할 수는 있지만 그 도메인의 내부 모델을 직접 변경하지 않는다.
- 검색, 필터, 지역과 음식 카테고리는 현재 MVP에서 별도 변경 이유가 없으므로 Restaurant의 탐색 또는 구성 개념으로 둔다. 단, 유튜버 필터의 관계 판정은 Visit가 소유한다.
- 관리자와 일반 사용자는 사용자 유형이다. 관리자라는 이유만으로 독립 비즈니스 도메인을 만들지 않는다.
- 공개 상태는 각 대상 도메인이 상태를 소유하고, 일반 사용자 조회에는 일관된 공개 정책을 적용한다. Publication이라는 별도 도메인은 만들지 않는다.
- 방문 관계는 단순 연결 데이터가 아니다. 실제 방문 근거, 대상 일치, 중복, 유효성과 노출 규칙을 가진 독립 책임이다.
- `Common`처럼 변경 이유와 소유자가 불명확한 범용 도메인을 만들지 않는다.
- 현재는 데이터베이스나 배포 단위를 도메인별로 물리 분리하지 않는다.
- 4명의 백엔드 개발자가 세로 기능을 병렬로 완결할 수 있을 만큼 경계를 명확히 하되, 팀원 수에 맞추기 위한 인위적인 일대일 분리는 하지 않는다.
- 순환 변경 의존을 금지한다. 조회 조합 때문에 양방향 협업이 보이더라도 소유 데이터의 변경은 항상 해당 소유 도메인의 공개 유스케이스를 통한다.

## 3. 도메인 요약

| 도메인 | 핵심 책임 | 소유 개념 | 주요 협업 대상 |
|---|---|---|---|
| Restaurant | 맛집 기본 정보, 지역·대표 음식 카테고리와 맛집 중심 탐색 | 맛집, 지역, 대표 음식 카테고리, 맛집 공개 상태 | Visit |
| Creator | YouTube 채널 단위 유튜버 기본 정보와 상태 | 유튜버(YouTube 채널), 채널 표시 정보, 유튜버 공개 상태 | Visit, Video |
| Video | YouTube 영상 링크·메타데이터와 영상 상태 | 영상, 원본 링크, 제목, 썸네일, 영상 공개 상태 | Visit, Creator |
| Visit | 실제 방문이 검증된 맛집·유튜버·영상 관계와 관계 기반 조회 | 방문 관계, 방문 근거, 관계 유효성·중복·공개 상태 | Restaurant, Creator, Video |

도메인 경계는 네 개지만 담당자 수와 강제로 일치시키지 않는다. 특히 관리자 접근과 여러 도메인의 결과 조합은 애플리케이션 계층 책임이며 별도 비즈니스 도메인이 아니다.

## 4. Restaurant 도메인

### 책임

- 맛집 기본 정보의 등록 및 조회
- 맛집과 카카오 장소의 동일성 검증 기준 관리
- 맛집의 서울특별시 자치구와 대표 음식 카테고리 관리
- 맛집의 공개·비공개 판단과 영상·방문 관계로부터 독립된 생명주기 관리
- 맛집 이름 검색, 지역·음식 카테고리 필터, 조건 조합, 페이지 조회와 기본 정렬
- 맛집 상세 기본 정보 제공

유튜버 조건이 없는 검색·필터는 Restaurant가 완결한다. 유튜버 조건이 포함되면 Visit에서 유효한 방문 관계에 해당하는 맛집 식별자 집합을 받아 Restaurant의 나머지 조건과 결합한다.

### 소유 데이터 개념

- 맛집
- 카카오에서 확인한 장소 동일성
- 맛집 이름, 전체 도로명주소, 상세 위치, 전화번호와 카카오 장소 링크
- 서울특별시 자치구
- 대표 음식 카테고리와 `기타`의 구체 음식 종류
- 맛집 공개 상태

### 소유 기능 요구사항

- FR-RESTAURANT-001
- FR-RESTAURANT-002
- FR-RESTAURANT-003
- FR-RESTAURANT-004
- FR-RESTAURANT-005
- FR-RESTAURANT-006
- FR-RESTAURANT-007
- FR-RESTAURANT-008
- FR-RESTAURANT-009
- FR-RESTAURANT-010
- FR-RESTAURANT-011
- FR-ADMIN-002

### 소유 비즈니스 규칙

- BR-RESTAURANT-001 ~ BR-RESTAURANT-011
- BR-SEARCH-001 ~ BR-SEARCH-006
- BR-SEARCH-008 ~ BR-SEARCH-009
- BR-PUBLICATION-003

### 제공하는 정보

- 맛집 식별 정보와 기본 정보
- 지역과 대표 음식 카테고리
- 맛집 공개 여부와 조회 가능 여부
- 이름·지역·음식 카테고리·페이지·정렬 조건을 적용한 맛집 조회 결과

### 필요로 하는 외부 정보

- 유튜버 조건이 있을 때 Visit가 판정한 공개·유효 방문 관계의 맛집 식별자
- 맛집 상세 또는 목록에 표시할 방문 유튜버와 관련 영상의 조합 결과

### 책임에서 제외되는 항목

- 유튜버 기본 정보와 공개 상태의 변경
- 영상 링크·메타데이터와 영상 공개 상태의 변경
- 방문 사실 검증, 방문 관계 생성과 관계 중복 판정
- Visit 내부의 관계 유효성 규칙
- 관리자 인증

### 변경 이유

- 맛집 기본 정보, 장소 동일성 또는 생명주기 정책이 변경되는 경우
- 서울특별시 자치구나 대표 음식 카테고리 정책이 변경되는 경우
- 맛집 이름 검색, 지역·카테고리 필터, 페이지 또는 기본 정렬 정책이 변경되는 경우
- 맛집 자체의 공개 조건이 변경되는 경우

## 5. Creator 도메인

### 책임

- YouTube 채널을 고유 관리 단위로 하는 유튜버 기본 정보 등록 및 조회
- 동일 채널 중복 판단과 채널명 변경 시 동일성 유지
- 채널명과 채널 링크의 표시 정보 관리
- 채널 삭제·비공개 확인에 따른 유튜버 공개 상태 관리
- Visit가 관계 판정과 결과 조합에 사용할 유튜버 존재 여부와 공개 정보 제공

### 소유 데이터 개념

- 유튜버로 표현되는 YouTube 채널
- YouTube 채널명과 채널 링크
- 채널 동일성
- 유튜버 공개 상태

### 소유 기능 요구사항

- FR-ADMIN-003

FR-CREATOR-001과 FR-CREATOR-002의 관계 기반 최종 사용자 유스케이스는 Visit가 주 소유한다. FR-CREATOR-003의 공개 유튜버 선택 목록은 Creator가 주 소유하며 Visit와 Restaurant가 필터 연동에 협업한다.

### 소유 비즈니스 규칙

- BR-CREATOR-001 ~ BR-CREATOR-004
- BR-CREATOR-006 ~ BR-CREATOR-007
- BR-PUBLICATION-004

### 제공하는 정보

- 유튜버 식별 정보
- 현재 YouTube 채널명과 채널 링크
- 동일 채널 여부
- 유튜버 공개 여부와 조회 가능 여부

### 필요로 하는 외부 정보

- 채널 상태와 동일성을 검증할 공개 YouTube 정보
- 방문 맛집이나 관련 영상을 보여줄 때 Visit의 관계 조회 결과

### 책임에서 제외되는 항목

- 방문 관계의 저장, 변경, 중복과 실제 방문 근거 판정
- 특정 유튜버가 방문한 맛집 목록의 관계 판정
- 영상 링크와 메타데이터 자체의 관리
- 관리자 인증과 다중 도메인 등록 흐름 조율

### 변경 이유

- 유튜버 관리 단위, 필수 정보 또는 동일 채널 판단 정책이 변경되는 경우
- 채널명·채널 링크 표시 정책이 변경되는 경우
- 채널 이용 불가와 재공개 정책이 변경되는 경우

## 6. Video 도메인

### 책임

- YouTube 영상 기본 정보의 등록 및 조회
- 영상 제목, 썸네일, 게시 채널명과 원본 링크 관리
- 동일 원본 영상 중복 판단
- 영상 원본을 저장·재배포하지 않는 보관 경계 유지
- 영상 표시 정보 변경, 외부 링크 장애와 이용 불가 상태 처리
- Visit가 관계 판정과 관련 영상 조합에 사용할 영상 존재 여부와 공개 정보 제공

### 소유 데이터 개념

- YouTube 영상
- 영상 제목, 썸네일과 게시 채널명
- YouTube 원본 링크와 원본 영상 동일성
- 영상 공개·이용 가능 상태

### 소유 기능 요구사항

- FR-ADMIN-004

FR-VIDEO-001은 단순 영상 조회가 아니라 특정 맛집의 유효한 방문 관계에 연결된 영상을 찾는 유스케이스이므로 Visit가 주 소유하고 Video가 표시 정보를 제공한다.

### 소유 비즈니스 규칙

- BR-VIDEO-001 ~ BR-VIDEO-003
- BR-VIDEO-007 ~ BR-VIDEO-009
- BR-PUBLICATION-005
- BR-PUBLICATION-007

### 제공하는 정보

- 영상 식별 정보
- 영상 제목, 썸네일, 게시 채널명과 원본 링크
- 동일 영상 여부
- 영상 공개·이용 가능 여부

### 필요로 하는 외부 정보

- 게시 채널과 등록 유튜버의 일치 여부를 확인할 Creator 정보
- 특정 맛집과 연결된 관련 영상을 찾을 Visit의 관계 조회 결과

### 책임에서 제외되는 항목

- 영상이 특정 맛집의 실제 방문 근거인지에 대한 최종 관계 판정
- 맛집·유튜버·영상 방문 관계의 생성과 중복 판정
- 영상 게시일을 방문일로 해석하는 정책
- 맛집과 유튜버 기본 정보의 변경

### 변경 이유

- 영상 필수 메타데이터나 동일 영상 판단 정책이 변경되는 경우
- 원본 링크와 영상 원본 보관 경계가 변경되는 경우
- 영상 표시 정보, 외부 링크 장애 또는 이용 불가 처리 정책이 변경되는 경우

## 7. Visit 도메인

### 책임

- 맛집 1개, 유튜버 1명과 근거 영상 1개로 구성된 방문 관계 등록 및 조회
- 영상에서 실제 방문이 확인되는지와 영상 게시 채널·유튜버가 일치하는지 검증
- 동일 맛집·유튜버·영상 조합의 중복 방지
- 하나의 영상과 여러 맛집 사이의 관계를 맛집별로 독립 검증
- 방문 관계의 공개·유효 상태 관리
- 유튜버별 방문 맛집, 맛집별 방문 유튜버와 맛집별 관련 영상의 관계 판정
- 관계가 무효여도 맛집 기본 정보는 유지되는 생명주기 분리

유튜버 필터의 결과는 Visit가 유효한 관계로 판정하고 Restaurant가 맛집 기본 정보와 다른 탐색 조건을 적용해 최종 목록을 구성한다. 맛집 상세의 방문 유튜버·관련 영상 영역도 Visit가 관계 결과를 주도하고 Creator와 Video의 공개 표시 정보를 조합한다. 최종 상세 조합 유스케이스를 Restaurant에 둘지 전용 조회 책임에 둘지는 검토 항목으로 남긴다.

### 소유 데이터 개념

- 방문 관계
- 맛집·유튜버·영상 식별자의 관계 참조
- 실제 방문 근거 확인 결과
- 관계 중복과 유효성
- 방문 관계 공개 상태

### 소유 기능 요구사항

- FR-CREATOR-001
- FR-CREATOR-002
- FR-VIDEO-001
- FR-VISIT-001

### 소유 비즈니스 규칙

- BR-CREATOR-005
- BR-VIDEO-004 ~ BR-VIDEO-006
- BR-VISIT-001 ~ BR-VISIT-007
- BR-SEARCH-007
- BR-PUBLICATION-006

### 제공하는 정보

- 맛집에 연결된 공개·유효 방문 관계
- 유튜버가 방문한 맛집 식별자
- 맛집을 방문한 유튜버 식별자
- 맛집과 연결된 관련 영상 식별자
- 관계가 없는 경우의 빈 관계 결과

### 필요로 하는 외부 정보

- Restaurant의 맛집 존재 여부와 공개 상태
- Creator의 유튜버 존재 여부, 채널 동일성·공개 상태와 표시 정보
- Video의 영상 존재 여부, 게시 채널·공개 상태와 표시 정보

### 책임에서 제외되는 항목

- 맛집, 유튜버와 영상 기본 정보의 직접 수정
- 다른 도메인의 공개 상태 자체를 변경하는 일
- 영상 원본이나 외부 링크 상태의 관리
- 실제 방문 날짜 관리
- 맛집 이름·지역·음식 카테고리 검색 규칙

### 변경 이유

- 방문 근거, 대상 일치 또는 관계 생성 조건이 변경되는 경우
- 관계 중복, 다대상 연결 또는 관계 유효성 정책이 변경되는 경우
- 관계 기반 탐색과 연결 정보 노출 정책이 변경되는 경우

## 8. 관리자 기능의 책임 위치

### 선택지 검토

1. **Admin 독립 비즈니스 도메인**: 관리자 자체가 독립된 핵심 업무 개념과 규칙을 소유하지 않고, 현재 규칙은 인증·검증·등록 흐름에 관한 것이므로 과도한 분리다.
2. **Admin 애플리케이션 조율 책임**: 여러 도메인을 함께 다루는 흐름에는 적합하지만, 이 선택만 적용하면 각 도메인의 등록 규칙까지 중앙 조율자가 소유하는 것으로 오해될 수 있다.
3. **각 도메인이 등록 기능을 소유하고 Admin은 인증과 진입점만 제공**: 데이터와 규칙의 소유권을 유지하면서 관리자 접근과 필요한 조율만 애플리케이션 계층에 둘 수 있다.

### 최종 권장안

선택지 3을 권장한다. Restaurant, Creator, Video와 Visit는 각각 자신의 등록 유스케이스와 불변 조건을 소유한다. 관리자 기능은 독립 도메인이 아니라 관리자 인증, 공통 진입점, 입력 순서와 오류 처리를 담당하는 애플리케이션 계층 책임으로 둔다. Visit 등록처럼 여러 대상의 존재와 일치 여부를 확인하는 흐름도 애플리케이션 서비스가 각 도메인의 공개 기능을 호출해 조율하되, 최종 방문 관계 규칙은 Visit가 판단한다.

이 방식은 Admin이 모든 내부 모델을 직접 수정하는 결합을 막고, 각 담당자가 등록부터 조회까지 세로 기능을 완결하기 쉽다. 관리자 접근 규칙과 등록 흐름 공통 정책은 애플리케이션 책임이지만 새로운 비즈니스 도메인을 뜻하지 않는다.

### 관리자 애플리케이션 책임

- FR-ADMIN-001의 관리자 접근과 인증된 진입점 제공
- BR-ADMIN-001 ~ BR-ADMIN-008의 공통 관리자 등록 정책 조율
- BR-PUBLICATION-001, BR-PUBLICATION-002와 BR-PUBLICATION-008의 일관된 접근·노출 정책 적용
- 각 도메인의 공개 등록 유스케이스 호출
- 여러 호출이 필요한 경우 부분 반영 방지와 오류 결과 조합

### 관리자 책임에서 제외되는 항목

- Restaurant, Creator, Video와 Visit의 내부 모델 직접 변경
- 각 도메인의 중복·필수값·관계 생성 규칙 재구현
- 관리자라는 이유로 기본 정보와 관계 데이터의 소유권을 가져오는 일
- MVP에서 제외된 수정·삭제·승인 상태 관리 기능 추가

## 9. 공통 개념 및 참조 데이터

| 항목 | 분류 | 책임 위치와 판단 |
|---|---|---|
| 지역 | 특정 도메인의 구성 개념 | 서울특별시 자치구 1개는 Restaurant가 주소와 함께 소유한다. 현재 범위에서는 독립 생명주기나 유스케이스가 없다. |
| 음식 카테고리 | 특정 도메인의 구성 개념 | 사전 정의된 대표 카테고리 1개와 `기타` 기록은 Restaurant 정책이다. 현재는 별도 도메인이 아니다. |
| 공개 상태 | 여러 도메인이 사용하는 공통 정책 | 상태 값의 의미와 노출 우선순위는 공통 정책이지만 각 대상의 상태와 판단은 Restaurant, Creator, Video, Visit가 각각 소유한다. 추후 복잡한 게시 워크플로가 생기면 분리를 검토한다. |
| 관리자 | 애플리케이션 또는 인터페이스 계층 관심사 | 인증된 운영자와 등록 진입점이다. 독립 비즈니스 도메인이 아니다. |

| 이미지 또는 썸네일 URL | 특정 도메인의 구성 개념 | 영상 썸네일은 Video가 소유한다. 향후 맛집 이미지가 추가되면 해당 이미지의 업무 소유자를 별도로 판단한다. |

공통 정책은 공유 계약이나 정책으로 둘 수 있지만 `Common`이라는 포괄 도메인에 업무 규칙을 모으지 않는다.

## 12. 도메인 간 협업 관계

### Restaurant → Visit

- 목적:
  - 맛집 목록·상세에 방문 유튜버와 관련 영상 관계를 제공하고 유튜버 필터를 적용한다.
- 요청 정보:
  - 공개·유효한 방문 관계, 맛집에 연결된 유튜버·영상 식별자 또는 유튜버 조건에 해당하는 맛집 식별자
- 전달 식별자:
  - 맛집 식별자 또는 유튜버 식별자
- 금지:
  - Restaurant가 Visit 관계 데이터를 직접 변경하지 않는다.
  - Restaurant가 실제 방문 검증과 관계 중복 규칙을 구현하지 않는다.

### Visit → Restaurant

- 목적:
  - 방문 관계 등록 시 맛집의 존재를 확인하고 관계 조회 시 공개 가능한 맛집인지 확인한다.
- 요청 정보:
  - 맛집 존재 여부, 식별 정보와 공개 상태
- 전달 식별자:
  - 맛집 식별자
- 금지:
  - Visit가 맛집 이름, 주소, 지역, 음식 카테고리나 상태를 직접 변경하지 않는다.
  - Visit가 관계 유무를 이유로 맛집을 생성·삭제·비공개하지 않는다.

### Visit → Creator

- 목적:
  - 방문 관계 등록 시 유튜버 존재와 영상 게시 채널 일치를 확인하고 조회 결과에 공개 채널 정보를 제공한다.
- 요청 정보:
  - 유튜버 존재 여부, 채널 동일성, 공개 상태, 채널명과 채널 링크
- 전달 식별자:
  - 유튜버 식별자와 영상의 게시 채널 식별 정보
- 금지:
  - Visit가 유튜버 기본 정보나 공개 상태를 직접 변경하지 않는다.
  - Creator가 방문 관계를 직접 저장하거나 변경하지 않는다.

### Visit → Video

- 목적:
  - 방문 관계 등록 시 영상 존재·게시 채널·공개 상태를 확인하고 관련 영상 표시 정보를 제공한다.
- 요청 정보:
  - 영상 존재 여부, 게시 채널, 공개 상태, 제목, 썸네일과 원본 링크
- 전달 식별자:
  - 영상 식별자
- 금지:
  - Visit가 영상 링크, 메타데이터나 공개 상태를 직접 변경하지 않는다.
  - Video가 특정 맛집과의 방문 관계를 직접 생성하지 않는다.

### 관리자 등록 흐름 → Restaurant

- 목적:
  - 검증된 맛집 기본 정보를 등록한다.
- 요청 정보:
  - 맛집 필수 정보와 관리자가 확인한 카카오 장소 정보
- 전달 식별자:
  - 등록 또는 기존 맛집 식별자
- 금지:
  - 관리자 흐름이 맛집 중복, 지역과 카테고리 규칙을 우회하지 않는다.
  - Restaurant 내부 모델을 직접 수정하지 않는다.

### 관리자 등록 흐름 → Creator

- 목적:
  - 검증된 YouTube 채널 정보를 유튜버로 등록한다.
- 요청 정보:
  - 채널명과 채널 링크
- 전달 식별자:
  - 등록 또는 기존 유튜버 식별자
- 금지:
  - 관리자 흐름이 채널 관리 단위와 동일 채널 판정을 재구현하지 않는다.

### 관리자 등록 흐름 → Video

- 목적:
  - 검증된 영상 메타데이터와 원본 링크를 등록한다.
- 요청 정보:
  - 제목, 썸네일, 게시 채널명과 원본 링크
- 전달 식별자:
  - 등록 또는 기존 영상 식별자
- 금지:
  - 관리자 흐름이 동일 영상 판정이나 원본 보관 금지 규칙을 우회하지 않는다.

### 관리자 등록 흐름 → Visit

- 목적:
  - 관리자가 실제 방문을 확인한 맛집·유튜버·영상 관계를 등록한다.
- 요청 정보:
  - 세 대상 식별자와 검증된 방문 근거
- 전달 식별자:
  - 방문 관계 식별 결과
- 금지:
  - 관리자 흐름이 대상 존재, 게시 채널 일치, 실제 방문 근거와 중복 규칙을 우회하지 않는다.
  - 여러 도메인의 기본 정보를 Visit를 통해 수정하지 않는다.

조회에서는 Restaurant와 Visit가 서로 정보를 요청하는 모습이 나타날 수 있다. 이는 조회 조합이지 양방향 변경 의존이 아니다. Restaurant는 맛집을, Visit는 관계를 각각 변경하며 상대 내부 모델을 직접 수정하지 않는다.

## 13. 의존 방향

- 각 도메인은 다른 도메인의 내부 모델을 직접 소유하지 않는다.
- 다른 도메인의 데이터를 변경할 때는 해당 도메인이 공개한 유스케이스를 사용한다.
- Visit는 맛집, 유튜버와 영상의 존재·공개 상태가 필요하지만 기본 정보를 직접 수정하지 않는다.
- Restaurant, Creator와 Video는 Visit의 관계 생성·검증·중복 규칙을 직접 구현하지 않는다.
- 도메인 간 전달은 필요한 식별 정보, 공개 상태와 표시 정보로 제한한다.
- 조회 조합은 애플리케이션 서비스 또는 전용 조회 책임에서 수행할 수 있다. 전용 조회 책임의 도입 여부는 후속 결정으로 남긴다.
- 관리자 유스케이스는 각 도메인에 의존하지만 각 도메인은 관리자 유스케이스에 의존하지 않는다.
- 도메인 이벤트, 포트, 모듈 공개 인터페이스 등 실제 의존 제어 방식은 후속 아키텍처 문서에서 확정한다.

개념적 변경 의존 방향은 다음과 같다.

```text
관리자 유스케이스(인증·조율)
 ├──> Restaurant
 ├──> Creator
 ├──> Video
 └──> Visit

Visit --존재·상태·표시 정보 조회--> Restaurant
Visit --존재·채널·표시 정보 조회--> Creator
Visit --존재·게시 채널·표시 정보 조회--> Video

Restaurant --관계 기반 조회 요청--> Visit
```

마지막 두 방향은 조회 협업이다. 변경 방향은 각 소유 도메인 안에서 끝나므로 Restaurant와 Visit 사이의 순환 변경 의존을 허용하지 않는다.

| External YouTube | 독립 도메인으로 두지 않음 | YouTube는 외부 시스템 경계다. 채널 정보는 Creator, 영상 정보는 Video가 소유한다. | 다수 외부 플랫폼 통합과 독립 동기화·장애 정책 도입 |
| Common | 만들지 않음 | 책임과 변경 이유가 불명확해 규칙 소유권을 숨기고 결합을 키운다. | 분리 조건 없음. 실제 책임이 발견되면 구체적인 이름의 정책 또는 도메인으로 정의 |
