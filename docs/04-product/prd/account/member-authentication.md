# 사용자 계정·인증 PRD

## 1. 문서 정보

이 문서는 일반 사용자 계정 생성부터 일반 회원·관리자가 공유하는 로그인, 세션 유지, RBAC 관리자 진입, 비밀번호 재설정과 탈퇴까지 하나의 사용자 목표로 정의한다. 주 Workstream은 `WS-05 사용자 계정·인증`이며 최종 책임자는 김인안이다. `member_account`가 단일 계정 원장이고 `MEMBER|ADMIN` 역할을 가진다. API 경로·메서드·필드는 [회원 계정·인증 API](../../../05-specs/api/account/member-authentication-api.md), 물리 데이터 구조는 데이터 계약에서 확정한다.

## 2. 해결할 문제

찜과 최근 본 맛집을 여러 기기에서 안전하게 이어서 사용하려면 사용자를 식별하고 인증 상태를 관리할 수 있어야 한다. 사용자는 가입·로그인·세션 만료·비밀번호 분실·탈퇴 상황에서 다음 행동을 명확히 이해해야 하며, 공격자는 응답이나 처리 시간 차이로 계정 존재 또는 상태를 알아낼 수 없어야 한다.

## 3. 목표

- 사용자가 이메일 인증을 거쳐 계정을 활성화하고 로그인한다.
- 짧은 Access Token과 회전 가능한 Refresh Token으로 인증 상태를 안전하게 유지한다.
- 비밀번호를 잊은 사용자가 이메일로 재설정하고 기존 인증 상태를 모두 폐기한다.
- 사용자가 탈퇴하면 즉시 인증을 차단하고 개인정보·개인화 데이터를 정해진 시간 안에 정리한다.
- 인증·Redis·메일 장애를 개인화 기능에 격리하고 공개 조회를 계속 제공한다.

## 4. 대상 사용자

- 찜과 최근 본 맛집을 계정에 연결하려는 일반 사용자
- 이메일 인증을 기다리는 미인증 회원
- Access Token 만료 후 이용을 이어가려는 로그인 회원
- 비밀번호를 잊었거나 탈퇴하려는 회원
- 같은 로그인 화면을 사용하고 메인 페이지에서 관리자 기능으로 진입하는 `ADMIN` 사용자

## 5. 사용자 여정

### 5.1 회원가입과 이메일 인증

1. 사용자가 이메일과 비밀번호를 입력하고 개인정보 처리 안내를 확인한 뒤 가입을 요청한다.
2. 시스템은 이메일을 정규화하고 비밀번호 정책과 요청 제한을 검증한다.
3. 외부 응답은 같은 이메일의 계정 상태를 노출하지 않는 접수 결과를 제공한다.
4. 클라이언트는 회원가입 접수 성공 시 비밀번호와 비밀번호 확인 값을 정리하고 접수 이메일만 재발송 대상으로 보존한다.
5. 신규 가입 가능한 요청이면 혼동 문자를 제외한 영문 대문자·숫자 8자의 일회용 이메일 인증 코드를 발급하고 메일을 보낸다.
6. 사용자가 5분 안에 최신 인증 요청을 한 번 사용해 인증을 완료한다.
7. 인증 성공 또는 확정된 `400` Token 오류에서는 클라이언트가 Token 입력을 정리한다.
8. `503`·그 밖의 일시적 HTTP 오류·네트워크 오류에서는 클라이언트가 같은 Token으로 재시도할 수 있도록 입력을 보존한다.
9. 사용자는 인증 완료 후 로그인할 수 있다.

인증 메일 재발송은 이메일당 최소 60초 간격과 하루 최대 5회를 적용한다. 회원가입 요청은 정규화 이메일당 최소 60초 간격과 하루 최대 5회이며, 비밀번호 재설정 요청과 합쳐 요청 출처당 시간당 최대 20회다.

메일 발송 장애가 발생해도 신규·미존재·미인증·탈퇴·활성 이메일에 동일한 상태 코드·본문과 처리 시간 기준을 적용한다. 외부 응답은 메일 발송 여부나 계정 생성 여부를 구분하지 않으며, 내부 재시도·실패 관측만 상태별로 처리한다.

### 5.2 로그인과 세션 유지

1. 사용자가 일반 회원·관리자 구분 없는 하나의 로그인 화면에서 이메일과 비밀번호로 로그인한다.
2. 시스템은 활성·이메일 인증 완료 계정과 자격 증명을 검증한다.
3. 성공하면 30분 Access Token과 14일 Refresh Token을 포함한 새 활성 세션을 만든다.
4. `MEMBER`는 최대 3개, `ADMIN`은 최대 1개 세션을 유지하며 상한 초과 시 가장 오래된 세션을 폐기한다.
5. Access Token이 만료되면 아직 사용하지 않은 최신 Refresh Token으로 재발급한다.
6. 재발급에 사용한 Refresh Token은 즉시 폐기하고 새 Token으로 회전한다.
7. 새로고침이나 화면 복귀 뒤 TanStack Query로 현재 사용자 정보를 조회해 식별자·이메일·역할을 복구한다.
8. 현재 역할이 `ADMIN`이면 메인 페이지에 관리자 진입 링크를 표시하고 관리자 Route를 허용한다. 이 클라이언트 가드는 서버 `/api/admin/**` RBAC를 대신하지 않는다.

Refresh Token 재사용이 탐지되면 해당 Token 계열을 폐기한다. Redis에서 세션을 검증하거나 안전하게 생성·회전할 수 없으면 로그인과 재발급은 실패한다.

### 5.3 로그아웃과 인증 만료

1. 회원이 로그아웃을 요청한다.
2. 클라이언트는 보유한 인증 정보를 제거한다.
3. 시스템은 현재 서버 Refresh 세션 폐기를 확인한 뒤에만 로그아웃 성공을 제공한다.
4. Redis 장애로 폐기를 확인할 수 없으면 성공으로 표시하지 않고 복구 후 재시도를 안내한다.

만료·변조·폐기된 Token 또는 재사용이 탐지된 Token으로 인증할 수 없다. 인증 만료나 권한 오류는 입력 오류·서버 오류와 구분해 사용자가 재로그인 또는 이전 화면 이동을 선택할 수 있게 한다.

### 5.4 비밀번호 재설정

1. 사용자가 이메일을 입력해 비밀번호 재설정을 요청한다.
2. 시스템은 계정 상태와 관계없는 동일한 접수 결과를 제공한다.
3. 유효한 활성 계정이면 30분 동안 한 번 사용할 수 있는 최신 재설정 Token을 메일로 보낸다.
4. 사용자가 메일의 `비밀번호 재설정` 링크로 진입하면 클라이언트가 URL fragment의 Token을 읽고 주소 표시줄에서 제거한다.
5. 사용자가 새 비밀번호 정책을 만족하는 비밀번호로 재설정을 완료한다.
6. 시스템은 해당 회원의 모든 활성 세션과 남은 재설정 Token을 폐기한다.
7. 사용자는 새 비밀번호로 다시 로그인한다.

### 5.5 회원 탈퇴

1. 로그인 회원이 탈퇴 영향과 삭제 대상을 확인하고 의사를 명시적으로 확정한다.
2. 시스템은 요청 즉시 로그인을 차단하고 모든 활성 인증 상태를 폐기한다.
3. 이메일·비밀번호 해시·회원 식별 정보, 인증·재설정 Token, 찜과 최근 본 맛집을 정리한다.
4. 정리가 모두 끝난 뒤 같은 이메일의 재가입을 허용한다.

정리 실패 시 로그인 차단과 재가입 금지를 유지하고 15분마다 재시도한다. 1시간 동안 완료되지 않으면 운영 알림을 발생시키며, 요청 후 24시간 안에 완료하거나 운영자가 수동 복구한다.

## 6. 기능 범위

### 포함 범위

- 이메일과 비밀번호를 사용하는 자체 회원가입
- 가입 이메일 인증과 인증 메일 재발송
- 로그인, Access Token 재발급과 로그아웃
- 현재 로그인 회원의 최소 사용자 정보 조회
- 이메일을 이용한 비밀번호 재설정
- 회원 탈퇴와 동일 이메일 재가입 조건
- 계정 상태 비노출, 요청 제한과 로그인 실패 제한
- `MEMBER` 최대 3개·`ADMIN` 최대 1개 세션, 단일 로그인과 현재 역할 응답
- TanStack Query 현재 사용자 상태를 이용한 메인 페이지 관리자 진입 링크와 Route Guard
- Redis·메일 장애 시 인증 기능 격리와 fail-closed 처리

### 제외 범위

- 소셜 로그인과 다중 인증
- 닉네임·자기소개·프로필 이미지와 일반 사용자 프로필 화면
- 휴면 계정 전환, 장기 미접속자 관리, 신고와 제재
- 공개 관리자 가입·역할 변경 UI/API와 세분화된 관리자 권한
- 비밀번호 재설정 이외의 계정 복구 절차
- 사용자가 개별 활성 세션을 조회하거나 원격 종료하는 세션 관리 화면

## 7. 개인정보 및 보안 정책

- 계정 유지 중 이메일, 비밀번호 해시, 계정 상태와 가입·이메일 인증 시각만 필수 개인정보로 저장한다.
- 탈퇴 처리 중에는 정리 완료를 위해 탈퇴 요청 시각과 처리 상태를 임시 보관할 수 있다.
- 이름, 전화번호, 생년월일, 주소와 사용자 위치는 수집하지 않는다.
- 비밀번호는 12자 이상 64자 이하이며 정규화한 이메일과 같을 수 없다. 문자 종류 조합은 강제하지 않는다.
- 비밀번호 원문과 인증·재설정·Refresh Token 원문은 저장하거나 로그·응답에 노출하지 않는다.
- 인증·재설정·Refresh Token은 고엔트로피 불투명 일회용 값이며 서버에는 해시만 저장한다.
- 가입·로그인·인증 재발송·비밀번호 재설정은 미존재·미인증·탈퇴·활성 계정과 잘못된 비밀번호에 동일 처리 경로를 적용한다. 동일 부하의 상태별 서버 처리 시간 p95 차이는 100ms 이하다.
- 로그인 실패는 첫 실패부터 15분 동안 계정·요청 출처 조합당 5회, 계정 전체 10회, 요청 출처 전체 50회로 제한한다. 어느 한도든 충족하면 남은 제한 시간 동안 해당 범위의 로그인을 차단한다.
- 현재 사용자 조회는 인증된 본인에게 불투명 계정 식별자, 이메일과 현재 단일 역할만 반환하며 닉네임·프로필·내부 계정 상태는 추가하지 않는다.
- 공개 회원가입 요청에는 역할 필드가 없고 알 수 없는 `role` 입력을 거부하며 서버가 항상 `MEMBER`를 부여한다. `ADMIN` 역할은 승인된 운영 절차로만 변경한다.

## 8. 화면과 상태

화면의 명칭과 정보 구조만 이 PRD에서 확정하며 실제 Route는 프론트 계약에서 확정한다.

| 화면 | 정상 상태 | 빈·대기 상태 | 오류·경계 상태 |
|---|---|---|---|
| 회원가입 | 이메일·비밀번호 입력, 정책 안내와 가입 요청 | 가입 접수 후 이메일 확인 안내 | 입력 정책 위반은 수정 지점을 표시하되, 메일 장애를 포함해 계정 존재·생성·발송 여부는 동일 응답으로 숨김 |
| 이메일 인증 | 메일의 최신 유효 8자 코드를 입력해 인증 완료, 코드 입력 정리 및 로그인 이동 | 인증 메일 대기와 제한 범위 내 재발송 | 잘못된 형식·만료·사용·교체 코드는 입력 정리·재발송 안내, `429`는 제한 해제 뒤 재시도, `503`·기타 일시적 HTTP·네트워크 오류는 코드 보존·재시도 안내 |
| 통합 로그인 | 자격 증명 확인 후 안전한 원래 목적 화면 또는 개인화 진입, `ADMIN`은 메인에서 관리자 링크 표시 | 입력 전 초기 상태 | 미존재·미인증·탈퇴·역할·잘못된 비밀번호와 제한 상태를 계정 열거가 불가능한 동일 범주로 표시 |
| 인증 만료·권한 오류 | 재발급 성공 시 현재 흐름을 이어감 | 재인증 진행 중 | 재발급 불가 시 재로그인 안내, 권한 없음은 인증 만료와 구분 |
| 비밀번호 재설정 | 요청 접수, 유효 Token 확인, 새 비밀번호 등록 | 메일 대기 | 계정 상태는 숨기고 만료·변조·재사용 Token은 새 요청 안내 |
| 로그아웃 | 서버 Refresh 세션 폐기 확인 후 비로그인 상태 | 서버 폐기 확인 중 | Redis 장애 시 클라이언트 정보는 제거하되 완료로 표시하지 않고 복구 후 재시도 안내 |
| 회원 탈퇴 | 삭제 대상 확인, 명시적 확인, 처리 접수 | 정리 진행 중이며 로그인과 재가입 차단 | 정리 지연 시 일반 오류 대신 처리 중임을 안내하고 운영 복구 대상이 됨 |

모든 화면은 비밀번호와 Token을 URL, 브라우저 로그 또는 분석 이벤트에 남기지 않는다. 공개 맛집 탐색 화면은 인증 오류나 인증 저장소 장애에도 계속 사용할 수 있어야 한다.

폼 상태의 민감 입력은 오류 종류와 관계없이 일괄 제거하지 않는다. 회원가입 접수 성공 시 비밀번호·확인 값을 정리하고, 이메일 인증 코드는 인증 성공 또는 확정된 `400`에서만 정리한다. 제출 제한 `429`, `503`·그 밖의 일시적 HTTP 오류·네트워크 오류에서는 유효할 수 있는 코드를 보존한다.

## 10. 비즈니스 규칙

- 회원 식별, 비밀번호, 이메일 인증과 탈퇴는 [BR-MEMBER-001](../../../01-requirements/business-rules.md#br-member-001-이메일-정규화와-고유성)~[BR-MEMBER-004](../../../01-requirements/business-rules.md#br-member-004-회원-탈퇴와-재가입)를 따른다.
- Token 수명·회전, 세션 상한, 로그인 제한, 재발송·재설정과 상태 비노출은 [BR-AUTH-001](../../../01-requirements/business-rules.md#br-auth-001-인증-유효-시간)~[BR-AUTH-008](../../../01-requirements/business-rules.md#br-auth-008-회원가입비밀번호-재설정-요청-제한)을 따른다.
- 규칙의 숫자 기준과 외부 응답 비노출 조건은 화면 문구보다 우선하며 화면만으로 계정 상태를 추론할 수 없어야 한다.

## 11. 비기능 요구사항

- 자격 증명·Token 보호와 계정 열거 방지는 [NFR-SECURITY-003](../../../01-requirements/non-functional-requirements.md#nfr-security-003-비밀정보와-오류-정보-보호)~[NFR-SECURITY-005](../../../01-requirements/non-functional-requirements.md#nfr-security-005-회원-인증-남용과-계정-열거-방지)를 따른다.
- 장애 격리·재시도와 사용자 오류 구분은 [NFR-RELIABILITY-001](../../../01-requirements/non-functional-requirements.md#nfr-reliability-001-오류-격리와-공통-오류-정책)~[NFR-RELIABILITY-003](../../../01-requirements/non-functional-requirements.md#nfr-reliability-003-사용자-오류-메시지와-기능-분리)를 따른다.
- 회원 개인정보와 탈퇴 생명주기는 [NFR-PRIVACY-003](../../../01-requirements/non-functional-requirements.md#nfr-privacy-003-회원-개인정보-최소-수집과-생명주기)을 따른다.
- 전체 인증 여정, 저장소 장애와 브라우저 기준은 [NFR-TEST-004](../../../01-requirements/non-functional-requirements.md#nfr-test-004-1차-확장-보안통합브라우저-검증)로 검증한다.

## 12. 제품 성공 기준

- 가입을 시작한 사용자가 이메일 인증을 완료하고 로그인할 수 있다.
- 인증된 회원이 Token 재발급으로 이용을 이어가고 명시적으로 로그아웃할 수 있다.
- 새로고침 뒤 현재 사용자 정보를 복구하고 동일한 개인화 흐름을 이어갈 수 있다.
- `MEMBER` 네 번째 로그인 뒤 활성 세션은 3개, `ADMIN` 재로그인 뒤 활성 세션은 1개를 초과하지 않는다.
- 비밀번호 재설정 뒤 모든 기존 세션과 남은 재설정 Token으로 인증할 수 없다.
- 비인증 계정 상태별 외부 응답과 처리 시간 차이로 계정 존재·상태를 식별할 수 없다.
- 탈퇴 요청 즉시 로그인이 차단되고 24시간 안에 정리가 완료되거나 수동 복구된다.
- Redis·메일 장애 중 인증·개인화 기능은 안전하게 실패하고 공개 조회는 계속 동작한다.

초기 제품 기준은 성공 사용자 수나 전환율이 아니라 위 요구사항의 인수 시나리오 통과율 100%로 판단한다. 운영 지표의 목표값은 실제 이용 기준선을 확보한 뒤 별도 제품 측정 계약에서 확정한다.

## 14. 완료 기준

- 8개 관련 FR과 12개 관련 BR이 구현 및 추적성 문서에 연결된다.
- 회원가입 → 이메일 인증 → 로그인 → 재발급 → 로그아웃 정상 흐름이 브라우저에서 통과한다.
- 현재 사용자 조회는 `id`, `email`, `role`만 반환하고 다른 계정 입력·탈퇴 처리 중 계정을 거부한다.
- 비밀번호 재설정과 탈퇴의 인증 상태 전체 폐기 및 데이터 정리가 통합 테스트로 검증된다.
- 8자 인증 코드의 문자 집합·정규화·CSPRNG 생성·제출 제한과 중복·동시 요청, Token 만료·변조·재사용·이전 발급, 최대 세션 수와 세 종류 로그인 제한이 검증된다.
- 미존재·미인증·탈퇴·활성 계정과 잘못된 비밀번호에 대한 동일 응답·동일 처리 경로 및 p95 100ms 기준이 검증된다.
- Redis·메일 장애 시 fail-closed, 로그아웃 재시도, 공개 조회 격리가 검증된다.
- API·데이터·ADR·사용자 흐름과 화면 와이어프레임이 이 PRD의 범위 및 상태 계약과 일치한다.

## 15. 리스크와 후속 결정

- 메일 발송 지연은 가입·재설정 완료율에 직접 영향을 주므로 발송 수단과 재시도·관측 계약이 필요하다.
- Redis 장애 중 로그아웃은 클라이언트와 서버 상태가 일시적으로 달라질 수 있어 복구 후 재시도 UX와 운영 관측이 필요하다.
- 개인정보 동의 문구와 법적 보존 의무는 구현 전에 별도 검토하되, 이 PRD보다 많은 개인정보를 임의로 수집하지 않는다.
- 화면 Route와 물리 데이터 구조는 후속 명세에서 확정한다. API 경로·필드·오류 코드와 Token 전달은 통합 계정·인증 API와 ADR-AUTH-007을 따른다.
