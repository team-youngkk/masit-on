# 맛잇온 팀 역할

## 1. 문서 목적

이 문서는 맛잇온 1차 MVP의 네 Workstream을 팀원별 책임으로 연결하고, 각 팀원의 주요 책임, 결정 권한, 산출물과 협업 관계를 정의한다. 역할은 기술 계층이 아니라 사용자 가치와 관리자 업무 흐름을 끝까지 완성하는 기능 소유권을 기준으로 한다.

현재 배정은 2026-07-27 승인된 Workstream 복잡도, 의존성, 통합 지점과 공통 책임 부담 기준안이다. 일정 차단이나 지속적인 부담 불균형이 확인될 때만 소유권 변경 절차로 조정하며 각 Workstream의 최종 책임자는 한 명으로 유지한다.

## 2. 역할 배정 원칙

- 모든 팀원은 백엔드 기능 개발을 담당하고 하나의 주요 Workstream을 끝까지 소유한다.
- 프로젝트 리더도 관리 업무에만 머물지 않고 주요 Workstream 하나를 소유한다.
- Controller, Service, Repository, Entity와 같은 기술 계층별로 역할을 나누지 않는다.
- 각 기능 요구사항과 공동 구현 작업에는 최종 책임자 또는 구현 책임자 한 명을 둔다.
- Workstream 담당자는 요구사항 구체화, API 계약, 데이터 모델 협의, 구현, 테스트, 문서화와 통합까지 책임진다.
- High 복잡도 Workstream과 다수의 공통 책임이 한 사람에게 함께 집중되지 않도록 한다.
- 보조 책임자는 리뷰, 계약 협의와 통합을 지원하며 최종 책임자를 대신하지 않는다.
- 공통 기반은 최소화하고, 각 Workstream 담당자가 합의된 공통 계약을 자신의 기능에 적용한다.
- 공동 정책은 팀이 결정하고 내부 구현은 담당자가 결정한다.
- 개인별 역량과 선호도가 확인되면 Workstream 경계를 유지한 채 담당자 배정을 재검토할 수 있다.

### 횡단 역할과 기술 의사결정 담당

`영크크`는 팀 이름이다. 발표자료와 기록은 특정 개인에게 귀속하지 않고 영크크 팀 전체가 공동으로 책임진다.

| 역할 영역 | 담당 | 책임 |
|---|---|---|
| 리더 | 이우람 | 일정 지연을 조기에 인지하고 영향, 대응 선택지와 결정 필요 사항을 팀에 공유한다. |
| 발표자료 제작 | 영크크(팀 공동) | 발표자료를 함께 제작하고 발표 리허설을 주도한다. |
| 기록 | 영크크(팀 공동) | 회의록을 정리하고 README를 최초 작성·관리한다. 내용 작성에는 모든 팀원이 참여한다. |
| AI | 김인안, 이우람, 양성훈 | AI 기능 요구사항, 활용 범위, 프롬프트·응답 형식과 연동 방식을 제안하고 팀의 기술 의사결정을 주도한다. |
| 인프라 | 이우람 | 개발·배포 환경, CI/CD, 서버 구성과 환경변수 관리 기준을 제안하고 팀의 기술 의사결정을 주도한다. |
| 백엔드 | 양성훈, 박진영 | API 구조, 비즈니스 로직, 데이터베이스와 예외 처리 기준을 제안하고 팀의 기술 의사결정을 주도한다. |
| 프론트엔드 | 양성훈, 김인안 | 화면 구조, 사용자 흐름, 백엔드 연동과 UI 상태 처리 기준을 제안하고 팀의 기술 의사결정을 주도한다. |

- 모든 팀원은 모든 티켓의 개발과 리뷰에 참여할 수 있다.
- 영역 담당자는 해당 영역의 구현을 전담하거나 다른 팀원의 수정을 제한하는 사람이 아니다.
- 영역 담당자는 기준과 선택지를 먼저 정리하고, 영향받는 팀원과 함께 기술 결정을 내리도록 회의를 주도한다.
- Workstream 최종 책임자는 횡단 역할과 별개로 담당 기능의 문서, 구현, 테스트와 통합 완료 책임을 유지한다.

## 4. 이우람 역할

### 주요 역할

- 프로젝트 리더
- [WS-03](../02-analysis/mvp-workstreams.md#7-ws-03-유튜버-기반-탐색) 유튜버 기반 탐색 최종 책임자
- 공통 계약 및 아키텍처 조율 책임자
- 통합 일정과 위험 관리 책임자
- 배포·인프라 기반 책임자
- AI 기술 의사결정 공동 담당자

### 소유 Workstream

- [WS-03](../02-analysis/mvp-workstreams.md#7-ws-03-유튜버-기반-탐색) 유튜버 기반 탐색

### 핵심 책임

- 유튜버 기준 공개·유효 방문 맛집 조회 요구사항을 구체화한다.
- Visit 관계 유효성, 공개 상태와 중복 제거 계약을 작성하고 구현한다.
- [WS-01](../02-analysis/mvp-workstreams.md#5-ws-01-맛집-탐색)이 사용할 유튜버 조건 판정 계약과 [WS-02](../02-analysis/mvp-workstreams.md#6-ws-02-맛집-상세-및-콘텐츠-조회)가 사용할 관계 판정의 일관성을 보장한다.
- [WS-03](../02-analysis/mvp-workstreams.md#7-ws-03-유튜버-기반-탐색) 자동화 테스트와 관련 문서를 갱신한다.
- 서비스 범위·일정 변경, Workstream 간 의존성과 지연을 감지한다.
- 공통 계약 변경과 통합 순서를 조율하고 배포 준비 상태를 확인한다.
- 코드와 문서 기준의 불일치를 확인하되 담당자 대신 모든 문제를 직접 해결하지 않는다.

### 소유 산출물

- [WS-03](../02-analysis/mvp-workstreams.md#7-ws-03-유튜버-기반-탐색) API 및 관계 판정 계약
- [WS-03](../02-analysis/mvp-workstreams.md#7-ws-03-유튜버-기반-탐색) 구현 코드와 자동화 테스트
- Visit 관련 데이터 모델 변경안
- [FR-CREATOR-001](../01-requirements/functional-requirements.md#fr-creator-001-유튜버-기준-방문-맛집-조회), [FR-CREATOR-003](../01-requirements/functional-requirements.md#fr-creator-003-유튜버-필터-선택-목록-조회)과 관련 규칙 문서 수정
- [WS-01](../02-analysis/mvp-workstreams.md#5-ws-01-맛집-탐색)·[WS-02](../02-analysis/mvp-workstreams.md#6-ws-02-맛집-상세-및-콘텐츠-조회) 관계 계약 통합 확인 결과
- 아키텍처 결정 조율 기록과 배포·헬스체크 문서

### 결정 권한

- [WS-03](../02-analysis/mvp-workstreams.md#7-ws-03-유튜버-기반-탐색) 내부 메서드와 클래스 구조
- 관계 판정 테스트 데이터와 테스트 구성
- 기존 Visit·공통 계약을 바꾸지 않는 리팩터링
- 합의된 배포 기준 안의 운영 절차 구체화

### 팀 합의가 필요한 변경

- Visit 관계의 구성·유효성 또는 핵심 데이터 관계 변경
- 공통 응답·오류·식별자·날짜 계약 변경
- [WS-01](../02-analysis/mvp-workstreams.md#5-ws-01-맛집-탐색)·[WS-02](../02-analysis/mvp-workstreams.md#6-ws-02-맛집-상세-및-콘텐츠-조회)·[WS-04](../02-analysis/mvp-workstreams.md#8-ws-04-관리자-데이터-등록)가 사용하는 관계 판정 계약 변경
- 신규 인프라, 외부 기술 또는 라이브러리 도입
- 관리자 인증 정책 또는 MVP 범위 변경

### 협업 대상

- 양성훈: 유튜버 조건 결과와 최종 검색·필터 AND 조합 계약
- 박진영: 맛집별 콘텐츠 조회와 동일한 Visit 유효성 정책
- 김인안: 방문 관계 등록 검증과 등록 결과의 조회 반영

### 완료 책임

- [FR-CREATOR-001](../01-requirements/functional-requirements.md#fr-creator-001-유튜버-기준-방문-맛집-조회)과 [FR-CREATOR-003](../01-requirements/functional-requirements.md#fr-creator-003-유튜버-필터-선택-목록-조회) 인수 조건 및 관련 비기능 요구사항 충족
- 관계 유효성·공개 상태·중복 제거 자동화 테스트 통과
- [WS-01](../02-analysis/mvp-workstreams.md#5-ws-01-맛집-탐색)·[WS-02](../02-analysis/mvp-workstreams.md#6-ws-02-맛집-상세-및-콘텐츠-조회)와 동일한 판정 정책으로 통합 완료
- API 계약과 실제 구현 일치, 리뷰 반영과 관련 문서 최신화
- 배포 전후 검사와 헬스체크 기준 확인

### 담당하지 않는 책임

- 모든 아키텍처와 공통 구현을 독점하지 않는다.
- 다른 Workstream 내부 구현을 임의로 변경하지 않는다.
- 회의 결정을 독점하지 않고 미결정 항목과 선택지를 구조화한다.
- 팀 합의 없이 공통 계약이나 MVP 범위를 변경하지 않는다.

### 주요 리스크

- [WS-03](../02-analysis/mvp-workstreams.md#7-ws-03-유튜버-기반-탐색) 요구사항 수는 적지만 [WS-01](../02-analysis/mvp-workstreams.md#5-ws-01-맛집-탐색)·[WS-02](../02-analysis/mvp-workstreams.md#6-ws-02-맛집-상세-및-콘텐츠-조회)·[WS-04](../02-analysis/mvp-workstreams.md#8-ws-04-관리자-데이터-등록) 통합 지원이 집중될 수 있다.
- 아키텍처·배포 책임이 기능 개발 일정을 방해할 수 있다.
- 유튜버 최소 선택 목록과 관계 판정 계약을 함께 안정적으로 제공해야 한다.

## 8. 공통 책임

모든 팀원은 다음을 책임진다.

- 자신이 소유한 요구사항, 비즈니스 규칙과 비기능 요구사항을 이해한다.
- 합의된 API, 식별자, 오류와 공개 상태 계약을 준수한다.
- 정상·예외·경계 조건을 포함한 자동화 테스트를 작성한다.
- 다른 Workstream의 코드와 문서를 리뷰한다.
- 요구사항, 계약, 구현 또는 운영 기대가 바뀌면 관련 문서를 갱신한다.
- 다른 Workstream에 미치는 변경 영향과 통합 위험을 조기에 공유한다.
- 저장소의 브랜치·커밋·리뷰 규칙을 준수한다.
- 다른 담당자의 기능과 공유 계약을 협의 없이 변경하지 않는다.
- 임시 구현, Stub 또는 Fake를 사용하면 제거 시점이나 테스트 전용 유지 근거를 기록한다.
- AI가 생성한 코드와 문서를 직접 검토하고 결과에 대한 최종 책임을 진다.
- 발표자료, 발표 리허설, 회의록과 README 작성·관리에 영크크 팀 공동 책임으로 참여한다.

### AI 활용 책임

- AI는 확정된 요구사항, API 계약과 ADR을 기준으로 사용한다.
- AI가 기능 범위를 임의로 확장하거나 미확정 정책을 결정하게 하지 않는다.
- AI 생성 코드도 동일한 코드 리뷰, 자동화 테스트와 보안 검증을 거친다.
- 프론트엔드 AI 작업에는 확정된 API 계약만 제공한다.
- AI 결과가 문서와 다르면 문서를 기준으로 검토한다.
- 문서 변경이 필요하면 코드를 문서에 맞추기 전에 영향받는 담당자와 팀 합의를 진행한다.
- 김인안·이우람·양성훈은 AI 활용 기준과 연동 방식을 공동으로 정리한다.
- 양성훈·김인안은 프론트엔드 구조와 백엔드 연동 기준을 공동으로 정리한다.
- 각 Workstream 담당자는 자신의 기능에 적용된 AI 결과와 화면 연동 결과를 검증한다.

## 9. 공동 결정 사항

다음 항목은 팀 공동 결정 대상이다.

- 도메인 또는 Workstream 경계 변경
- 공통 API 성공·빈 결과·오류 응답 형식
- 핵심 데이터 관계와 도메인 간 식별자 표현
- 날짜·시간 표현과 시간대 원칙
- 관리자 인증·권한 정책
- 공개·비공개·삭제 상태와 조합 우선순위
- 패키지 구조와 공유 파일 변경 규칙
- 새로운 외부 기술, 인프라 또는 라이브러리 도입
- MVP 범위 변경
- 다른 Workstream의 API·데이터·판정 계약에 영향을 주는 변경

다음 항목은 원칙적으로 Workstream 담당자가 결정한다.

- 담당 Workstream 내부 메서드 구조와 클래스 분리
- 테스트 데이터와 Stub/Fake 구성
- 도메인 규칙을 위반하지 않는 내부 구현 방식
- 외부 API·데이터 계약에 영향을 주지 않는 리팩터링
- 담당 기능 문서의 표현 개선

담당자 결정 항목이라도 다른 Workstream의 계약, 데이터 관계 또는 운영 기준에 영향을 주면 변경 전에 팀 협의를 거친다.

횡단 역할 담당자는 기술 결정을 단독 확정하지 않는다. 담당자가 기준, 선택지와 영향 범위를 정리해 제안하고, 영향받는 Workstream 담당자가 리뷰한 뒤 팀이 결정한다.

## 10. 역할 간 협업 규칙

- 변경 제안자는 영향받는 요구사항 ID, 계약, 데이터와 테스트를 먼저 식별한다.
- 기능 책임자는 구현 방향을 제안하고, 영향받는 Workstream 담당자는 계약 호환성과 통합 위험을 리뷰한다.
- 다른 Workstream의 내부 구현에 직접 의존하지 않고 합의된 식별자·상태·표시 정보·판정 결과 계약만 사용한다.
- [WS-01](../02-analysis/mvp-workstreams.md#5-ws-01-맛집-탐색)은 최종 탐색 조합, [WS-02](../02-analysis/mvp-workstreams.md#6-ws-02-맛집-상세-및-콘텐츠-조회)는 최종 상세 조합, [WS-03](../02-analysis/mvp-workstreams.md#7-ws-03-유튜버-기반-탐색)은 Visit 관계 판정, [WS-04](../02-analysis/mvp-workstreams.md#8-ws-04-관리자-데이터-등록)는 등록 순서와 조회 반영을 각각 소유한다.
- 공유 파일은 변경 범위를 최소화하고 한 변경에서 구현 책임자 한 명이 병합을 주도한다.
- 자신의 코드와 문서는 스스로 최종 승인하지 않으며 다른 Workstream 담당자 한 명 이상이 리뷰한다.
- 공통 계약과 핵심 데이터 관계 변경은 영향받는 모든 담당자가 리뷰한다.
- 이견이 생기면 이우람은 결정을 독점하지 않고 선택지, 근거, 영향과 결정 시점을 구조화한다.
- 작업 차단, 오류와 일정 위험은 발견 즉시 공유하고 임시 우회는 제거 조건과 함께 기록한다.

## 11. 역할 변경 기준

다음 경우 역할 조정을 검토한다.

- Workstream 규모가 예상보다 크게 증가한 경우
- 특정 팀원에게 High 복잡도 작업과 공통 작업이 집중된 경우
- 공통 작업이 기능 구현을 지속적으로 방해하는 경우
- 선행 작업 지연으로 담당자가 장기간 차단되는 경우
- 새로운 기능이 MVP에 공식 포함된 경우
- 담당자의 부재 또는 일정이 변경된 경우
- Workstream 경계 자체가 변경된 경우

역할 변경 시 변경 이유, 인수인계 산출물, 적용 시점과 미완료 위험을 기록하고 다음 문서를 함께 갱신한다.

- [roles.md](roles.md)
- [ownership.md](ownership.md)
- [mvp-workstreams.md](../02-analysis/mvp-workstreams.md)
- 관련 API 명세
- 구현 계획 및 Task 문서

- 영향: [WS-04](../02-analysis/mvp-workstreams.md#8-ws-04-관리자-데이터-등록) 일정, 계약 변경 절차와 인수 테스트
