## 3. 문제 현상

- 재현 조건: PR #125 본문 "병합 후 할 일" 절과 `.github/PULL_REQUEST_TEMPLATE.md:76-77`(또는 `CLAUDE.md` 9절)을 나란히 읽는다.
- 실제 결과: 템플릿·`CLAUDE.md`는 "정상적인 `develop → main` 병합 뒤에는 커밋 수 차이만을 이유로 `main → develop` 역동기화 PR을 만들지 않고, `main` 전용 Hotfix가 있을 때만 역동기화한다"고 명시하는데, PR #125 본문은 "배포 후 `main`의 병합 커밋을 `develop`으로 역류한다"라고 적어 같은 PR 안에서 정책과 실행 계획이 모순됐다.
- 기대 결과: 이 PR은 이미 병합된 develop PR 4건(#121~#124)을 `main`으로 승격하는 정상 릴리즈이며 `main` 전용 Hotfix가 아니므로, 정책의 예외 조건에 해당하지 않는다. 본문의 실행 계획이 정책과 일치해야 한다.
- 영향 범위: PR 본문 정확성. 코드·API·DB 계약에는 영향이 없다.

## 4. 근본 원인

이전 승격 PR([#101](https://github.com/team-youngkk/masit-on/pull/101))의 "병합 후 할 일" 문구를 참고해 PR #125를 작성하면서, #101의 역동기화 계획 문구를 그대로 옮겨 적었다. #101 작성 시점의 맥락은 확인하지 않았고, 이번 PR이 재확인·명문화하는 "정상 릴리즈는 역동기화하지 않는다"는 정책과 대조하지 않아 PR 본문 안에서 자기모순이 생겼다.

## 5. 해결

- 변경 내용: PR #125 본문 "병합 후 할 일"의 마지막 항목 "배포 후 `main`의 병합 커밋을 `develop`으로 역류한다"를 삭제하고, "이 PR은 정상적인 `develop → main` 승격이며 `main` 전용 Hotfix가 아니므로, 병합 후 커밋 수 차이만을 이유로 한 `main → develop` 역동기화 PR은 만들지 않는다"로 대체했다.
- 선택 이유: 코드·계약 변경이 아니라 PR 본문 서술 오류이므로, 실행 계획을 기존 정책 문구에 맞춰 정정하는 것이 최소 수정이다.
- 변경 파일: PR #125 본문(GitHub REST/GraphQL로 직접 정정, 저장소 커밋 없음)
- 고려한 대안: 없음 — 리뷰가 제시한 삭제 방향이 정책과 정확히 일치해 그대로 반영했다.
