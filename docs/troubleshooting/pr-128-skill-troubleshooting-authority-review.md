## 3. 문제 현상과 발생 조건

- 오류 메시지: 없음 (실행 오류가 아니라 문서·규칙 간 모순)
- 발생 환경: `masit-on` 저장소 `docs/pr-125-review-scope-fix` 브랜치, PR #128 리뷰 라운드. 대상은 실행 코드가 아니라 스킬 정의(`.claude/skills/`, `.codex/skills/`)와 트러블슈팅 문서
- 영향 범위: 이후 모든 구현·위임·리뷰의 판단 기준과 트러블슈팅 문서의 발견성. 실행 코드·API·DB 계약에는 영향이 없다

### 3.1 비계약 문서를 계약보다 높은 제약으로 승격

- 재현 조건: PR #128이 추가한 `implement-review-workflow/SKILL.md`의 "트러블슈팅 기록 선행 확인" 항목과 `AGENTS.md` 2절(또는 `CLAUDE.md` 2절) 권위 순서를 나란히 읽는다.
- 실제 결과: 추가한 규칙이 트러블슈팅 기록의 "재발 방지"를 조건 없이 구현 제약(`binding constraints`)으로 삼고, 그 제약을 서브에이전트 위임 프롬프트까지 전달하도록 지시했다. 권위 순서에 열거된 것은 확정 요구사항·Accepted ADR·API/데이터 계약·아키텍처·구현 컨벤션·외부 컨벤션 여섯 항목뿐이며 트러블슈팅 기록은 없다.
- 기대 결과: 트러블슈팅 기록은 회귀 위험을 상기시키는 검토 자료로 쓰고, 현재 계약과 충돌하면 계약이 이긴다.

### 3.2 이번 라운드의 기록이 인덱스에 없음

- 재현 조건: PR #128 리뷰 스레드를 처리한 뒤 `docs/troubleshooting/README.md` 목록을 확인한다.
- 실제 결과: PR #128의 앞선 변경은 PR #125 후속 대응이라 `pr-125-*.md`에 함께 기록했고 그 문서와 `pr-127-*.md`는 이미 인덱스에 있었다. 하지만 PR #128 자체에 달린 리뷰 스레드를 다루는 기록은 없어 인덱스에도 없었다.
- 기대 결과: 리뷰 라운드의 기록을 인덱스에서 찾을 수 있어야 한다. 이번 PR이 추가한 규칙(구현 전 트러블슈팅 기록 조회)은 인덱스가 완전하다는 전제에 의존한다.

### 3.3 신규 문서가 같은 PR이 갱신한 템플릿을 따르지 않음

- 재현 조건: 같은 PR의 커밋 `55eeea9`가 갱신한 `assets/troubleshooting-record-template.md`와 그 이후 작성한 이 문서의 최초 버전을 대조한다.
- 실제 결과: 템플릿은 10절 체계(메타데이터에 `주 문제 유형`·`기존 기록`, 5절 "확인 및 시도", 9절 "도입 전후 비교 지표" 신설)로 바뀌었는데, 이 문서는 구 8절 체계로 작성돼 신규 필드와 두 절이 모두 없었다.
- 기대 결과: 템플릿을 갱신한 PR이 만든 첫 문서는 새 템플릿을 따라야 한다. 그러지 않으면 다음 작성자가 이 문서를 예시로 복사해 새 템플릿이 무력화된다.

### 3.4 기록 생성 단위 기준이 스킬과 충돌

- 재현 조건: 이 문서 최초 버전의 재발 방지 두 번째 항목과 `.codex/skills/troubleshoot-pr-review/SKILL.md` 4절을 나란히 읽는다.
- 실제 결과: 기록은 "트러블슈팅 기록은 PR 단위로 만든다. 새 PR에 자체 리뷰 스레드가 달리면 그 PR 번호의 기록을 만든다"고 규정했고, 스킬 4절은 "같은 PR 또는 같은 문제의 기록이 이미 있으면 기존 문서에 추가하고, 별도 사건으로 남겨야 할 때만 새 문서를 만든다"고 규정했다. 같은 상황에 서로 다른 답을 준다.
- 기대 결과: 새 규칙에 따라 이 기록을 읽는 다음 작업자가 단일한 기준을 얻어야 한다.

## 4. 근본 원인

3.1은 스킬 규칙을 쓸 때 "이 문서를 반드시 읽어라"와 "이 문서를 제약으로 삼아라"를 구분하지 않은 것이 원인이다. 의도는 과거 실수 반복 방지였는데, 문장이 트러블슈팅 기록에 계약과 같은 강제력을 부여해 저장소가 이미 정한 문서 권위 순서와 모순됐다. 권위 순서를 다시 확인하지 않고 규칙을 추가한 절차상 누락이다.

3.2와 3.4는 같은 근본 원인을 공유한다. 기록 파일의 생성 단위를 "PR 단위"로 임의 가정하고, 같은 PR이 이미 고쳐 놓은 스킬 4절의 재사용 규칙(같은 문제면 갱신)을 확인하지 않았다. 그 가정 때문에 PR #128 기록이 없다는 공백(3.2)이 생겼고, 공백을 메우며 쓴 재발 방지 문구가 스킬과 충돌했다(3.4).

3.3의 원인은 같은 PR 안에서 템플릿을 갱신한 사실을 인지하지 못하고, 직전 기록(`pr-125-*.md`, 구 8절 체계)의 구조를 그대로 본떠 새 문서를 작성한 것이다. 이는 [pr-125 기록](pr-125-develop-to-main-sync-policy-review.md) 4절이 이미 지적한 "과거 문서 문구를 그대로 옮겨 적는" 실수와 같은 유형이며, 그 기록의 재발 방지를 이번 작성에 적용하지 않았다.

## 6. 최종 해결

- 변경 내용:
  - `.claude/skills/implement-review-workflow/SKILL.md`와 `.codex/skills/implement-review-workflow/SKILL.md`의 트러블슈팅 선행 확인 항목을 수정했다. "제약으로 삼는다"(`binding constraints`) → "회귀 위험 점검 목록"으로 바꾸고, 트러블슈팅 기록이 권위 순서에 없는 비계약 문서임을 명시했다. 각 재발 방지 항목을 현재 요구사항·ADR·계약·아키텍처와 대조해 유효한 항목만 제약·위임 프롬프트로 전달하고, 충돌 시 권위 순서를 따르며 기록을 버리도록 했다. 낡은 기록 때문에 구현을 멈추지는 않되 문서 충돌로 보고하도록 구분했다(3.1).
  - 이 문서를 작성하고 `docs/troubleshooting/README.md` 인덱스 최상단에 등록했다(3.2).
  - 이 문서를 갱신된 10절 템플릿으로 다시 작성했다. `주 문제 유형`·`기존 기록` 메타데이터, 5절 "확인 및 시도", 9절 "도입 전후 비교 지표"를 채웠고 비교 지표는 `해당 없음`과 이유를 기록했다(3.3).
  - 8절 재발 방지의 기록 생성 단위 기준을 스킬 4절과 같은 문구("같은 문제는 기존 기록을 갱신하고, 별도 사건일 때만 새 기록")로 교체하고, PR #128을 별도 사건으로 판단한 근거를 1절 `기존 기록`과 8절에 남겼다(3.4).
- 선택 이유: 3.1은 규칙의 의도(회귀 방지)를 유지하면서 강제력만 계약 아래로 낮추는 최소 수정이다. 규칙을 되돌리면 이번 PR의 목적이 사라지고, 그대로 두면 문서 권위 정책과 모순이 남는다. 3.4는 두 기준 중 스킬 쪽을 남겼다 — 스킬이 실제 작업 절차를 구동하는 문서이므로 기록이 스킬을 따라야 방향이 맞다.
- 변경 파일: `.claude/skills/implement-review-workflow/SKILL.md`, `.codex/skills/implement-review-workflow/SKILL.md`, `docs/troubleshooting/pr-128-skill-troubleshooting-authority-review.md`(이 문서), `docs/troubleshooting/README.md`
- 고려한 대안: 5절 표의 기각 항목 참고. 특히 이 기록을 `pr-125-*.md`에 통합하는 방안은 원인과 대상 파일이 달라 채택하지 않았다.

## 8. 재발 방지 및 다음 확인

- 재발 방지:
  - 스킬·지침에 "이 문서를 따르라"는 규칙을 추가할 때는 그 문서가 `AGENTS.md`·`CLAUDE.md` 2절 권위 순서의 어디에 해당하는지 먼저 확인하고, 순서에 없는 문서에는 계약과 같은 강제력을 부여하지 않는다. 이 항목은 두 `implement-review-workflow/SKILL.md`에 규칙으로 반영했다.
  - 트러블슈팅 기록은 `troubleshoot-pr-review/SKILL.md` 4절과 같은 기준으로 만든다 — **같은 PR 또는 같은 문제의 기록이 있으면 그 문서를 갱신하고, 별도 사건일 때만 새 문서를 만들어 서로 링크한다.** PR 번호가 다르다는 것만으로 새 문서를 만들지 않는다. 이 문서를 별도로 남긴 근거는 1절 `기존 기록`에 있다.
  - 트러블슈팅 기록을 새로 쓰기 전에 `assets/troubleshooting-record-template.md`를 그 시점에 다시 읽는다. 직전 기록의 구조를 기억이나 복사로 재현하지 않는다 — 같은 PR에서 템플릿이 바뀌었을 수 있다.
- 다음 확인: 위 세 항목이 실제로 지켜지는지는 다음 리뷰·구현 라운드에서 확인한다. 담당은 이 저장소에서 해당 스킬을 실행하는 작업자이며, 별도 추적 이슈는 만들지 않았다(스킬 규칙 자체에 반영돼 매 실행에서 확인된다).
