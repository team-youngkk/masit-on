# 맛잇온 요구사항 검토 결과

## 1. 문서 목적

이 문서는 맛잇온 비즈니스 규칙 작성 과정에서 확인된 미결정 사항의 합의 결과를 기록한다. 확정된 결과는 [business-rules.md](business-rules.md)에 반영하며, 기술 구현 방식은 후속 설계에서 결정한다.

## 2. 확정된 결정

### RV-BR-001 유튜버 관리 단위

- 상태: 결정 완료
- 결정:
  - MVP에서는 YouTube 채널을 유튜버 정보의 고유한 관리 단위로 사용한다.
  - 한 사람이 여러 채널을 운영하면 채널별로 별도 등록한다.
  - 여러 사람이 하나의 채널을 운영하면 하나의 유튜버 정보로 등록한다.
  - 문서와 화면에서는 서비스 표준 용어인 `유튜버`를 사용할 수 있다.
- 근거:
  - 영상 게시 주체, 동일 채널 중복 판단과 방문 관계의 기준을 일관되게 유지할 수 있다.

### RV-BR-002 유튜버 대표 이름과 채널명 변경

- 상태: 결정 완료
- 결정:
  - 화면의 대표 이름은 현재 등록된 YouTube 채널명으로 한다.
  - 채널명이 변경되어도 YouTube에서 동일 채널임이 확인되면 기존 유튜버 정보로 유지한다.
  - 기존 영상과 방문 관계는 유지한다.
  - 채널명만으로 동일 채널 여부를 판단하지 않는다.
  - 동일 채널인지 확인할 수 없으면 변경하거나 신규 등록하지 않고 보류한다.

### RV-BR-003 채널 삭제·비공개 처리

- 상태: 결정 완료
- 결정:
  - 채널이 삭제되거나 비공개된 사실을 관리자가 확인하면 해당 유튜버 정보를 일반 사용자에게 비공개한다.
  - 해당 유튜버의 방문 관계는 유튜버 필터와 맛집 상세에서 제외한다.
  - 연결된 맛집 기본 정보는 계속 공개한다.
  - 유튜버 정보, 영상과 방문 관계는 자동 삭제하지 않고 관리자 확인 목적으로 유지한다.
  - 채널이 다시 공개되어도 관리자가 확인하기 전에는 자동으로 재공개하지 않는다.
  - 일시적인 링크 오류만으로 비공개 처리하지 않는다.

### RV-BR-004 맛집 이름·주소 변경

- 상태: 결정 완료
- 결정:
  - 상호명만 변경되고 카카오에서 동일한 장소로 확인되면 기존 맛집 정보를 갱신하고 방문 관계를 유지한다.
  - 주소 표기 오류를 정정하는 경우에도 기존 맛집과 방문 관계를 유지한다.
  - 실제로 다른 장소로 이전한 경우에는 기존 장소와 새 장소를 별도 맛집으로 취급한다.
  - 이전 전 영상과 방문 관계를 새 장소로 자동 이전하지 않는다.

### RV-BR-005 폐업·장기 운영 중단 처리

- 상태: 결정 완료
- 결정:
  - 폐업이 확인된 맛집은 비공개하고 검색, 필터와 상세에서 제외한다.
  - 장기 운영 중단이 확인된 맛집도 재개 여부를 확인할 때까지 비공개한다.
  - 기존 정보와 관계는 관리자 확인 목적으로 유지한다.
  - 재개업이 확인되면 관리자가 장소의 동일성을 검증한 후 재공개한다.

### RV-BR-006 영상 정보 변경과 이용 불가 처리

- 상태: 결정 완료
- 결정:
  - 제목이나 썸네일이 변경되어도 동일한 YouTube 원본 영상이면 기존 영상 정보로 유지하고 기존 방문 관계도 유지한다.
  - 영상이 삭제되거나 비공개된 사실을 관리자가 확인하면 관련 영상 목록에서 제외한다.
  - 해당 영상만을 근거로 하는 방문 관계도 사용자 조회와 유튜버 필터에서 제외한다.
  - 연결된 맛집 기본 정보는 계속 공개한다.
  - 영상과 방문 관계는 자동 삭제하지 않고 관리자 확인 목적으로 유지한다.
  - 일시적인 링크 오류만으로 비공개 처리하지 않는다.
  - 영상이 다시 공개되면 관리자가 실제 방문 근거를 다시 확인한 후 재공개한다.

### RV-BR-007 방문 날짜

- 상태: 결정 완료
- 결정:
  - MVP에서는 실제 방문 날짜를 별도로 관리하지 않는다.
  - 영상 게시일을 방문 날짜로 사용하지 않는다.
  - 방문 날짜가 필요한 기능은 범위 변경 후, 영상 또는 다른 검증 가능한 출처에서 날짜를 확인할 수 있는 경우에만 도입한다.

### RV-BR-008 방문 관계 검증 상태

- 상태: 결정 완료
- 결정:
  - MVP에서는 방문 관계에 별도 검증 상태를 두지 않는다.
  - 관리자가 실제 방문 근거를 확인한 뒤 등록을 완료했다는 사실을 검증 완료로 본다.
  - 검증되지 않은 관계는 등록하지 않는다.

### RV-BR-009 잘못 등록된 데이터의 정정

- 상태: 결정 완료
- 결정:
  - 오류가 확인된 공개 데이터는 먼저 일반 사용자 조회에서 제외한다.
  - 관리자가 출처와 사실 관계를 다시 확인한 뒤 정정한다.
  - 정정 후 등록 및 공개 조건을 다시 충족한 경우에만 재공개한다.
  - 오류 데이터를 다른 데이터로 임의 병합하거나 관련 관계를 자동 이전하지 않는다.
  - 관리자 수정·삭제 화면은 MVP 범위에 추가하지 않으며, 해당 기능 도입 시 이 정책을 따른다.

### RV-BR-010 동시 등록과 보류 요청

- 상태: 결정 완료
- 결정:
  - 동일 대상에 대한 등록 요청이 동시에 처리되어도 하나의 데이터 또는 관계만 등록되어야 한다.
  - 먼저 등록이 완료된 기존 대상을 이후 요청에 사용한다.
  - 동일 여부를 판단할 수 없는 요청은 일반 사용자에게 노출하지 않고 보류한다.
  - 보류한 요청은 관리자가 출처와 식별 정보를 다시 확인한 뒤 등록, 기존 대상 사용 또는 거부로 종결한다.

### RV-BR-011 빈 검색어 처리

- 상태: 결정 완료
- 결정:
  - 검색어의 앞뒤 공백을 제거한 결과가 비어 있으면 맛집 이름 조건을 적용하지 않는다.
  - 다른 필터가 있으면 해당 필터만 적용하고, 다른 조건도 없으면 전체 맛집 목록을 조회한다.

### RV-BR-012 기본 정렬

- 상태: 결정 완료
- 결정:
  - 맛집 목록의 기본 정렬은 맛집 이름 오름차순으로 한다.
  - 맛집 이름이 같으면 전체 도로명주소 오름차순으로 정렬한다.
  - 같은 조건의 페이지 조회에서 결과 순서가 변해 누락되거나 중복되지 않아야 한다.

### RV-BR-013 페이지 크기

- 상태: 결정 완료
- 결정:
  - 일반 목록의 기본 페이지 크기는 20개로 한다.
  - 일반 목록에서 사용자가 선택할 수 있는 페이지 크기는 10개, 20개 또는 50개로 제한한다.
  - 일반 목록에서 페이지 크기를 지정하지 않으면 20개를 적용한다.
  - 단, 3열 카드 UI를 사용하는 WS-01 맛집 탐색의 `GET /api/restaurants`와 자연어 검색의 `POST /api/restaurants/natural-language-search`는 기본 페이지 크기 21개와 허용 크기 10개, 20개, 21개, 50개를 적용한다. 기존 호출자의 `size=20` 요청은 계속 허용한다.

### RV-BR-014 기타 음식 카테고리 기록

- 상태: 결정 완료
- 결정:
  - `기타` 카테고리는 기존 분류에 명확히 해당하지 않을 때만 선택한다.
  - 관리자는 실제 음식 종류를 알 수 있는 구체적인 명칭을 필수로 기록한다.
  - 공백만 있거나 `기타`, `음식`처럼 실제 종류를 식별할 수 없는 기록은 허용하지 않는다.

### RV-BR-015 음식 카테고리 분류 기준

- 상태: 결정 완료
- 결정:
  - MVP에서는 현재 정의된 10개 대표 음식 카테고리를 더 세분화하지 않는다.
  - 관리자는 해당 맛집의 주된 메뉴와 영업 정체성을 가장 잘 나타내는 카테고리 1개를 지정한다.
  - 여러 종류의 음식을 제공하더라도 복수 카테고리를 지정하지 않는다.
  - 기존 카테고리 중 하나로 명확히 분류할 수 없을 때만 `기타`를 사용한다.
  - 판단 근거가 부족하면 임의로 지정하지 않고 등록을 보류한다.

## 3. 후속 기술 설계 항목

다음 사항은 비즈니스 정책을 변경하지 않는 범위에서 후속 기술 설계로 결정한다.

- 공개·비공개·삭제 상태의 저장 구조
- 물리 삭제 또는 논리 삭제 구현 방식
- YouTube 동일 채널 및 동일 영상 식별값의 저장 방식
- 동시 등록 방지 구현 방식
- 관리자 JWT 만료·서명 키 교체와 Redis Refresh Token 세부 운영
- YouTube API 호출 실패·할당량 초과 처리의 기술 구현
- 자동 주기 동기화 도입 시점과 외부 링크 상태 확인 주기
- 문자열 정렬 방식과 최종 정렬 안정성 보장 방식
- 페이지 요청·응답의 구체적인 API 표현

## 4. 3차 확장 확정 결정과 실행 게이트

### RV-BR-016 경로 결과 만료 시간

- 상태: 결정 완료
- 결정:
  - 모든 경로 결과는 생성 시각과 만료 시각을 가진다.
  - 만료 뒤에는 기존 거리·시간을 정상 결과로 재사용하지 않고 새 경로를 조회한다.
  - `expiresAt`은 `generatedAt`으로부터 5분 뒤로 정한다.
  - 초기에는 캐시를 사용하지 않으며, 만료 전에도 서버는 결과를 저장·재사용하지 않는다.
- 영향:
  - 코스 API 응답, 캐시 키·TTL, 외부 호출 비용과 재조회 UX

### RV-NFR-017 자연어·AI 품질 목표값

- 상태: 결정 완료
- 결정:
  - 자연어 Dataset은 240건, AI Dataset은 중복 영상 그룹을 제거한 120건, 코스 Fixture는 60건으로 고정한다.
  - 세 Dataset은 Development 60%, Calibration 20%, Release holdout 20%로 분할한다. 동일 영상·맛집·문장 변형 그룹은 하나의 분할에만 둔다.
  - 자연어 조건 집합 exact match는 90% 이상, 지원 조건 재현율은 95% 이상, 미지원 조건 오적용은 0건으로 한다.
  - AI 맛집·주소 후보 정밀도는 90% 이상, 방문 근거 재현율은 80% 이상, 자동 등록 정밀도는 90% 이상으로 한다. 잘못된 장소 연결과 자동 검증 우회는 0건이어야 한다.
  - AI 태그 후보 정밀도는 90% 이상, 재현율은 80% 이상으로 하며, 미확정·근거 없는 태그의 공개는 0건으로 한다.
  - Critical 오류는 평균 점수와 무관하게 0건이어야 한다. 정답 충돌은 Critical 100%, 일반 사례 20%를 교차 검토한다.
- 영향:
  - 모델·Prompt 활성화 게이트, 회귀 테스트와 자동 차단·예외 보정 작업량

### RV-NFR-018 AI·Mobility timeout과 재시도 수치

- 상태: 결정 완료
- 결정:
  - 연결·응답·전체 작업 timeout, 동시 처리·rate limit, 최대 재시도 횟수와 전체 시간 예산을 모두 유한값으로 둔다.
  - 429·quota·비용 상한은 fail-closed로 처리하고, 재시도로 비용 상한을 우회하지 않는다.
  - Gemini 호출은 연결 5초·응답 90초·시도 전체 120초, 최대 2회 재시도(총 3회), backoff 5초·30초를 사용한다.
  - Gemini 정책 거부·입력 오류·Schema 오류는 재시도하지 않는다.
  - Kakao Mobility는 연결 1초·응답 4초·요청 전체 5초, 자동 재시도 0회로 한다. 실패하면 즉시 부분·실패 결과를 반환한다.
- 영향:
  - 비동기 작업 복구, 코스 응답 시간, 비용 hard stop과 운영 경보
