# 맛잇온 비즈니스 규칙

## 1. 문서 목적

이 문서는 맛잇온 MVP와 승인된 확장 단계의 여러 기능에 공통으로 적용되는 서비스 운영 규칙, 데이터 등록 기준, 관계 생성 기준, 공개 기준과 중복 판단 기준을 정의한다. API 명세, 데이터 모델과 테스트는 이 문서의 규칙을 검증 가능한 기준으로 사용한다.

기준 문서는 다음과 같다.

- [docs/00-overview/service-overview.md](../00-overview/service-overview.md)
- [docs/00-overview/scope.md](../00-overview/scope.md)
- [docs/00-overview/glossary.md](../00-overview/glossary.md)
- [docs/01-requirements/functional-requirements.md](functional-requirements.md)
- [docs/01-requirements/requirements-review.md](requirements-review.md)

기준 문서에서 확정되지 않은 사항은 [requirements-review.md](requirements-review.md)의 합의 결과를 따르며, 아직 결정되지 않은 사항만 제14장의 `검토 필요` 항목으로 유지한다.

## 2. 규칙 작성 원칙

- 각 규칙은 `BR-{DOMAIN}-{NUMBER}` 형식의 고유 ID를 가진다.
- 하나의 규칙에는 하나의 검증 가능한 핵심 정책만 포함한다.
- 기능별 화면 또는 처리 절차를 반복하지 않고 여러 기능이 공유하는 업무 정책을 정의한다.
- 확정된 요구사항과 범위만 규칙으로 작성하며, 미확정 사항은 제14장에 기록한다.
- 규칙의 적용 대상, 허용, 금지, 예외, 위반 시 처리와 관련 요구사항을 명시한다.
- 데이터베이스 구조, API URL, HTTP 상태 코드, ORM, 인덱스, 캐시, 검색 엔진, 삭제 구현 방식, 인증 기술과 외부 API 사용 여부는 후속 기술 설계에서 결정한다.
- MVP에서 제외된 기능은 범위 변경 절차 없이 규칙의 예외로 추가하지 않는다.
- 정보 변경, 정정, 비공개 및 재공개 규칙은 해당 상황에서 지켜야 할 운영 정책을 정의하며, 관리자 수정·삭제·상태 관리 화면을 MVP 범위에 추가하지 않는다.

## 3. 맛집 규칙

### BR-RESTAURANT-001 맛집의 의미

- 규칙:
  - 맛집은 관리자가 검증하여 맛잇온에 등록한 음식점을 의미한다.
- 적용 대상:
  - 맛집 등록
  - 맛집 목록·검색·필터·상세 조회
- 허용:
  - 서비스 등록 기준을 충족한 음식점을 맛집으로 취급하는 경우
- 금지:
  - 등록되지 않은 음식점을 서비스의 맛집으로 노출하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 등록되지 않은 음식점은 일반 사용자 조회 대상에서 제외한다.
- 관련 요구사항:
  - [FR-RESTAURANT-001](functional-requirements.md#fr-restaurant-001-맛집-목록-조회)
  - [FR-ADMIN-002](functional-requirements.md#fr-admin-002-맛집-정보-등록)

### BR-RESTAURANT-002 영상과 독립된 맛집

- 규칙:
  - 맛집은 영상 또는 방문 관계가 없어도 등록할 수 있고, 공개 상태이면 기본 정보를 조회할 수 있어야 한다.
- 적용 대상:
  - 맛집 등록
  - 맛집 목록·상세 조회
- 허용:
  - 영상과 방문 관계가 없는 맛집의 기본 정보를 등록하고 공개하는 경우
- 금지:
  - 영상이나 방문 관계가 없다는 이유만으로 맛집 기본 조회를 제한하는 경우
- 예외:
  - 맛집 자체가 비공개 또는 삭제 상태인 경우
- 위반 시 처리:
  - 연결 정보가 없는 영역만 빈 결과로 제공하고 맛집 기본 정보는 제공한다.
- 관련 요구사항:
  - [FR-RESTAURANT-001](functional-requirements.md#fr-restaurant-001-맛집-목록-조회)
  - [FR-RESTAURANT-008](functional-requirements.md#fr-restaurant-008-맛집-기본-정보-조회)
  - [FR-RESTAURANT-011](functional-requirements.md#fr-restaurant-011-영상-연결이-없는-맛집-상세-조회)
  - [FR-ADMIN-002](functional-requirements.md#fr-admin-002-맛집-정보-등록)

### BR-RESTAURANT-003 맛집 최소 등록 정보

- 규칙:
  - 맛집 등록에는 맛집 이름, 카카오에서 확인한 동일 장소 정보와 카카오 장소 링크, 서울특별시 내 전체 도로명주소, 전화번호와 사전 정의된 대표 음식 카테고리 1개가 모두 필요하다.
- 적용 대상:
  - 맛집 등록
  - 맛집 공개 검증
- 허용:
  - 필수 정보가 모두 유효하고 관리자가 장소 일치 여부를 확인한 경우
- 금지:
  - 필수 정보가 누락되거나 서울특별시 밖의 장소를 등록하는 경우
- 예외:
  - 건물명, 층 또는 호수 등 상세 위치는 해당 정보가 있는 경우에만 등록한다.
- 위반 시 처리:
  - 맛집 등록을 거부한다.
- 관련 요구사항:
  - [FR-RESTAURANT-008](functional-requirements.md#fr-restaurant-008-맛집-기본-정보-조회)

  - [FR-ADMIN-002](functional-requirements.md#fr-admin-002-맛집-정보-등록)

### BR-RESTAURANT-004 대표 음식 카테고리

- 규칙:
  - 하나의 맛집에는 주된 메뉴와 영업 정체성을 가장 잘 나타내는 사전 정의된 대표 음식 카테고리를 정확히 1개 지정한다.
- 적용 대상:
  - 맛집 등록
  - 음식 카테고리 표시 및 필터
- 허용:
  - 한식, 중식, 일식, 양식, 동남아 음식, 인도·남아시아 음식, 분식, 카페·디저트, 술집·주점, 기타 중 1개를 지정하는 경우
- 금지:
  - 복수 카테고리를 지정하거나 사전 정의되지 않은 카테고리를 지정하거나 근거가 부족한 상태에서 임의로 지정하는 경우
- 예외:
  - `기타`는 기존 카테고리에 명확히 해당하지 않을 때만 사용하며, 별도 구체 음식 종류를 저장하지 않는다.
- 위반 시 처리:
  - 대표 카테고리의 판단 근거가 부족하면 등록을 보류하고, 대표 카테고리가 없거나 `기타`의 음식 종류 기록이 비어 있거나 식별할 수 없으면 맛집 등록을 거부한다.
- 관련 요구사항:
  - [FR-RESTAURANT-004](functional-requirements.md#fr-restaurant-004-음식-카테고리별-필터)
  - [FR-RESTAURANT-010](functional-requirements.md#fr-restaurant-010-음식-카테고리-확인)
  - [FR-ADMIN-002](functional-requirements.md#fr-admin-002-맛집-정보-등록)

### BR-RESTAURANT-005 맛집의 지역 소속

- 규칙:
  - 하나의 맛집은 등록된 전체 도로명주소에 해당하는 서울특별시 자치구 1개에 속한다.
- 적용 대상:
  - 맛집 등록
  - 지역 표시 및 필터
- 허용:
  - 서울특별시 내 유효한 전체 도로명주소와 그 주소의 자치구를 등록하는 경우
- 금지:
  - 둘 이상의 자치구를 지정하거나 서울특별시 밖의 지역을 지정하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 맛집 등록을 거부한다.
- 관련 요구사항:
  - [FR-RESTAURANT-003](functional-requirements.md#fr-restaurant-003-지역별-필터)
  - [FR-RESTAURANT-009](functional-requirements.md#fr-restaurant-009-지역-정보-확인)
  - [FR-ADMIN-002](functional-requirements.md#fr-admin-002-맛집-정보-등록)

### BR-RESTAURANT-006 맛집 중복 판단

- 규칙:
  - 카카오에서 동일한 장소로 확인되는 맛집은 동일 맛집으로 판단한다.
- 적용 대상:
  - 맛집 등록
  - 중복 검증
- 허용:
  - 카카오에서 서로 다른 장소로 확인되는 맛집을 별도로 등록하는 경우
- 금지:
  - 카카오에서 동일한 장소로 확인되는 맛집을 새 맛집으로 등록하는 경우
- 예외:
  - 동일 여부를 판단할 수 없는 경우에는 동일 또는 별도 맛집으로 확정하지 않는다.
- 위반 시 처리:
  - 새 등록을 거부하고 기존 맛집을 사용한다. 동일 여부가 불명확하면 등록을 보류한다.
- 관련 요구사항:
  - [FR-ADMIN-002](functional-requirements.md#fr-admin-002-맛집-정보-등록)

### BR-RESTAURANT-007 동일 상호의 지점 구분

- 규칙:
  - 상호명이 같아도 카카오에서 서로 다른 장소로 확인되는 지점은 별도 맛집으로 등록할 수 있다.
- 적용 대상:
  - 맛집 등록
  - 중복 검증
- 허용:
  - 동일 상호의 지점별 카카오 장소가 서로 다른 경우
- 금지:
  - 상호명만으로 서로 다른 지점을 하나의 맛집으로 병합하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 카카오 장소 일치 여부를 다시 검증한다.
- 관련 요구사항:
  - [FR-ADMIN-002](functional-requirements.md#fr-admin-002-맛집-정보-등록)

### BR-RESTAURANT-008 맛집 공개 조건

- 규칙:
  - 일반 사용자에게는 필수 등록 기준을 충족하고 공개 상태인 맛집만 노출한다.
- 적용 대상:
  - 맛집 목록·검색·필터·상세 조회
- 허용:
  - 공개 상태인 맛집을 일반 사용자 조회에 포함하는 경우
- 금지:
  - 비공개 또는 삭제 상태인 맛집을 일반 사용자 조회에 포함하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 해당 맛집을 일반 사용자 조회 결과에서 제외한다.
- 관련 요구사항:
  - [FR-RESTAURANT-001](functional-requirements.md#fr-restaurant-001-맛집-목록-조회)
  - [FR-RESTAURANT-008](functional-requirements.md#fr-restaurant-008-맛집-기본-정보-조회)

### BR-RESTAURANT-009 맛집 이름 변경

- 규칙:
  - 상호명이 변경되어도 카카오에서 동일한 장소로 확인되면 기존 맛집으로 유지하고 기존 방문 관계를 보존한다.
- 적용 대상:
  - 맛집 정보 변경
  - 중복 검증
  - 방문 관계 정합성
- 허용:
  - 동일 장소임을 관리자가 확인한 뒤 등록된 상호명을 갱신하는 경우
- 금지:
  - 상호명 변경만으로 새 맛집을 만들거나 기존 방문 관계를 이전 또는 삭제하는 경우
- 예외:
  - 동일 장소인지 확인할 수 없으면 변경을 보류한다.
- 위반 시 처리:
  - 장소 동일성을 다시 검증하고 확인 전까지 기존 정보를 유지한다.
- 관련 요구사항:
  - [FR-ADMIN-002](functional-requirements.md#fr-admin-002-맛집-정보-등록)

### BR-RESTAURANT-010 주소 변경과 장소 이전

- 규칙:
  - 주소 표기 오류의 정정은 기존 맛집과 방문 관계를 유지하되, 실제로 다른 장소로 이전한 경우 기존 장소와 새 장소를 별도 맛집으로 취급한다.
- 적용 대상:
  - 맛집 정보 변경
  - 맛집 중복 판단
  - 방문 관계 정합성
- 허용:
  - 주소 표기만 바로잡거나 실제 이전한 새 장소를 별도 맛집으로 등록하는 경우
- 금지:
  - 이전 전 영상과 방문 관계를 새 장소로 자동 이전하는 경우
- 예외:
  - 카카오에서 장소의 동일성을 확인할 수 없으면 정정 또는 신규 등록을 보류한다.
- 위반 시 처리:
  - 장소별 맛집 정보를 분리하고 검증되지 않은 관계 이전을 거부한다.
- 관련 요구사항:
  - [FR-ADMIN-002](functional-requirements.md#fr-admin-002-맛집-정보-등록)
  - [FR-VISIT-001](functional-requirements.md#fr-visit-001-맛집유튜버영상-방문-관계-등록)

### BR-RESTAURANT-011 폐업과 장기 운영 중단

- 규칙:
  - 폐업 또는 장기 운영 중단이 확인된 맛집은 재개 여부를 확인할 때까지 비공개 상태로 관리한다.
- 적용 대상:
  - 맛집 상태 판단
  - 맛집 재공개 검증
- 허용:
  - 기존 정보와 관계를 관리자 확인 목적으로 유지하고, 재개업 시 장소 동일성을 검증한 뒤 재공개하는 경우
- 금지:
  - 폐업 또는 장기 운영 중단이 확인된 맛집을 공개 상태로 유지하거나 관련 데이터를 자동 삭제하는 경우
- 예외:
  - 일시적인 정보 조회 오류만으로 운영 중단을 확정하지 않는다.
- 위반 시 처리:
  - 해당 맛집을 비공개 상태로 전환하고 재개업 검증 전까지 재공개하지 않는다.
- 관련 요구사항:
  - [FR-RESTAURANT-001](functional-requirements.md#fr-restaurant-001-맛집-목록-조회)
  - [FR-RESTAURANT-008](functional-requirements.md#fr-restaurant-008-맛집-기본-정보-조회)

## 4. 유튜버 및 채널 규칙

### BR-CREATOR-001 유튜버 정보의 의미

- 규칙:
  - MVP의 유튜버 정보는 YouTube 채널을 고유한 관리 단위로 하며, `유튜버`는 해당 채널을 지칭하는 서비스 표준 용어다.
- 적용 대상:
  - 유튜버 등록
  - 방문 관계
  - 유튜버 표시 및 필터
- 허용:

- 예외:
  - 없음
- 위반 시 처리:
  - YouTube 채널 단위로 다시 식별하고 동일 채널 여부가 불명확하면 등록을 보류한다.

- 규칙:

- 적용 대상:

- 예외:

- 위반 시 처리:

### BR-CREATOR-004 유튜버 표시 정보

- 규칙:
  - 일반 사용자 조회의 유튜버 대표 이름은 현재 등록된 YouTube 채널명으로 하며, 맛집 상세에는 등록된 채널 링크를 함께 제공한다.
  - 유튜버 필터 선택 목록에는 공개 유튜버의 식별자와 현재 채널명만 채널명 오름차순으로 제공한다.
  - 맛집 목록에는 중복 제거한 채널명을 채널명 오름차순으로 최대 3명까지 표시하고, 나머지는 `외 N명`으로 축약한다. 전체 방문 유튜버는 맛집 상세에서 제공한다.
- 적용 대상:
  - 맛집 목록
  - 맛집 상세
  - 방문 유튜버 조회
- 허용:
  - 관리자가 검증한 현재 채널명을 표시하는 경우
- 금지:
  - 검증되지 않은 별칭이나 개인 제작자 이름을 대표 이름으로 표시하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 검증된 표시 정보가 없는 유튜버는 일반 사용자 조회에 제공하지 않는다.
- 관련 요구사항:
  - [FR-CREATOR-003](functional-requirements.md#fr-creator-003-유튜버-필터-선택-목록-조회)

- 금지:
  - 근거 영상과 무관한 유튜버를 방문 관계에 연결하는 경우
- 예외:
  - 여러 제작자가 참여한 영상도 게시된 YouTube 채널을 유튜버 관리 단위로 사용한다.
- 위반 시 처리:

### BR-CREATOR-006 채널명 변경과 동일성 유지

- 규칙:
  - 채널명이 변경되어도 YouTube에서 동일 채널임이 확인되면 기존 유튜버 정보로 유지하고 기존 영상과 방문 관계를 보존한다.
- 적용 대상:
  - 유튜버 정보 변경
  - 중복 검증
  - 방문 관계 정합성
- 허용:
  - 동일 채널임을 관리자가 확인한 뒤 대표 채널명을 갱신하는 경우
- 금지:
  - 채널명만으로 동일성을 판단하거나 채널명 변경만으로 새 유튜버 정보를 등록하는 경우
- 예외:
  - 동일 채널인지 확인할 수 없으면 변경과 신규 등록을 보류한다.
- 위반 시 처리:
  - 채널 동일성을 다시 검증하고 기존 관계를 임의로 변경하지 않는다.

### BR-CREATOR-007 채널 이용 불가 처리

- 규칙:
  - 채널이 삭제되거나 비공개된 사실을 관리자가 확인하면 해당 유튜버 정보를 비공개 상태로 관리한다.
- 적용 대상:
  - 유튜버 상태 판단
  - 유튜버 재공개 검증
- 허용:
  - 관련 데이터를 관리자 확인 목적으로 유지하고 채널 재공개 후 관리자가 확인한 뒤 다시 공개하는 경우
- 금지:
  - 채널 이용 불가만을 이유로 유튜버 정보, 영상 또는 방문 관계를 자동 삭제하는 경우
  - 일시적인 링크 오류만으로 비공개 처리하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 해당 유튜버를 비공개 상태로 전환하고 관리자 확인 전까지 재공개하지 않는다.
- 관련 요구사항:

  - 동일 원본 영상임을 관리자가 확인한 뒤 제목 또는 썸네일을 갱신하는 경우
- 금지:
  - 제목 또는 썸네일 변경만으로 새 영상을 등록하거나 기존 방문 관계를 변경하는 경우
- 예외:
  - 동일 원본 영상인지 확인할 수 없으면 변경을 보류한다.
- 위반 시 처리:
  - 원본 영상의 동일성을 다시 검증한다.
- 관련 요구사항:
  - [FR-ADMIN-004](functional-requirements.md#fr-admin-004-영상-정보-등록)

### BR-VIDEO-009 영상 이용 불가 처리

- 규칙:
  - 영상이 삭제되거나 비공개된 사실을 관리자가 확인하면 해당 영상을 비공개 상태로 관리한다.
- 적용 대상:
  - 영상 상태 판단
  - 영상 재공개 검증
- 허용:
  - 영상과 관계를 관리자 확인 목적으로 유지하고, 영상 재공개 후 실제 방문 근거를 다시 확인한 뒤 재공개하는 경우
- 금지:
  - 영상 이용 불가만을 이유로 영상, 방문 관계 또는 맛집 정보를 자동 삭제하는 경우
  - 일시적인 링크 오류만으로 영상과 관계를 비공개 처리하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 해당 영상을 비공개 상태로 전환하고 실제 방문 근거 재검증 전까지 재공개하지 않는다.
- 관련 요구사항:

## 6. 방문 관계 규칙

### BR-VISIT-001 방문 관계의 구성

- 규칙:
  - 하나의 방문 관계는 등록된 맛집 1개, 유튜버 1명과 실제 방문 근거 영상 1개를 연결한다.
- 적용 대상:
  - 방문 관계 등록
  - 유튜버 필터
  - 방문 유튜버 및 관련 영상 조회
- 허용:
  - 세 참조 대상이 모두 등록되어 있고 서로 일치하는 경우
- 금지:
  - 참조 대상 중 하나라도 존재하지 않거나 서로 일치하지 않는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 방문 관계 등록을 거부한다.
- 관련 요구사항:
  - [FR-VISIT-001](functional-requirements.md#fr-visit-001-맛집유튜버영상-방문-관계-등록)

### BR-VISIT-002 방문 근거 필수

- 규칙:
  - 방문 관계는 실제 방문을 확인할 수 있는 영상을 근거로 생성해야 한다.
- 적용 대상:
  - 방문 관계 등록
  - 유튜버별 맛집 조회
  - 맛집 상세의 방문 유튜버 조회
  - 관련 영상 조회
- 허용:
  - 영상에서 유튜버의 해당 맛집 실제 방문이 확인되는 경우
- 금지:
  - 근거 영상 없이 관계를 생성하는 경우
  - 단순 언급, 추천 또는 추정만으로 관계를 생성하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 방문 관계 등록을 거부한다.
- 관련 요구사항:
  - [FR-CREATOR-001](functional-requirements.md#fr-creator-001-유튜버-기준-방문-맛집-조회)
  - [FR-CREATOR-002](functional-requirements.md#fr-creator-002-방문-유튜버-정보-확인)
  - [FR-VIDEO-001](functional-requirements.md#fr-video-001-관련-영상-정보-확인)
  - [FR-VISIT-001](functional-requirements.md#fr-visit-001-맛집유튜버영상-방문-관계-등록)

### BR-VISIT-003 방문 관계 중복 판단

- 규칙:
  - 동일한 맛집·유튜버·영상 조합은 하나의 방문 관계로만 등록한다.
- 적용 대상:
  - 방문 관계 등록
  - 중복 검증
- 허용:
  - 같은 맛집과 유튜버라도 근거 영상이 다르면 별도 방문 관계로 등록하는 경우
- 금지:
  - 동일한 세 대상의 조합을 중복 등록하는 경우
- 예외:
  - 동일 여부를 판단할 수 없는 경우에는 등록을 보류한다.
- 위반 시 처리:
  - 새 등록을 거부하고 기존 관계를 사용한다.
- 관련 요구사항:
  - [FR-VISIT-001](functional-requirements.md#fr-visit-001-맛집유튜버영상-방문-관계-등록)

### BR-VISIT-004 방문 관계의 연결 범위

- 규칙:
  - 하나의 맛집은 여러 유튜버와, 하나의 유튜버는 여러 맛집과, 하나의 영상은 여러 맛집과 각각 방문 관계를 맺을 수 있다.
- 적용 대상:
  - 방문 관계 등록
  - 유튜버별 맛집 조회
  - 방문 유튜버 및 관련 영상 조회
- 허용:
  - 각 맛집의 실제 방문이 근거 영상에서 확인되는 관계를 개별 등록하는 경우
- 금지:
  - 하나의 유효한 관계가 있다는 이유로 검증하지 않은 다른 관계를 생성하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 개별 방문 사실이 확인되지 않은 관계 등록을 거부한다.
- 관련 요구사항:
  - [FR-CREATOR-001](functional-requirements.md#fr-creator-001-유튜버-기준-방문-맛집-조회)
  - [FR-CREATOR-002](functional-requirements.md#fr-creator-002-방문-유튜버-정보-확인)
  - [FR-VIDEO-001](functional-requirements.md#fr-video-001-관련-영상-정보-확인)
  - [FR-VISIT-001](functional-requirements.md#fr-visit-001-맛집유튜버영상-방문-관계-등록)

### BR-VISIT-005 방문 관계의 조회 유효성

- 규칙:
  - 일반 사용자 조회에는 방문 관계와 그 맛집, 유튜버, 영상이 모두 공개 상태인 관계만 사용한다.
- 적용 대상:
  - 유튜버 필터
  - 방문 유튜버 조회
  - 관련 영상 조회
- 허용:
  - 연결된 모든 대상과 관계가 공개 상태인 경우
- 금지:
  - 관계 또는 연결 대상 중 하나라도 비공개 또는 삭제 상태인 관계를 조회에 사용하는 경우
- 예외:
  - 관계가 유효하지 않아도 공개 맛집의 기본 정보는 조회할 수 있다.
- 위반 시 처리:
  - 해당 관계를 일반 사용자 조회에서 제외한다.
- 관련 요구사항:
  - [FR-CREATOR-001](functional-requirements.md#fr-creator-001-유튜버-기준-방문-맛집-조회)

### BR-VISIT-006 방문 날짜 관리 제외

- 규칙:
  - MVP에서는 실제 방문 날짜를 별도로 관리하지 않으며 영상 게시일을 방문 날짜로 사용하지 않는다.
- 적용 대상:
  - 방문 관계 등록
  - 방문 정보 표시
- 허용:
  - 방문 날짜 없이 실제 방문 사실과 근거 영상만으로 관계를 등록하는 경우
- 금지:
  - 영상 게시일을 실제 방문 날짜로 저장하거나 표시하는 경우
- 예외:
  - 방문 날짜 기능은 범위 변경 후 검증 가능한 출처가 있을 때 별도 도입할 수 있다.
- 위반 시 처리:
  - 근거 없는 방문 날짜를 등록하거나 표시하지 않는다.
- 관련 요구사항:
  - [FR-VISIT-001](functional-requirements.md#fr-visit-001-맛집유튜버영상-방문-관계-등록)

### BR-VISIT-007 등록 완료와 검증 상태

- 규칙:
  - MVP에서는 방문 관계에 별도 검증 상태를 두지 않으며, 관리자가 실제 방문 근거를 확인하고 등록을 완료한 관계만 검증된 관계로 취급한다.
- 적용 대상:
  - 방문 관계 등록
  - 방문 관계 조회
- 허용:
  - 관리자 검증을 마친 관계를 등록하고 조회에 사용하는 경우
- 금지:
  - 검증되지 않은 관계를 임시 상태로 등록하거나 일반 사용자 조회에 사용하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 검증되지 않은 관계 등록을 거부한다.
- 관련 요구사항:
  - [FR-VISIT-001](functional-requirements.md#fr-visit-001-맛집유튜버영상-방문-관계-등록)

## 7. 검색 및 필터 규칙

### BR-SEARCH-001 검색 대상과 일치 기준

- 규칙:
  - 검색은 등록된 맛집 이름만을 대상으로 하며, 검색어가 이름의 일부와 일치하면 결과에 포함하고 영문 대소문자는 구분하지 않는다.
- 적용 대상:
  - 맛집 이름 검색
- 허용:
  - 맛집 이름의 부분 일치 검색
- 금지:
  - 메뉴명, 지역명, YouTube 채널명, 영상 제목, 초성, 유사어, 별칭 또는 오타 보정을 검색 대상으로 사용하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 허용되지 않은 대상을 검색 범위에 포함하지 않는다.
- 관련 요구사항:
  - [FR-RESTAURANT-002](functional-requirements.md#fr-restaurant-002-맛집-이름-검색)

### BR-SEARCH-002 검색어 공백 처리

- 규칙:
  - 맛집 이름 검색 전 검색어의 앞뒤 공백을 제거한다.
- 적용 대상:
  - 맛집 이름 검색
- 허용:
  - 앞뒤 공백을 제거한 검색어로 검색하는 경우
- 금지:
  - 앞뒤 공백 차이만으로 다른 검색 결과를 제공하는 경우
- 예외:
  - 앞뒤 공백 제거 후 검색어가 비어 있으면 맛집 이름 조건을 적용하지 않는다.
- 위반 시 처리:
  - 앞뒤 공백을 제거한 값을 다시 평가하고, 빈 값이면 다른 지정 조건만 적용하거나 전체 목록을 조회한다.
- 관련 요구사항:
  - [FR-RESTAURANT-002](functional-requirements.md#fr-restaurant-002-맛집-이름-검색)

### BR-SEARCH-003 필터 종류와 단일 선택

- 규칙:
  - 지역, 유튜버와 대표 음식 카테고리는 필터 조건이며, 각 종류에서는 한 번에 1개 값만 선택할 수 있다.

  - 지역·유튜버·음식 카테고리 필터
- 허용:
  - 서로 다른 종류의 필터를 각각 1개씩 지정하는 경우
- 금지:
  - 같은 종류의 필터에서 여러 값을 동시에 지정하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 유효하지 않은 필터 조건으로 처리한다.
- 관련 요구사항:
  - [FR-RESTAURANT-003](functional-requirements.md#fr-restaurant-003-지역별-필터)

### BR-SEARCH-004 검색과 필터 조합

- 규칙:
  - 맛집 이름 검색과 서로 다른 종류의 필터를 함께 사용하면 지정된 모든 조건을 만족하는 맛집만 조회한다.
- 적용 대상:
  - 맛집 목록·검색·필터
- 허용:
  - 검색, 지역, 유튜버와 음식 카테고리 조건을 함께 적용하는 경우
- 금지:
  - 일부 조건만 만족한 맛집을 결과에 포함하는 경우
- 예외:
  - 지정하지 않은 조건은 적용하지 않는다.
- 위반 시 처리:
  - 모든 지정 조건을 다시 적용한 결과를 제공한다.
- 관련 요구사항:
  - [FR-RESTAURANT-005](functional-requirements.md#fr-restaurant-005-검색-및-필터-조건-조합)

### BR-SEARCH-005 조회 결과의 고유성

- 규칙:
  - 하나의 맛집은 동일한 조회 결과에 한 번만 표시한다.
- 적용 대상:
  - 맛집 목록·검색·필터
- 허용:
  - 여러 방문 관계가 같은 맛집에 연결되어도 맛집을 한 번 표시하는 경우
- 금지:
  - 관계 수에 따라 같은 맛집을 중복 표시하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 맛집 기준으로 중복을 제거한다.
- 관련 요구사항:
  - [FR-CREATOR-001](functional-requirements.md#fr-creator-001-유튜버-기준-방문-맛집-조회)

### BR-SEARCH-006 빈 조회 결과

- 규칙:
  - 검색 또는 필터 조건을 만족하는 맛집이 없으면 정상적인 빈 목록을 제공한다.
- 적용 대상:
  - 맛집 목록·검색·필터
- 허용:
  - 결과가 없는 요청에 빈 목록을 제공하는 경우
- 금지:

- 예외:
  - 유효하지 않은 요청 조건은 빈 결과가 아니라 잘못된 요청으로 구분한다.
- 위반 시 처리:
  - 유효한 조건의 무결과 요청을 빈 목록으로 처리한다.

- 규칙:

- 적용 대상:
  - 모든 관리자 등록 기능
- 허용:
  - 사전에 발급된 관리자 계정으로 인증하고 권한을 확인한 경우
- 금지:
  - 일반 사용자 또는 인증되지 않은 사용자가 등록 기능에 접근하는 경우
- 예외:
  - 일반 사용자 조회에는 관리자 인증을 요구하지 않는다.
- 위반 시 처리:
  - 관리자 등록 기능 접근을 거부한다.
- 관련 요구사항:
  - [FR-ADMIN-001](functional-requirements.md#fr-admin-001-관리자-등록-기능-접근)

### BR-ADMIN-002 등록 전 사실 검증

- 규칙:
  - 관리자는 등록 전에 정보의 출처와 사실 여부를 확인하고, 방문 관계는 영상에서 실제 방문 사실까지 확인해야 한다.
- 적용 대상:
  - 맛집·유튜버·영상·방문 관계 등록
- 허용:
  - 출처와 사실 관계를 관리자가 직접 검증한 경우
- 금지:
  - YouTube API 조회 결과를 관리자가 확인하지 않은 채 자동 등록하거나 AI 판정 또는 확인되지 않은 추정만으로 등록하는 경우
- 예외:
  - 없음
- 위반 시 처리:
  - 등록을 거부한다.
- 관련 요구사항:

- 예외:

- 위반 시 처리:
  - 등록을 거부하거나 판단 완료 시까지 보류한다.

- 규칙:

- 적용 대상:
  - 관리자 등록
  - 일반 사용자 조회 반영

  - 검증 완료 후 등록하고 공개 조건을 충족한 결과를 조회에 반영하는 경우
- 금지:
  - 검증 전 데이터를 일반 사용자에게 노출하는 경우
- 예외:
  - 비공개 또는 삭제 상태인 데이터와 관계는 반영하지 않는다.
- 위반 시 처리:
  - 공개 조건을 충족하지 않은 데이터를 일반 사용자 조회에서 제외한다.

  - 오류 데이터를 비공개한 뒤 재검증하고 정정하는 경우

## 10. 1차 확장 규칙

<a id="br-member-001-이메일-고유성"></a><a id="br-member-001-이메일-정규화와-고유성"></a>

### BR-MEMBER-001 이메일 정규화와 고유성

- 이메일은 공백 제거와 소문자 정규화를 마친 값으로 비교·저장하며, 탈퇴 정리가 완료되지 않은 계정을 포함해 중복 가입을 허용하지 않는다.
- 가입·인증 재발송·비밀번호 재설정의 외부 응답은 이 규칙의 판정 결과로 계정 존재나 상태를 누설하지 않는다.

<a id="br-member-002-비밀번호-정책"></a>

### BR-MEMBER-002 비밀번호 정책

- 비밀번호는 12자 이상 64자 이하이고 정규화 이메일과 같을 수 없으며, 문자 종류 조합은 강제하지 않는다.
- 비밀번호 원문은 저장·로그·응답에 남기지 않고 정책을 통과한 값의 해시만 보관한다.

<a id="br-member-003-계정-상태"></a>

### BR-MEMBER-003 계정 상태와 전이

- 계정 상태는 `PENDING_VERIFICATION`, `ACTIVE`, `DELETION_PENDING`, `DISABLED`만 사용한다.
- 이메일 인증은 최신의 유효한 1회용 Token으로만 `PENDING_VERIFICATION`을 `ACTIVE`로 바꾸며, 로그인은 `ACTIVE` 상태에서만 허용한다.
- 가입 이메일 인증 Token은 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` 문자 집합에서 CSPRNG로 생성한 8자 코드로 고정한다. 입력은 앞뒤 공백 제거와 영문 대문자 변환 뒤 검증하며 비밀번호 재설정 Token에는 이 형식을 적용하지 않는다.

<a id="br-member-004-회원-탈퇴와-재가입"></a>

### BR-MEMBER-004 회원 탈퇴와 재가입

- 탈퇴 요청은 먼저 `DELETION_PENDING`으로 전이해 즉시 인증을 차단하고, 세션·인증 Token·찜·최근 기록을 정리한 뒤 개인정보를 물리 삭제한다.
- 정리 실패 중에는 로그인과 재가입을 막으며, 정리가 끝난 같은 이메일만 재가입할 수 있다.

<a id="br-auth-001-관리자와-회원-인증-분리"></a><a id="br-auth-001-인증-유효-시간"></a>

### BR-AUTH-001 인증 유효 시간과 관리자 경계

- 회원 Access Token은 30분, Refresh Token은 14일을 기본 유효 시간으로 하며, 관리자와 회원은 JWT audience·principal·cookie·Redis namespace를 공유하지 않는다.
- 회원 Token을 관리자 경로에, 관리자 Token을 회원 개인화 경로에 사용하면 인증에 실패해야 한다.

<a id="br-auth-002-회원-access-refresh-token"></a>

### BR-AUTH-002 회원 Access·Refresh Token 전달과 보관

- Access Token은 API 인증에만 사용하고 Refresh Token은 회원 전용 HttpOnly·Secure 쿠키로 전달한다.
- Refresh Token 원문은 저장·로그·응답에 남기지 않고 해시와 세션 식별자만 서버 저장소에 보관한다.

<a id="br-auth-003-refresh-token-회전과-재사용"></a>

### BR-AUTH-003 Refresh Token 회전과 재사용 탐지

- 재발급에 성공하면 사용한 Refresh Token을 원자적으로 폐기하고 같은 세션 계열의 새 Token만 유효하게 만든다.
- 만료·폐기·재사용 Token 또는 Redis 장애는 fail-closed로 처리하며, 재사용 탐지 시 해당 Token 계열을 폐기한다.

<a id="br-auth-004-다중-세션-한도"></a>

### BR-AUTH-004 다중 세션 한도

- 회원별 활성 세션은 최대 3개이며, 네 번째 세션을 만들면 생성 시각이 가장 오래된 세션을 폐기한다.
- 폐기된 세션의 `sid`는 Access Token 만료까지 거부한다.

<a id="br-auth-005-로그인-실패-제한"></a>

### BR-AUTH-005 로그인 실패 제한

- 로그인 실패는 15분 동안 계정·요청 출처 조합 5회, 계정 전체 10회, 요청 출처 전체 50회로 제한한다.
- 어느 한도든 넘으면 남은 제한 시간 동안 로그인을 차단하되, 외부 응답으로 계정 존재·상태를 구분하지 않는다.

<a id="br-auth-006-로그아웃과-폐기"></a>

### BR-AUTH-006 로그아웃·재설정·탈퇴의 세션 폐기

- 로그아웃은 현재 Refresh 세션의 서버 폐기가 확인된 경우에만 완료로 표시한다.
- 비밀번호 재설정과 탈퇴는 해당 회원의 모든 활성 세션과 남은 Action Token을 폐기한다.

<a id="br-auth-007-공개-상세의-선택적-회원-인증"></a>

### BR-AUTH-007 공개 상세의 선택적 회원 인증과 장애 격리

- 공개 맛집 상세는 유효한 회원 Token이 있을 때만 현재 회원으로 식별해 최근 기록을 갱신한다.
- Token이 없거나 만료·변조·폐기됐거나 회원 audience가 아니면 익명 공개 조회로 `200`을 유지하고 최근 기록을 만들지 않는다.

<a id="br-auth-008-인증-장애-격리"></a><a id="br-auth-008-회원가입비밀번호-재설정-요청-제한"></a>

### BR-AUTH-008 회원 인증 요청 제한과 장애 격리

- 가입과 인증 메일 재발송은 정규화 이메일당 최소 60초 간격·하루 최대 5회이며, 비밀번호 재설정 요청과 합쳐 요청 출처당 시간당 최대 20회다.
- 이메일 인증 코드 제출은 신뢰된 요청 출처당 10분에 최대 10회로 제한하고 초과 요청은 계정·코드 존재 여부를 구분하지 않는 `429`로 거부한다.
- 최신 인증 요청만 유효하고 인증 Token은 24시간, 비밀번호 재설정 Token은 30분 동안 한 번만 사용할 수 있다.
- 회원 인증 상태·폐기 표식 또는 개인화 저장소에 장애가 나면 공개 맛집 상세는 익명 `200`과 최근 기록 생략으로 처리하며, 이 내부 실패를 공개 응답으로 전파하지 않는다.

<a id="br-favorite-001-회원별-찜의-고유성과-멱등성"></a>

### BR-FAVORITE-001 회원별 찜의 고유성과 멱등성

- `(member, restaurant)` 찜 관계는 하나만 존재한다.
- 공개 맛집의 중복 추가는 같은 성공 상태를 반환하고, 본인만 자신의 찜을 만들 수 있다.

<a id="br-favorite-002-찜-상태-조회와-본인-경계"></a>

### BR-FAVORITE-002 찜 상태 조회와 본인 경계

- 찜 상태 조회는 인증된 현재 회원과 공개 맛집 하나의 관계만 반환한다.
- 다른 회원 식별자를 입력하거나 타인의 관계를 조회·변경하는 기능은 제공하지 않는다.

<a id="br-favorite-003-찜-목록-정렬과-공개-상태"></a>

### BR-FAVORITE-003 찜 목록 정렬과 공개 상태

- 찜 목록은 `favoritedAt` 내림차순과 맛집 식별자 보조 정렬로 안정적으로 표시하며 공개 맛집 관계만 포함한다.
- 목록 GET은 찜을 삭제하거나 상태를 변경하지 않는다.

<a id="br-favorite-004-맛집-상태에-따른-찜-보존과-정리"></a>

### BR-FAVORITE-004 맛집 상태에 따른 찜 보존과 정리

- 비공개 맛집의 찜은 관계를 보존하되 회원 목록과 상태 조회에서 숨긴다.
- 회원 탈퇴와 맛집 물리 삭제의 Command/FK 정책은 찜 관계를 정리하며, 공개 조회는 그 정리를 수행하지 않는다.

<a id="br-recent-001-최근-본-맛집의-기록과-갱신"></a>

### BR-RECENT-001 최근 본 맛집의 기록과 갱신

- 유효 회원이 공개 맛집 상세를 성공적으로 조회하면 같은 `(member, restaurant)` 기록을 upsert하고 `viewedAt`을 최신 시각으로 갱신한다.
- 기록은 공개 상세 응답이 성공한 뒤에만 만들며, 동일 맛집의 중복 행은 허용하지 않는다.

<a id="br-recent-002-최근-기록의-보존-상한과-정리"></a>

### BR-RECENT-002 최근 기록의 보존 상한과 정리

- 최근 기록 upsert Command는 회원별 최신 50개만 유지하도록 초과분을 정리한다.
- 30일이 지난 기록은 별도의 주기 cleanup Command로 삭제하며, 상세 조회·목록 GET·upsert Command가 30일 보존 정리를 수행하지 않는다.

<a id="br-recent-003-최근-기록-목록-공개-상태와-정렬"></a>

### BR-RECENT-003 최근 기록 목록의 공개 상태와 정렬

- 목록은 보존 기간 안의 공개 맛집 기록만 `viewedAt` 내림차순과 맛집 식별자 보조 정렬로 반환한다.
- 목록 GET은 보존 기간 경과·비공개 관계를 필터링할 뿐 삭제하지 않는다.

<a id="br-recent-004-최근-기록-생성-실패-격리"></a>

### BR-RECENT-004 최근 기록 생성 실패 격리

- 최근 기록 저장 또는 개인화 저장소 실패는 공개 맛집 상세의 성공 응답을 실패시키지 않는다.
- 이 경우 기록만 생략하며, 공개 응답에는 인증·저장소 내부 상태를 노출하지 않는다.

<a id="br-recent-005-최근-기록-개별-삭제의-멱등성과-소유권"></a>

### BR-RECENT-005 최근 기록 개별 삭제의 멱등성과 소유권

- 개별 삭제는 인증된 현재 회원의 해당 맛집 기록만 대상으로 하며, 없는 기록을 반복 삭제해도 같은 성공 상태를 반환한다.
- 타 회원의 기록은 식별하거나 삭제할 수 없다.

<a id="br-map-001-wgs84-좌표와-null-처리"></a><a id="br-map-001-지도-표시-대상과-좌표"></a>

### BR-MAP-001 지도 표시 대상과 좌표

- WGS84 위도·경도가 모두 유효한 공개 맛집만 지도 표시 대상이다.
- 좌표가 없거나 둘 중 하나만 있는 맛집은 지도에서만 제외하고 기존 목록·상세에는 유지한다.

<a id="br-map-002-bounds-검색과-기존-필터-결합"></a><a id="br-map-002-지도-영역과-필터-조합"></a>

### BR-MAP-002 지도 필터 조합과 뷰포트 독립

- 지도 마커 조회에는 이름·자치구·음식 카테고리·유튜버 조건만 AND로 조합한다.
- 현재 지도 뷰포트의 `south`·`west`·`north`·`east`는 서버 요청·Query Key·URL·로그에 포함하지 않는다.
- 지도 이동·확대·축소만으로 결과를 재조회하거나 기존 마커·대체 목록을 제거하지 않는다.
- 조합 결과는 맛집 단위로 중복을 제거하며 지도와 대체 목록에 같은 결과를 사용한다.

<a id="br-map-003-지도-결과-상한과-호출-제한"></a><a id="br-map-003-지도-마커-수-제한"></a>

### BR-MAP-003 지도 마커 수 제한

- 지도 탐색 조건 결과는 최대 200개까지만 표시한다.
- 200개를 초과하면 임의의 일부를 표시하지 않고 탐색 조건 추가를 안내한다.

<a id="br-map-004-지도-sdk와-키-경계"></a><a id="br-map-004-지도-조회-호출-제한"></a>

### BR-MAP-004 지도 조회 호출 경계

- 최초 화면 진입과 URL 탐색 조건 변경 때만 조회하고, 클라이언트당 초당 최대 4회로 제한한다.
- 브라우저용 지도 키와 서버 비밀 키를 분리하며 지도 뷰포트는 서버로 전송하거나 로그에 남기지 않는다.

<a id="br-map-005-지도-접근성과-장애-격리"></a><a id="br-map-005-마커-요약과-사용자-위치-비수집"></a>

### BR-MAP-005 마커 요약과 사용자 위치 비수집

- 마커와 대체 목록은 같은 맛집의 이름·대표 음식 카테고리·주소 요약과 상세 이동을 제공한다.
- 현재 위치를 요청·수집·저장하지 않으며 SDK 실패는 지도 밖 공개 탐색을 막지 않는다.

기존 `BR-CREATOR-001`~`007`은 제3장의 유튜버 등록·방문 관계 규칙을 그대로 적용한다. 유튜버 상세에 추가되는 규칙은 다음과 같다.

<a id="br-creator-008-비공개-creator"></a><a id="br-creator-008-유튜버-상세-공개와-찾을-수-없음-처리"></a>

### BR-CREATOR-008 유튜버 상세 공개와 찾을 수 없음 처리

<a id="br-creator-009-삭제-creator"></a><a id="br-creator-009-유튜버-상세-표시-정보"></a>

### BR-CREATOR-009 유튜버 상세 표시 정보

- 상세는 저장된 채널 이름·채널 URL·프로필 이미지·설명·handle만 표시하며 선택 값이 없으면 `null`로 표시한다.
- 조회 중 외부 API로 현재 값을 보강하지 않는다.

<a id="br-creator-010-외부-상태"></a><a id="br-creator-010-유튜버-방문-맛집의-고유성과-정렬"></a>

### BR-CREATOR-010 유튜버 방문 맛집의 고유성과 정렬

<a id="br-creator-011-외부-api-호출-금지"></a><a id="br-creator-011-유튜버-근거-영상의-고유성과-정렬"></a>

### BR-CREATOR-011 유튜버 근거 영상의 고유성과 정렬

- 공개·유효 Visit에 연결된 근거 영상만 한 번씩 표시하고, 등록 시각 내림차순과 영상 식별자 보조 정렬을 사용한다.
- 사용자 조회 중 YouTube API를 호출하지 않는다.

<a id="br-creator-012-캐시-도입-보류"></a><a id="br-creator-012-유튜버-상세-연결-목록의-페이지"></a>

### BR-CREATOR-012 유튜버 상세 연결 목록의 페이지

- 방문 맛집과 근거 영상은 각각 독립적인 1-base 페이지를 사용하며 기본 20개, 허용 크기 10·20·50을 적용한다.
- 빈 목록은 정상 `200`과 빈 `items`로 반환하며, 캐시는 병목 근거 전까지 도입하지 않는다.

## 11. 2차 확장 규칙

### 11.1 개인 컬렉션 규칙

<a id="br-collection-001-소유권과-비공개-경계"></a>

### BR-COLLECTION-001 소유권과 비공개 경계

- 개인 컬렉션은 생성 회원 한 명이 소유하며 소유자 본인만 조회·변경·삭제한다.
- 다른 회원에게 컬렉션 식별자·이름·포함 맛집·존재 여부를 노출하지 않고 공개·링크 공유·공동 편집을 제공하지 않는다.

<a id="br-collection-002-맛집-관계의-고유성과-상한"></a>

### BR-COLLECTION-002 맛집 관계의 고유성과 상한

- 같은 컬렉션의 같은 맛집 관계는 하나만 존재하며 중복 추가는 새 관계를 만들지 않는다.
- 한 맛집은 같은 회원 또는 다른 회원의 여러 컬렉션에 포함할 수 있다.
- 회원당 컬렉션은 최대 20개, 컬렉션당 맛집은 최대 100개이며 동시 요청도 상한을 초과해 저장하지 않는다.

<a id="br-collection-003-정렬과-직접-순서-변경-제외"></a>

### BR-COLLECTION-003 정렬과 직접 순서 변경 제외

- 컬렉션 목록은 최근 수정 시각 내림차순과 컬렉션 식별자 보조 정렬을 사용한다.
- 포함 맛집은 추가 시각 내림차순과 맛집 식별자 보조 정렬을 사용한다.
- 사용자가 임의 순서를 저장하거나 재정렬하는 기능과 순서 열은 초기 범위에 두지 않는다.

<a id="br-collection-004-맛집-공개-상태"></a>

### BR-COLLECTION-004 맛집 공개 상태

- 공개·활성 맛집만 새로 추가할 수 있다.
- 포함 뒤 비공개로 전환된 맛집 관계는 보존하되 목록에서 숨기며, 삭제된 맛집 관계는 맛집 삭제 정책에 따라 정리한다.
- 컬렉션 조회는 숨김 관계를 삭제하거나 맛집 상태를 변경하지 않는다.

<a id="br-collection-005-삭제와-회원-탈퇴"></a>

### BR-COLLECTION-005 삭제와 회원 탈퇴

- 컬렉션 삭제는 컬렉션과 그 포함 관계만 삭제하며 맛집·찜·다른 컬렉션을 변경하지 않는다.
- 회원 탈퇴 정리는 해당 회원의 모든 컬렉션과 포함 관계를 삭제한다.

### 11.2 인기 맛집 규칙

<a id="br-popular-001-인기-신호와-집계-기간"></a>

### BR-POPULAR-001 인기 신호와 집계 기간

- 인기 신호는 전체 기간에 현재 유지 중인 찜 관계 수 하나다.
- 최근 본 맛집, 상세 조회, 비로그인 조회, 기간별 행동량과 추천 점수를 인기 신호에 포함하지 않는다.
- `인기 맛집`은 현재 많이 찜한 맛집을 뜻하며 최근 인기·급상승·조회수 인기라고 표현하지 않는다.

<a id="br-popular-002-포함-대상과-안정-정렬"></a>

### BR-POPULAR-002 포함 대상과 안정 정렬

- 현재 찜이 1건 이상인 공개·활성 맛집만 포함한다.
- 찜 수 내림차순, 맛집 식별자 오름차순으로 정렬한 상위 20개만 제공하고 페이지를 두지 않는다.
- 공개 결과에는 집계 찜 수만 제공하며 회원 식별자와 개별 회원의 찜 여부를 노출하지 않는다.

<a id="br-popular-003-실시간-집계와-반영"></a>

### BR-POPULAR-003 실시간 집계와 반영

- 각 요청은 현재 찜 관계와 맛집 공개 상태를 기준으로 집계한다.
- 찜·찜 해제·회원 탈퇴·맛집 공개 상태 변경은 해당 트랜잭션 커밋 뒤 다음 인기 조회에 반영한다.
- 배치·캐시·Snapshot과 재계산 작업은 초기 범위에 두지 않으며 성능 기준 미달이 측정될 때 별도 변경 절차로 재검토한다.

### 11.3 관리자 큐레이션 규칙

<a id="br-curation-001-소유권과-게시-상태"></a>

### BR-CURATION-001 소유권과 게시 상태

- 관리자만 큐레이션을 생성·수정·게시·게시 중단한다.
- 새 큐레이션은 `DRAFT`이며 게시하면 `PUBLISHED`, 게시 중단하면 다시 `DRAFT`가 된다.
- 공개 사용자는 `PUBLISHED` 큐레이션만 조회하고 관리자 식별 정보를 보지 않는다.

<a id="br-curation-002-구성과-정렬-상한"></a>

### BR-CURATION-002 구성과 정렬 상한

- 메인에 `PUBLISHED` 큐레이션을 최대 5개까지 두고 큐레이션 하나에는 맛집을 최대 20개까지 둔다.
- 같은 큐레이션의 같은 맛집은 한 번만 포함하며 관리자가 큐레이션과 포함 맛집의 표시 순서를 직접 지정한다.
- 저장된 표시 순서는 중복되지 않고 안정적으로 재현돼야 한다.

<a id="br-curation-003-맛집-공개-상태와-경고"></a>

### BR-CURATION-003 맛집 공개 상태와 경고

- 공개·활성 맛집만 큐레이션에 새로 포함한다.
- 포함 맛집이 비공개·삭제되면 공개 큐레이션 결과에서 자동 제외하고 관리자에게 구성 불일치 경고를 제공한다.
- 공개 조회는 큐레이션 구성을 자동 수정하거나 숨김 관계를 삭제하지 않는다.

<a id="br-curation-004-게시-중-수정-반영"></a>

### BR-CURATION-004 게시 중 수정 반영

- `PUBLISHED` 큐레이션의 저장 성공 결과는 별도 예약·버전 발행 없이 다음 공개 조회부터 즉시 반영한다.
- 수정이 실패하면 기존 공개 구성을 유지하고 부분 변경을 노출하지 않는다.

### 11.4 사용자 제보 규칙

<a id="br-submission-001-대상과-근거"></a>

### BR-SUBMISSION-001 대상과 근거

- 제보 대상은 신규 맛집·유튜버·영상과 신규 방문 관계다.
- 회원은 대상 식별에 필요한 설명과 근거 URL을 제공하며 첨부 파일과 공개 데이터 직접 등록·수정은 허용하지 않는다.

<a id="br-submission-002-중복과-요청-제한"></a>

### BR-SUBMISSION-002 중복과 요청 제한

- 같은 회원·대상·요청 유형의 `RECEIVED`·`IN_REVIEW`·`ACCEPTED` 제보는 하나만 유지하고 새 중복 요청에는 기존 요청을 안내한다.
- 회원별 제보·신고 신규 접수 합계는 한국 시간(`Asia/Seoul`) 달력 날짜마다 5건이며 두 기능이 같은 한도를 공유한다.

<a id="br-submission-003-상태-전이와-실제-등록"></a>

### BR-SUBMISSION-003 상태 전이와 실제 등록

- 정상 상태 흐름은 `RECEIVED → IN_REVIEW → ACCEPTED → COMPLETED`이며 반려는 `IN_REVIEW → REJECTED`다.
- `ACCEPTED`는 제보가 타당하다는 결정이며 공개 데이터 등록 완료를 뜻하지 않는다.
- 승인된 제보는 기존 관리자 검증·중복 판정·등록 흐름을 통과하고 실제 반영된 뒤에만 `COMPLETED`가 된다.
- `REJECTED`는 종료 상태이며 `COMPLETED`로 전환하지 않는다.

<a id="br-submission-004-소유권과-보존"></a>

### BR-SUBMISSION-004 소유권과 보존

- 회원은 본인 제보와 회원 공개 사유만 조회하며 다른 회원 정보와 관리자 전용 검토 기록은 보지 않는다.
- 종료된 제보는 1년간 처리 근거를 보관한 뒤 회원 식별 정보를 삭제한다.

## 12. 3차 확장 규칙

### 12.1 자연어 검색 규칙

<a id="br-nlsearch-001-직접-지정-필터-우선"></a>

### BR-NLSEARCH-001 직접 지정 필터 우선

- 자연어에서 해석한 조건과 사용자가 직접 지정한 구조화 필터가 같은 조건 종류에서 충돌하면 직접 지정 필터를 적용한다.
- 자연어 조건은 직접 필터가 없는 조건 종류에만 보충 적용하고, 서로 다른 조건 종류는 AND로 조합한다.
- 적용 조건 요약에는 자연어에서 해석한 값, 실제 적용한 값과 직접 필터 때문에 제외된 값을 구분한다.

<a id="br-nlsearch-002-검색-결과의-공개와-생명주기"></a>

### BR-NLSEARCH-002 검색 결과의 공개와 생명주기

- 자연어 검색은 기존 목록과 같은 공개·활성 맛집만 반환한다.
- 비공개·삭제 맛집과 공개·유효하지 않은 Creator·Video·Visit 관계는 자연어 해석이나 직접 필터가 일치해도 결과 근거로 사용하지 않는다.
- 유효한 조건의 결과가 0건인 상태와 조건을 해석하지 못한 상태를 서로 다른 결과로 처리한다.

<a id="br-nlsearch-003-태그-검색과-공개-visit-기준"></a>

### BR-NLSEARCH-003 태그 검색과 공개 Visit 기준

- 검색에 사용하는 태그는 활성 상태인 `TagDefinition`과 공개·유효한 `Visit`에 연결된 `VisitTag`만 허용한다.
- 여러 태그 조건은 같은 유효한 `Visit`에 모두 연결되어 있을 때만 만족하며, 결과 맛집은 중복 없이 반환한다.
- 자동 검증 전 AI 후보, 폐기 태그, 비공개·삭제·무효 `Visit`에 연결된 태그는 검색 조건과 결과에서 제외한다.

### 12.2 AI 영상 정보 추출 규칙

<a id="br-aiextract-001-ai-후보-생성-범위"></a>

### BR-AIEXTRACT-001 AI 후보 생성 범위

- AI는 맛집명, 메뉴·음식 표현, 주소·위치 표현, 실제 방문 여부와 그 근거 구간만 검수 후보로 생성할 수 있다.
- Creator와 Video의 외부 식별자·메타데이터, 영업시간·폐업·예약·가격과 공개 사실은 AI 결과만으로 확정하지 않는다.
- 근거 구간이 없거나 하나의 장소로 판정할 수 없으면 추정값을 확정하지 않고 `UNKNOWN` 또는 복수 후보로 남긴다.
- 한 영상에 여러 장소가 등장하는 것은 정상이다. 같은 필드에 후보가 여럿이라는 사실 자체는 확정을 막지 않으며, 시스템은 후보를 장소 단위 등록 단위로 묶어 각각 독립적으로 판정한다.
- 등록 단위는 맛집명 후보 하나와 그 후보에 결속된 주소·메뉴·방문 근거로 구성한다. 판정과 자동 등록은 등록 단위별로 수행하며, 한 단위의 차단이 같은 작업의 다른 단위를 차단하지 않는다.
- 후보 수에는 상한이 있다. 영상이 상한보다 많은 장소를 다루면 근거가 강한 후보만 남기고 나머지는 생략한다. 생략이 일어난 결과는 **그 사실을 반드시 표시해야 하며**, 관리자 화면은 일부 맛집이 누락됐음을 경고한다. 표시 없이 조용히 생략하지 않는다.
- 절삭 표시는 모델 응답의 값만 믿지 않는다. 후보 수가 상한과 같으면 표시가 없어도 절삭 가능으로 취급한다.
- 상한을 지키지 않은 응답은 종전대로 `SCHEMA` 실패로 기각하고 등록 단위를 만들지 않으며, 관리자는 보완 텍스트 재시도 또는 기존 수동 등록으로 복구한다.

<a id="br-aiextract-008-태그-후보-통제와-공개"></a>

### BR-AIEXTRACT-008 태그 후보 자동 등록과 공개

- AI는 자막에서 새로운 태그 후보를 생성할 수 있지만, 시스템은 정규화·동의어·문자 유사도·금지 표현·근거 검사를 통과한 후보만 자동 `TagDefinition`으로 등록한다.
- 태그 후보는 가능한 경우 timestamp 또는 안전한 text range 근거를 가져야 하며, 근거 없는 추정 태그는 `UNKNOWN` 또는 미확정 상태로 남긴다.
- 정상 경로에서는 관리자 태그 승인 없이 자동 판단을 사용한다. 관리자는 사후 보정·통합·폐기 이력을 남길 수 있다.
- 자동 태그 판단과 관리자 사후 보정은 append-only 감사 이력으로 저장하며, 재처리·보정은 기존 판단을 수정·삭제하지 않고 새 이력을 추가한다.
- `UNKNOWN` 근거의 AI 태그는 자동 등록하지 않고, `TIMESTAMP` 또는 `TEXT_RANGE` 근거가 있는 AI 태그만 `AI_AUTO_CONFIRMED` `VisitTag`로 연결한다.
- 하나의 `Visit`에는 여러 태그를 연결할 수 있지만 같은 태그의 중복 연결은 허용하지 않는다.
- 가격·품질·평점·영업시간·방문 가능 여부처럼 영상만으로 일반화하기 쉬운 사실과 근거 없는 홍보 표현은 자동 태그로 등록하지 않는다.

<a id="br-aiextract-002-자동-검증-없는-정식-저장-금지"></a>

### BR-AIEXTRACT-002 자동 검증 없는 정식 저장 금지

- AI 후보는 자동 구조·필수값·중복·Kakao 장소·YouTube 메타데이터·방문 근거 검증을 모두 통과한 경우 관리자 승인 없이 `Restaurant`, `Creator`, `Video`, `Visit`를 생성·수정·공개할 수 있다.
- 태그 후보도 자막 근거·정규화·중복·정책 검사를 통과한 경우 자동으로 `TagDefinition`과 `VisitTag`를 생성·공개할 수 있다.
- 자동 검증·정식 저장의 성패는 `BR-AIEXTRACT-001`의 등록 단위마다 판정한다. 한 등록 단위의 검증·저장 중 하나라도 실패하거나 결과가 모호하면 **그 등록 단위의** 정식 데이터는 0건 저장하고 자동 보류·거부 상태로 남긴다. 같은 작업의 다른 등록 단위가 통과했다면 그 등록은 유지하며 되돌리지 않는다.
- 작업 전체의 정식 데이터가 0건이 되는 경우는 두 가지다. 추출 자체가 실패해 후보 Snapshot이 없거나, Snapshot은 있으나 등록 단위를 하나도 만들지 못한 경우다.
- 관리자는 사후 수정·롤백을 수행할 수 있지만 정상 등록의 사전 승인자는 아니다.

<a id="br-aiextract-003-동일-영상-중복-추출"></a>

### BR-AIEXTRACT-003 동일 영상 중복 추출

- 정규화한 YouTube 영상 식별자, 입력 텍스트 해시, AI 모델 버전, Prompt 버전과 결과 Schema 버전이 모두 같으면 같은 추출 작업으로 식별한다.
- 같은 조합의 동시·반복 요청은 새 작업을 만들지 않고 기존 작업 식별자와 상태를 반환한다.
- 모델·Prompt·Schema 중 하나가 바뀌면 새 버전 작업을 만들 수 있지만 이전 결과를 덮어쓰거나 자동 폐기하지 않는다.

<a id="br-aiextract-004-모델-prompt-schema-버전"></a>

### BR-AIEXTRACT-004 모델·Prompt·결과 Schema 버전

- 모든 추출 작업과 후보에는 제공자, 모델, Prompt와 결과 Schema의 불변 버전을 기록한다.
- 검수 화면과 감사 이력은 후보를 만든 버전을 식별할 수 있어야 하며, 버전 변경 뒤 과거 결과를 조용히 재해석하지 않는다.
- 재처리는 관리자가 명시적으로 요청한 대상에만 수행하고 새 결과를 별도 후보로 보존한다.

<a id="br-aiextract-005-영상-유입-경로와-작업-수렴"></a>

### BR-AIEXTRACT-005 영상 유입 경로와 작업 수렴

- 영상 유입 경로는 `WEBHOOK`과 `ADMIN`으로 구분해 감사하고, 두 경로는 동일한 추출·검수·정식 등록 경계를 사용한다.
- Webhook은 관리자가 활성화한 채널만 대상으로 하며, 수신 자체로 공개 데이터나 관리자 검수 상태를 자동 확정하지 않는다.
- Webhook 반복 전달, 관리자 재입력, 초기 데이터 적립 요청은 정규화한 영상 식별자와 입력·버전 멱등성 키로 수렴한다.
- 초기 데이터 적립은 Webhook 실시간 작업보다 낮은 우선순위로 처리하며, 초기 적립 작업이 신규 영상 작업의 처리와 기존 공개 조회를 점유하지 않도록 한다.

<a id="br-aiextract-006-webhook-감시-채널-상태"></a>

### BR-AIEXTRACT-006 Webhook 감시 채널 상태

- Webhook 감시는 관리자 명시적 활성화가 있는 검증된 Creator 채널에만 적용한다. Creator 등록·수정만으로 자동 구독하지 않는다.
- 같은 YouTube 채널에는 유효한 감시 구독을 하나만 유지하며, 중복 활성화 요청은 기존 구독 상태를 반환한다.
- 감시 중지·구독 만료·갱신 실패는 과거 작업과 후보를 변경하지 않고 신규 자동 접수만 차단한다. 관리자 신규 영상 추가는 계속 허용한다.

<a id="br-aiextract-007-gemini-영상-입력과-fallback"></a>

### BR-AIEXTRACT-007 Gemini 영상 입력과 fallback

- 공개 YouTube URL이 유효하고 제공자 계약·quota 조건을 만족하면 Google Gemini API 영상 입력을 우선 사용한다.
- Gemini가 영상을 접근하지 못하거나 정책 제한·시간 초과·부분 추출로 정식 검수에 필요한 정보가 부족하면 추정값으로 보완하지 않고 실패·부분 상태를 기록한다.
- 관리자가 제공한 보완 텍스트는 명시적 재시도 입력으로만 사용하며, 이전 Gemini 결과를 조용히 덮어쓰지 않고 입력·모델·Prompt·Schema 버전이 다른 새 후보를 만든다.
- 보완 텍스트는 작업 처리와 Worker 재시작 복구를 위해 암호화된 임시 입력으로만 보존하고, 작업 종료 후 24시간 이내 삭제한다. 관리자 재시도는 이전 보완 텍스트를 자동 재사용하지 않는다.
- Gemini 영상 분석 결과의 timestamp·근거가 없으면 방문 여부나 장소 동일성을 확정하지 않는다.

<a id="br-aiextract-009-장소-동일성-자동-확정"></a>

### BR-AIEXTRACT-009 장소 동일성 자동 확정

> `BR-AIEXTRACT-009`·`010`·`011`은 `합의 대기` 상태다. 합의는 [PR #226](https://github.com/team-youngkk/masit-on/pull/226)의 소유자 승인으로 갈음하며, 승인 전에는 구현 계약으로 사용하지 않는다. 승인 후 병합 직전 커밋에서 이 표시를 제거한다. 절차와 불발 시 되돌릴 범위는 [ADR-AI-001 1절](../07-adr/integration/ai-001-video-extraction-candidate-boundary.md)에 있다.

- AI는 Kakao 장소 식별자를 만들 수 없으므로 상호명과 주소·위치 표현만 후보로 생성한다. AI 후보에 Kakao 장소 URL을 요구하지 않는다.
- 시스템은 등록 단위의 상호명과 주소 후보로 Kakao 장소를 검색해 동일성을 판정한다. 판정 주체는 관리자가 아니라 시스템이며 관리자 사전 승인을 요구하지 않는다.
- 자동 확정은 다음을 모두 만족할 때만 수행한다. 하나라도 어긋나면 `AUTO_BLOCKED`로 남기고 정식 저장은 0건이다.
  - 공백 제거·대소문자 통일 정규화 후 검색 결과의 장소명이 상호명 후보와 완전히 일치한다.
  - 검색 결과의 도로명주소가 AI 주소 후보와 시·구 단위까지 일치한다. 지번·도로명 표기 차이 때문에 주소 전체 문자열 완전일치는 요구하지 않는다.
  - 위 두 조건을 함께 만족하는 검색 결과가 정확히 1건이다. 0건이면 `PLACE_NOT_FOUND`, 2건 이상이면 `PLACE_AMBIGUOUS`로 차단한다.
  - 장소 식별자·장소명·도로명주소·좌표 등 정식 등록 필수값이 모두 존재한다.
- 관리자가 Kakao 장소 URL을 직접 제출하는 수동 등록 경로의 검증 기준은 바꾸지 않는다. 두 경로는 같은 장소에 대해 같은 동일성 결과를 만들어야 한다.
- 자동 확정한 장소 판정 근거(검색어, 채택한 장소 식별자, 충족한 일치 조건)는 감사 이력으로 남기고 관리자는 사후 보정·롤백할 수 있다.

<a id="br-aiextract-010-대표-음식-카테고리-자동-선정"></a>

### BR-AIEXTRACT-010 대표 음식 카테고리 자동 선정

- 대표 음식 카테고리는 공통 기준정보 10개 값 중 하나이며, 자동 등록 경로에서는 관리자가 선택하지 않고 시스템이 결정한다.
- 1순위 근거는 `BR-AIEXTRACT-009`로 확정한 Kakao 장소의 분류 표현이다. 분류 표현을 기준정보 매핑 표로 10개 값에 대응시킨다.
- Kakao 분류가 없거나 매핑 표에 대응 값이 없으면 2순위로 AI 메뉴 후보 표현을 같은 매핑 표에 대조한다. 메뉴 표현은 완전일치뿐 아니라 등록된 별칭·부분 표현 일치를 허용한다.
- 두 근거가 모두 실패하면 임의 기본값으로 대체하지 않고 `CATEGORY_UNRESOLVED`로 자동 확정을 차단한다. `기타`는 매핑 표가 명시적으로 `기타`를 지정한 경우에만 사용한다.
- 매핑 표는 코드 상수가 아니라 기준정보로 관리하고 변경 이력을 남긴다. 매핑 표 변경은 이미 등록된 결과를 소급 재계산하지 않는다. 물리 저장 경계는 데이터 계약의 `food_category_mapping`이고 소유자는 restaurant 도메인이다.
- 대조 순서는 근거 유형(Kakao 분류 우선), 일치 방식(완전일치 우선), 매핑 우선순위 순이다. 같은 순위에서 서로 다른 카테고리로 일치하는 행이 둘 이상이면 임의로 고르지 않고 `CATEGORY_UNRESOLVED`로 차단한다.
- 선정한 카테고리와 사용한 근거 순위, 사용한 매핑 행 식별자와 그 시점의 카테고리 값은 감사 이력에 남긴다.
- 관리자는 등록이 완료된 뒤에도 대표 카테고리만 보정할 수 있다. 이때 등록 결과와 공개 상태는 유지하고 이전 카테고리 값을 이력에 남긴다. 롤백이 끝난 등록 단위는 보정 대상이 아니다.

<a id="br-aiextract-011-등록-단위-일괄-등록과-예외-전환"></a>

### BR-AIEXTRACT-011 등록 단위 일괄 등록과 예외 전환

- 관리자가 등록 단위의 등록을 요청하면 시스템은 맛집·유튜버·영상·방문 관계 4종을 하나의 요청으로 등록하고 결과만 알린다. 관리자에게 단계별 진행, 장소 후보 선택, 주소 힌트 선택, Kakao 장소 URL 입력, 카테고리 선택을 요구하지 않는다.
- 이 경로는 Worker 자동 등록과 같은 판정 규칙을 사용한다. `BR-AIEXTRACT-009`의 장소 동일성 조건과 `BR-AIEXTRACT-010`의 카테고리 결정 규칙을 그대로 적용하며, 관리자가 실행 주체라는 이유로 기준을 완화하지 않는다.
- 유튜버와 영상은 작업이 이미 보유한 채널·영상 식별자로 등록한다. 이미 등록된 유튜버·영상은 중복 생성하지 않고 기존 식별자를 재사용하며, 재사용은 예외가 아니라 정상 경로다.
- 4종 등록의 원자 경계는 등록 단위 하나다. 등록 중 하나라도 실패하면 그 등록 단위의 정식 저장은 0건이고, 이미 완료된 다른 등록 단위는 되돌리지 않는다.
- 외부 조회·검증은 DB 트랜잭션 밖에서 수행하고, 검증을 모두 통과한 뒤 4종을 하나의 트랜잭션으로 저장한다.
- 다음 예외에서만 자동 등록을 중단한다. 그 밖의 사유로 자동 등록을 멈추거나 관리자 입력을 요구하지 않는다.
  - `PLACE_NOT_FOUND`·`PLACE_AMBIGUOUS`: 장소 동일성을 자동 확정할 수 없다.
  - `CATEGORY_UNRESOLVED`: 카테고리 근거를 찾지 못했다.
  - `MISSING_REQUIRED_FIELD`: 등록 단위에 상호명·주소 등 필수 후보가 없다.
  - `VISIT_EVIDENCE_REQUIRED`: 방문 근거가 `UNKNOWN`이거나 영상 `TIMESTAMP` 근거가 아니다.
  - `DUPLICATE_CONFLICT`: 같은 맛집·방문 관계가 이미 존재해 새 등록이 필요 없다.
  - `EXTERNAL_SERVICE_ERROR`: Kakao·YouTube 조회가 실패하거나 시간을 초과했다.
- **관리자 보조 입력은 판정 선택만 받고 후보 값 생성은 받지 않는다.** 보조 입력으로 복구할 수 있는 예외는 장소 동일성과 카테고리 두 가지뿐이다. 두 값은 관리자가 외부 기준정보 중 하나를 고르는 것이므로 AI 근거를 대체하지 않는다.
- 맛집명·주소·방문 근거가 부족한 예외는 보조 입력 대상이 아니다. 관리자가 값을 만들어 넣으면 영상 근거 없는 데이터가 등록되기 때문이다. 이 경우 보완 텍스트 재추출 또는 기존 수동 등록으로 처리하며, 방문 근거는 보완 텍스트 주장으로 확정할 수 없고 영상 `TIMESTAMP`를 요구한다.
- 보조 입력 경로에서 관리자가 제출한 값도 기존 외부 검증을 우회하지 않는다. 관리자 입력은 판정을 대체하는 것이 아니라 판정 입력을 보충한다.
- 자동 등록 실행 주체(`WORKER` 또는 `ADMIN`), 판정 근거와 예외 전환 사유는 감사 이력으로 남긴다.

### 12.3 동선 및 코스 규칙

<a id="br-course-001-코스-맛집-수와-출발점"></a>

### BR-COURSE-001 코스 맛집 수와 출발점

- 코스는 서로 다른 맛집 2개 이상 5개 이하로 구성한다.
- 첫 번째 선택 맛집은 출발점으로 고정하고 나머지 맛집만 방문 순서 계산 대상이 되며, 제안된 마지막 맛집을 도착점으로 사용한다.
- 자동 맛집 추가, 별도 출발지·도착지와 현재 위치는 초기 범위에 포함하지 않는다.

<a id="br-course-002-좌표-없는-맛집"></a>

### BR-COURSE-002 좌표 없는 맛집 처리

- 위도·경도 중 하나라도 없거나 유효 범위를 벗어난 맛집은 코스 후보가 될 수 없다.
- 선택 항목 중 좌표 없는 맛집이 하나라도 있으면 해당 맛집만 임의로 제외해 코스를 계산하지 않고 전체 요청을 거부하며 재선택을 안내한다.
- 좌표 누락은 맛집 자체의 공개 목록·상세 상태를 변경하지 않는다.

<a id="br-course-003-경로-결과-만료와-재조회"></a>

### BR-COURSE-003 경로 결과 만료와 재조회

- 경로 결과는 생성 시각과 만료 시각을 가진 요청 시점 Snapshot이며 영구 저장·공유하지 않는다.
- 만료 시간은 생성 시각부터 5분으로 고정하고, 만료 뒤에는 이전 거리·시간을 정상 결과처럼 재사용하지 않고 새 경로를 조회한다.
- 3차 확장에서는 서버 캐시를 사용하지 않는다. 캐시 도입은 별도 범위 변경과 ADR 승인이 필요하다.

<a id="br-course-004-외부-api-실패와-부분-결과"></a>

### BR-COURSE-004 외부 API 실패와 부분 결과

- 외부 경로 API가 전체 구간을 계산하지 못하면 완전한 코스 결과를 만들지 않는다.
- 부분 성공 구간의 거리·시간을 합쳐 전체 이동 거리나 도착 시간을 추정하지 않으며, 실패 응답에는 선택 맛집·입력 순서·실패 범주만 남길 수 있다.
- 실패·429·시간 초과는 기존 맛집·회원·AI 후보 데이터를 변경하지 않고 기존 탐색 기능으로 전파하지 않는다.

## 13. 규칙 간 우선순위

서로 다른 규칙이 충돌하면 다음 순서로 적용한다.

1. 프로젝트 범위와 단계별 포함·제외 범위
2. 데이터 사실성 및 방문 근거 규칙
3. 공개·비공개 및 접근 제한 규칙
4. 중복 및 관계 정합성 규칙
5. 검색 및 표시 규칙
6. 구현 편의성

구현 편의성을 이유로 상위 비즈니스 규칙을 위반할 수 없다. 충돌을 해소할 수 없으면 임의로 구현하지 않고 제14장의 검토 필요 항목으로 기록하며, 범위 변경이 필요한 경우 [docs/00-overview/scope.md](../00-overview/scope.md)를 먼저 변경한다.

## 14. 검토 필요 항목

경로 결과의 정확한 만료 시간은 후속 API·캐시 계약에서 확정한다. 그 밖의 합의된 결정은 [requirements-review.md](requirements-review.md)와 제3장부터 제12장의 규칙에 반영했다. 프로젝트 범위에 남아 있는 미결정 사항은 [docs/00-overview/scope.md](../00-overview/scope.md) 제9장을 단일 기준으로 사용한다.

비즈니스 정책을 변경하지 않는 후속 기술 선택은 [requirements-review.md](requirements-review.md) 제3장을 따른다.
