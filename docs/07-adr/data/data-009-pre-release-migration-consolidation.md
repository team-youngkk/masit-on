# ADR-DATA-009 운영 배포 전 마이그레이션 통합 범위

## 1. 상태

Accepted

이 ADR은 [ADR-DATA-004](data-004-flyway.md) 10절 강제 규칙의 `적용된` 범위를 확정한다. ADR-DATA-004를 대체하지 않으며 그 결정과 근거는 모두 유효하다.

## 2. 결정 요약

`적용된 마이그레이션`은 **모든 환경에 적용된 마이그레이션**을 뜻하며 개발 Docker와 공유 데이터베이스를 포함한다. 다만 운영 데이터베이스에 아직 적용되지 않은 마이그레이션에 한해, 구조적 검증 장치를 모두 통과하는 조건에서 운영 배포 전 1회 통합을 허용한다.

## 3. 배경

[ADR-DATA-004](data-004-flyway.md) 10절은 "적용된 마이그레이션은 수정하지 않고 새 파일로 변경한다"고 정하면서 어느 환경에 적용된 것인지 명시하지 않았다. 9절 적용 범위는 스키마 객체를 다루고 11절은 필요한 곳에 "운영"을 명시하므로, 조문만 보면 범위가 열려 있다.

그러나 같은 ADR 3절은 "이 스키마는 결국 하나의 공유 PostgreSQL 데이터베이스(개발 Docker, 운영 RDS 동일 구조)에 함께 적용된다"고 하고, 막으려는 해악으로 "팀원 A의 변경이 **팀원 B의 로컬 환경**이나 운영 배포에 반영되지 않아 조인 대상 테이블이 없거나 제약이 어긋나는 문제"를 든다. 7절도 "4명이 독립적으로 개발하면서도 하나의 공유 스키마에 안전하게 합류할 방법"을 선택 근거로 든다. 두 절 모두 개발 환경을 보호 대상에 포함한다.

한편 개발 과정에서 마이그레이션 파일이 누적되면 초기 스키마를 읽고 검토하는 비용이 커진다. 운영 데이터베이스가 아직 없거나 해당 버전이 운영에 적용되지 않은 시점에는 통합이 기술적으로 가능하고, 운영 이력에 없는 버전을 합치므로 운영 데이터베이스에는 checksum 충돌이 발생하지 않는다.

이 ADR은 두 요구를 모두 만족하는 경계를 정한다.

## 4. 결정 문제

`적용된`을 개발 환경까지 포함하는 넓은 의미로 확정하면 통합이 전면 금지된다. 운영 적용으로 좁히면 ADR-DATA-004 3·7절이 보호하려던 개발 환경 정합성이 무너진다. 개발 환경 정합성을 훼손하지 않으면서 운영 미적용 마이그레이션의 통합을 허용할 수 있는가.

## 5. 고려한 선택지

- **넓은 의미로 확정하고 통합을 금지한다**: ADR-DATA-004 3·7절 의도를 그대로 보존한다. 초기 스키마 파일 수가 누적되는 비용을 감수한다.
- **운영 적용으로 좁힌다**: 통합이 자유로워지지만 3절이 명시한 팀원 로컬 환경 보호가 사라지고, "스키마 변경 방식 자체가 실수를 구조적으로 줄여줘야 한다"는 3절 마지막 문장에 반한다.
- **넓은 의미를 유지하되 구조적 검증을 통과한 통합만 예외로 허용한다**: 보호 범위를 좁히지 않고, 통합 시 발생 가능한 실패를 절차 준수가 아니라 자동 검증으로 차단한다.

## 6. 결정

세 번째를 선택한다.

- `적용된 마이그레이션`은 개발 Docker와 공유 데이터베이스를 포함한 **모든 환경**에 적용된 것을 뜻한다. ADR-DATA-004 10절의 보호 범위를 좁히지 않는다.
- 운영 데이터베이스에 적용된 마이그레이션은 어떤 경우에도 수정·통합·삭제하지 않는다.
- 운영 데이터베이스에 적용되지 않은 마이그레이션은 10절 강제 규칙의 예외로 통합할 수 있다. 예외는 아래 강제 규칙을 모두 만족할 때만 성립한다.
- 통합은 운영 배포 직전에 수행하며 같은 버전 구간을 두 번 통합하지 않는다.

## 7. 선택 근거

ADR-DATA-004 3절이 막으려는 해악은 **조용한 스키마 불일치**다. 팀원 B의 로컬 환경에 변경이 반영되지 않아 조인 대상 테이블이 없거나 제약이 어긋나는 상태로 애플리케이션이 동작하는 상황이다.

통합이 만드는 상태는 성질이 다르다. 통합 대상을 이미 적용한 데이터베이스에서는 Flyway `validate`가 checksum 불일치와 파일 부재를 감지해 **애플리케이션 기동 자체를 거부한다.** 잘못된 스키마로 조용히 동작하는 것이 아니라 명시적 오류로 멈춘다. 이는 3절이 요구한 "실수를 구조적으로 줄여주는" 성질을 이미 갖추고 있으며, 통합의 위험은 정합성 훼손이 아니라 **재생성 절차를 모르는 개발자의 대기 시간**이다.

따라서 남는 실질 위험은 두 가지다. 통합 과정에서 SQL 내용이 바뀌는 것과, 운영에 이미 적용된 버전을 실수로 통합 대상에 넣는 것이다. 10절 강제 규칙은 이 둘을 절차 준수가 아니라 검증으로 차단한다.

## 8. 트레이드오프

통합을 병합하면 통합 대상을 적용한 모든 개발·공유 데이터베이스가 볼륨 재생성 전까지 기동하지 않는다. 개발자는 진행 중이던 로컬 데이터를 잃는다. 이 비용은 통합 빈도를 운영 배포 직전으로 제한하고 병합 담당자의 사전 공지를 강제해 예측 가능하게 만든다.

검증 절차가 늘어나 통합 PR의 준비 비용이 커진다. 통합이 잦지 않으므로 수용한다.

## 9. 적용 범위

Flyway 마이그레이션 파일과 `flyway_schema_history`가 있는 모든 환경에 적용한다. 통합 허용 판단은 운영 데이터베이스의 적용 이력을 기준으로 한다.

## 10. 강제 규칙

통합 PR은 다음을 모두 만족해야 병합할 수 있다.

1. 통합 대상 버전이 운영 `flyway_schema_history`에 없음을 조회 결과로 증명한다. 운영 데이터베이스가 없으면 그 사실을 근거로 대신한다.
2. 통합 전후 SQL 본문이 주석과 공백을 제외하고 동일함을 대조 결과로 증명한다.
3. 빈 데이터베이스에 통합 결과를 적용해 스키마와 기준 데이터가 통합 전과 같음을 자동화 테스트로 증명한다.
4. 통합 대상을 적용한 개발·공유 데이터베이스의 재생성 절차를 PR 본문 최상단에 명시하고, 병합 담당자가 병합 직후 팀에 공지한다.
5. 삭제된 마이그레이션 파일명을 참조하는 문서·주석이 남지 않음을 확인한다. 파일명 전체와 버전 번호 단독 표기를 모두 검색한다.

## 11. 금지 사항

운영에 적용된 마이그레이션의 수정·통합·삭제를 금지한다. `flyway repair`로 checksum 불일치를 덮는 행위를 금지한다. 통합과 스키마 변경을 같은 파일에 섞는 것을 금지한다. 10절 강제 규칙 중 하나라도 증명하지 못한 통합의 병합을 금지한다.

## 12. 구현 및 운영 영향

통합 시점에 마이그레이션 파일 수가 줄고 초기 스키마 검토 비용이 낮아진다. 운영 배포 경로와 `flyway_schema_history` 이력은 영향을 받지 않는다. 개발자는 통합이 병합된 릴리스마다 한 번 로컬 데이터베이스를 재생성한다.

## 13. 검증 방법

[ADR-DATA-004](data-004-flyway.md) 13절의 두 테스트를 그대로 유지한다. 빈 PostgreSQL에 전체 마이그레이션을 적용하는 테스트와, 기존 운영 스키마 스냅샷 위에 신규 마이그레이션만 추가 적용하는 업그레이드 테스트를 모두 실행한다. 후자는 통합된 마이그레이션이 운영의 기존 이력 위에 정상 적용되는지 확인하는 수단이므로 통합을 수행한 릴리스에서 특히 중요하다.

통합 PR에서는 10절 1~5번의 증명을 PR 본문에 기록하고 리뷰어가 대조한다. 통합 대상을 적용한 데이터베이스에서 Flyway `validate`가 실제로 기동을 차단하는지도 확인한다.

## 14. 재검토 조건

통합 빈도가 릴리스당 1회를 넘거나, 10절 강제 규칙의 증명이 형식적으로만 수행되거나, 볼륨 재생성 비용으로 개발 일정에 지장이 생기거나, 운영 데이터베이스가 여러 개로 늘어 적용 이력 판단이 복잡해지면 이 결정을 재검토한다.
