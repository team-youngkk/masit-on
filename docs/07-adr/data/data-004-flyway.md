# ADR-DATA-004 Flyway 스키마 마이그레이션

## 1. 상태

Accepted

## 2. 결정 요약

모든 PostgreSQL 스키마 변경은 Flyway 12.4.0 마이그레이션으로 버전 관리한다.

## 3. 배경

4명의 개발자가 각자 자신의 워크스트림(Restaurant, Visit, Creator, Video 등)에 속한 엔티티와 스키마를 병행해서 변경하지만, 이 스키마는 결국 하나의 공유 PostgreSQL 데이터베이스(개발 Docker, 운영 RDS 동일 구조)에 함께 적용된다. 누가 어떤 순서로 스키마를 바꿨는지가 코드로 남지 않으면, 팀원 A의 변경이 팀원 B의 로컬 환경이나 운영 배포에 반영되지 않아 조인 대상 테이블이 없거나 제약이 어긋나는 문제가 생기기 쉽다. 개인별 SQL·DBA 숙련도도 확인되지 않았으므로([#7 roles.md](../../03-team/roles.md)), 스키마 변경 방식 자체가 실수를 구조적으로 줄여줘야 한다.

## 4. 결정 문제

스키마 생성·변경·배포의 권위 있는 경로를 무엇으로 둘 것인가.

## 5. 고려한 선택지

- **Flyway 12.4.0**: 스키마 변경을 버전 번호가 매겨진 SQL 파일로 코드베이스에 남기고, 적용 이력을 DB에 기록해 어떤 마이그레이션이 어느 환경에 적용됐는지 추적한다. 4명이 각자 파일을 추가해도 버전 순서대로 자동 적용되므로 병합 시 스키마 불일치를 코드 리뷰 단계에서 미리 발견할 수 있다.
- **ORM(Hibernate) 자동 DDL**: `ddl-auto`로 엔티티 변경 시 스키마를 자동 생성·갱신하는 방식. 초기 개발 속도는 빠르지만 4명이 각자 엔티티를 독립적으로 수정하는 구조에서는 누가 어떤 스키마를 언제 바꿨는지 이력이 남지 않고, Hibernate가 추론한 DDL이 팀원마다 로컬에서 다르게 적용될 위험이 있다. 운영 배포에서 자동 DDL을 쓰면 의도치 않은 컬럼 삭제·타입 변경이 무자비로 실행될 수 있어 이 프로젝트처럼 되돌리기 어려운 관리자 등록 데이터를 다루는 경우 위험이 크다.
- **수동 SQL 실행 또는 다른 마이그레이션 도구**: 수동 실행은 이력을 남기려면 별도 문서화가 필요하고 사람이 순서를 놓치기 쉬워, 4인이 병렬로 스키마를 바꾸는 이 프로젝트 구조에서는 조율 비용이 Flyway보다 크다. 다른 마이그레이션 도구(Liquibase 등)는 기능상 대체 가능하지만 이미 PostgreSQL 17.10·Spring 생태계에 널리 쓰이는 Flyway 대비 이 프로젝트에 특별한 이점이 없어 전환 근거가 약하다.

## 6. 결정

Flyway 12.4.0을 유일한 스키마 변경 경로로 사용한다.

## 7. 선택 근거

Flyway를 유일한 경로로 강제한 이유는 4명이 서로 다른 엔티티/워크스트림을 독립적으로 개발하면서도([#8 scope.md](../../00-overview/scope.md) 6번, [#7 roles.md](../../03-team/roles.md)) 하나의 공유 스키마에 안전하게 합류할 방법이 필요했기 때문이다. 버전 번호가 매겨진 마이그레이션 파일은 Git 코드 리뷰 과정에서 스키마 변경 자체를 리뷰 대상으로 만들어, 팀원별 SQL 숙련도 차이와 무관하게 변경 내용이 명시적으로 드러난다. ORM 자동 DDL을 금지한 것은 그 반대 이유로, 스키마 변경이 코드 리뷰 없이 암묵적으로 일어나는 것을 막기 위함이다.

## 8. 트레이드오프

명시적 변경 이력과 리뷰 가능성을 얻는 대신, 모든 스키마 변경을 앞으로만 진행하는 새 마이그레이션 파일로 작성해야 하므로(이미 적용된 파일은 수정 금지, 10번 강제 규칙) 되돌리기(rollback) 자동화가 기본 제공되지 않는다. 즉 잘못된 마이그레이션을 배포한 뒤 되돌리려면 그 변경을 취소하는 새 마이그레이션을 작성해야 하며, 이 절차를 팀이 미리 정해두지 않으면 실제 장애 상황에서 즉흥적으로 대응하게 될 위험이 있다. 단일 EC2·수동 복구 운영 방식([#9 technology-policy.md](../../06-architecture/technology-policy.md) 13절)과 RDS 스냅샷 백업(RPO 24시간, [#3 RV-NFR-010](../../01-requirements/non-functional-requirements.md#rv-nfr-010-백업-주기와-복구-범위))을 마지막 안전망으로 두되, 마이그레이션 자체의 전진 호환성 검토(9, 12번)를 배포 전 필수 절차로 둬 되돌릴 필요가 생기는 상황 자체를 줄인다.

## 9. 적용 범위

테이블, 제약, 인덱스, 기준 데이터와 승인된 확장 설치에 적용한다.

## 10. 강제 규칙

적용된 마이그레이션은 수정하지 않고 새 파일로 변경하며 애플리케이션 호환 순서를 검토한다.

## 11. 금지 사항

운영 수동 DDL, Hibernate 자동 생성·갱신, 다른 도구 병행과 Flyway 버전 임의 변경을 금지한다.

## 12. 구현 및 운영 영향

배포 파이프라인은 애플리케이션 배포 전에 Flyway 마이그레이션을 먼저 적용하고, 적용 실패 시 배포 자체를 중단한다. 단일 EC2·수동 재기동 운영 방식이므로 마이그레이션 실패 시 자동 롤백은 없으며 운영자가 직접 상태를 확인하고 대응 마이그레이션을 작성하거나 RDS 스냅샷(RPO 24시간, [#3 RV-NFR-010](../../01-requirements/non-functional-requirements.md#rv-nfr-010-백업-주기와-복구-범위))으로 복구할지 판단한다. 마이그레이션 파일에는 적용 대상 애플리케이션 버전을 커밋 이력으로 대응시켜 어떤 배포에 어떤 스키마 변경이 포함됐는지 추적 가능하게 한다.

## 13. 검증 방법

CI에서 빈 PostgreSQL 17.10 컨테이너에 전체 마이그레이션을 처음부터 적용하는 테스트와, 기존 운영 스키마 스냅샷 위에 새 마이그레이션만 추가 적용하는 테스트를 모두 실행해 신규 환경과 기존 환경 양쪽에서 마이그레이션이 성공하는지 확인한다. 각 마이그레이션 적용 후에는 애플리케이션 통합 테스트(Spring Data JPA 엔티티 매핑, [#3 RV-NFR-004](../../01-requirements/non-functional-requirements.md#rv-nfr-004-목표-응답-시간과-허용-오류율) 성능 기준 대상 조회)를 실행해 스키마와 엔티티 정의가 어긋나지 않는지 검증한다. 팀원이 이미 적용된 마이그레이션 파일을 수정했는지는 Flyway의 체크섬 검증(checksum mismatch 시 배포 실패)으로 CI에서 자동 차단한다.

## 14. 재검토 조건

도구 지원 종료, 복구 요구 변화 또는 현재 방식으로 안전한 배포가 불가능할 때 재검토한다.
