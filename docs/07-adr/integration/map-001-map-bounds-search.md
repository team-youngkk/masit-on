# ADR-MAP-001 Kakao 지도 표시와 뷰포트 비종속 마커 조회

## 1. 상태

Accepted. 2026-08-03 WS-07 소유자 양성훈 승인으로 기존 `south`·`west`·`north`·`east` 서버 AND 조회 결정을 변경했다.

문서 계약은 변경됐지만 현재 코드는 bounds 요청·필터를 사용한다. 구현 정합화는 [E1-T11](../../08-planning/expansion-1-task-breakdown.md)에서 추적한다.

## 2. 결정 요약

Kakao Maps JavaScript API V3는 지도 표시·이동·확대·축소·마커 상호작용에 사용한다. 서버 `GET /api/restaurants/map-points`는 저장된 WGS84 좌표가 있는 공개 맛집을 URL 탐색 조건인 이름·자치구·음식 카테고리·유튜버로만 조회한다.

지도 뷰포트는 클라이언트 표시 상태다. `south`, `west`, `north`, `east`를 API·Query Key·URL·로그·분석 이벤트에 포함하지 않으며 지도 이동만으로 서버를 재조회하지 않는다.

## 3. 배경과 변경 이유

기존 결정은 현재 지도 영역과 필터를 AND로 조합했다. 이 방식에서는 사용자가 지도 중심이나 확대 수준을 조금만 바꿔도 기존 결과가 새 영역 밖으로 밀려 마커와 대체 목록에서 사라진다. 검색을 통해 확보한 후보 집합이 지도 조작에 종속되어 비교·회귀 탐색의 맥락이 끊기는 UX 문제가 확인됐다.

공개 맛집 데이터는 서울로 제한되고 초기 지도 결과 상한은 200개다. 이 범위에서는 뷰포트마다 결과 집합을 교체하는 이점보다, 검색 결과를 유지하고 지도를 독립적으로 탐색하는 사용성이 더 중요하다고 판단했다.

## 4. 결정

### 4.1 저장 좌표와 표시 대상

- Restaurant는 WGS84 `latitude`, `longitude` nullable 쌍을 소유한다.
- 공개·활성 상태이고 좌표 쌍이 유효한 맛집만 지도 마커 조회에 포함한다.
- 좌표가 없는 기존 맛집은 지도에서만 제외하고 일반 목록·상세에는 유지한다.
- PostGIS, 거리·반경·다각형 검색은 도입하지 않는다.

### 4.2 서버 조회 조건

- `GET /api/restaurants/map-points`는 `query`, `district`, `category`, `creatorId`만 선택적으로 받는다.
- 지정한 탐색 조건은 AND로 적용하고 맛집 단위로 중복 제거한다.
- `south`, `west`, `north`, `east`는 지원하지 않는다.
- 결과는 이름·ID로 안정 정렬하고 최대 200개다. 초과 시 일부 결과 대신 `TOO_MANY_RESULTS`를 반환해 탐색 조건 추가를 안내한다.

### 4.3 프론트엔드 상태와 재조회

- Query Key는 네 URL 탐색 조건만 포함한다.
- 지도 이동·확대·축소는 Kakao Map 인스턴스의 클라이언트 상태만 변경한다.
- 지도 `idle` 이벤트로 서버 요청을 만들거나 debounce하지 않는다.
- 지도 이동 전후 마커·대체 목록·선택 상태를 유지한다.
- 화면 밖 맛집을 목록에서 선택하면 지도를 해당 마커로 이동할 수 있다.

### 4.4 개인정보와 로그

- 브라우저 위치 권한을 요청하지 않고 사용자 현재 위치·기기 식별자·이동 이력을 수집하지 않는다.
- 지도 뷰포트도 서버에 전달하지 않으므로 뷰포트 원문 로그 마스킹 규칙에 의존하지 않는다.
- 회원 식별자·찜·최근 기록을 Kakao SDK 파라미터로 전달하지 않는다.

### 4.5 외부 서비스와 장애

- Kakao JavaScript 키는 환경별 허용 도메인으로 제한하고 서버 REST 키와 분리한다.
- 사용자 조회 중 Kakao Local REST API를 호출하지 않는다.
- SDK 실패 시 지도 오류·재시도를 제공하면서 대체 목록과 다른 공개 조회를 유지한다.
- API 실패·429에서는 마지막 정상 마커·목록을 유지한다.

## 5. 고려한 선택지

### 5.1 기존 bounds 서버 AND 조회

화면 안의 데이터만 전송할 수 있으나 지도 조작마다 결과 집합과 목록이 바뀌고 검색 후보가 사라지는 UX 문제가 있어 철회했다.

### 5.2 뷰포트 비종속 필터 조회 — 채택

필터 결과 집합이 안정적이고 지도 이동이 서버 호출을 만들지 않는다. 결과가 200개를 초과하면 조건 추가가 필요하며 대규모 데이터에서는 클러스터링·페이지·공간 조회를 별도 결정해야 한다.

### 5.3 브라우저가 전체 Restaurant를 받아 공개 상태를 필터링

서버 공개·필터·상한 정책을 우회하므로 채택하지 않는다. 서버가 승인된 마커 Projection만 반환한다.

## 6. 결과와 영향

긍정적 영향:

- 지도 이동으로 검색 결과와 대체 목록이 사라지지 않는다.
- 지도 이동당 API·DB 호출과 rate limit 충돌이 제거된다.
- 뷰포트가 서버·로그·분석에 전달되지 않아 개인정보 경계가 단순해진다.

비용과 제약:

- 화면 밖 마커도 응답과 대체 목록에 포함된다.
- 조건 없는 결과가 200개를 넘으면 사용자는 필터를 추가해야 한다.
- 기존 bounds Controller·Command·Query·프론트 Query Key·테스트를 후속 구현에서 제거해야 한다.
- 기존 좌표 partial index는 적용된 migration 이력이므로 수정하지 않는다. 새 조회 실행계획에서 필요성이 낮아져도 측정 없이 파괴적 migration을 만들지 않는다.

## 7. 검증 방법

- bounds 없는 API와 네 탐색 조건 AND, 200/201개 경계를 검증한다.
- bounds 파라미터가 더 이상 계약에 포함되지 않음을 API 테스트로 검증한다.
- 지도 이동·확대·축소 전후 추가 API 요청 0건과 결과·선택 유지 여부를 브라우저에서 검증한다.
- 필터 변경·뒤로가기·앞으로가기 때만 Query Key와 결과가 바뀌는지 검증한다.
- 좌표 없음·비공개·삭제 맛집 제외와 SDK 장애 시 대체 목록 유지를 검증한다.
- 요청·로그·분석 이벤트에 사용자 현재 위치와 지도 뷰포트가 없는지 검사한다.

## 8. 재검토 조건

- 필터 결과가 반복적으로 200개를 초과해 제품 탐색이 불가능해진다.
- 마커 클러스터링·무한 지도 탐색·현재 화면 검색이 별도 사용자 동작으로 승인된다.
- 운영 측정에서 응답 크기나 조회 성능이 NFR을 반복 위반한다.
- 거리·반경·다각형·경로 검색이 승인 범위에 들어온다.
