# ADR-MAP-001 Kakao 지도 표시와 WGS84 영역 조회

## 1. 상태

Accepted

2026-07-29 요구사항·API·데이터 계약 확정 결과를 동기화했다. 기존의 Kakao Maps JavaScript API, WGS84 사각 영역 조회와 PostGIS 제외 결론은 변경하지 않았다.

## 2. 결정 요약

1차 확장 지도 화면은 브라우저의 Kakao Maps JavaScript API V3로 표시한다. 서버는 외부 지도 API를 사용자 조회 시점에 호출하지 않고 PostgreSQL에 저장한 Restaurant의 WGS84 위도·경도를 `south`, `west`, `north`, `east` 사각 경계로 조회한다.

좌표는 Restaurant에 nullable `numeric(9,6)` 위도·경도 쌍으로 저장한다. 초기 영역 조회는 partial B-tree와 수치 범위 조건을 사용하며 PostGIS는 도입하지 않는다. 현재 위치, 거리·반경 검색, 날짜변경선을 가로지르는 영역과 자동 좌표 동기화는 1차 확장에서 제외한다.

## 3. 배경

[지도 기반 탐색 PRD](../../04-product/prd/discovery/map-discovery.md)는 사용자가 현재 보고 있는 지도 영역 안에서 공개 맛집의 위치를 파악하고, 지도 마커와 접근 가능한 대체 목록을 통해 같은 맛집 집합을 탐색하도록 요구한다. 이 목표에는 기본 지도 렌더링과 직사각형 영역 조회가 필요하지만 사용자의 현재 위치나 거리 계산은 필요하지 않다.

기존 Restaurant 구현과 V1 스키마에는 좌표가 없다. 기존 공개 맛집을 유지하면서 지도 기능을 추가하려면 좌표 미확보 행을 허용하고, 검증된 좌표가 생긴 행부터 지도에 노출해야 한다. Flyway가 외부 API를 호출하거나 알 수 없는 좌표를 `0,0` 등으로 채우면 배포 재현성과 데이터 신뢰성을 모두 잃는다.

Kakao Maps JavaScript API는 브라우저에 내려가는 외부 SDK다. 따라서 브라우저용 JavaScript 키는 사용자에게 전달되는 식별자라는 성격을 숨길 수 없으며, 서버에서 사용하는 Kakao Local REST API 키와 같은 비밀정보 취급이나 전달 경계를 적용할 수 없다. 키 분리, 허용 도메인 제한, 사용량·비용 감시와 SDK 장애 격리를 함께 결정해야 한다.

## 4. 결정 문제

다음 조건을 만족하면서 지도 표시와 공간 조회를 어떤 구조로 제공할 것인가.

- 현재 지도 화면의 직사각형 경계와 기존 맛집 탐색 조건을 함께 적용한다.
- 지도 결과와 대체 목록이 동일한 공개 Restaurant 집합을 표현한다.
- 기존 좌표 없는 Restaurant의 일반 목록·상세 계약을 깨뜨리지 않는다.
- 지도 제공자의 키·쿼터·비용·SDK 장애가 서버의 공개 조회 전체로 확산되지 않게 한다.
- 현재 위치와 이동 이력 같은 추가 개인정보를 수집하지 않는다.
- 초기 데이터 규모와 팀 운영 역량에 비례하는 저장·조회 구조를 선택한다.

## 5. 고려한 선택지

### 5.1. PostgreSQL 수치 좌표와 B-tree 영역 조회

Restaurant에 WGS84 위도·경도를 수치 컬럼으로 저장하고 `BETWEEN` 조건으로 직사각형 영역을 조회한다. 별도 확장 설치 없이 기존 PostgreSQL·JPA·Flyway 운영 방식 안에서 구현할 수 있고, 1차 확장의 사각 영역 조회와 초기 데이터 규모에 맞는다. 반면 거리·반경·다각형·경로 질의에는 적합하지 않고 데이터가 커지면 두 범위 조건의 실행계획을 다시 검토해야 한다.

### 5.2. PostGIS와 공간 인덱스

공간 타입과 GiST/SP-GiST 계열 인덱스를 사용하면 거리·반경·다각형 같은 공간 연산으로 확장하기 쉽다. 그러나 1차 확장에는 해당 기능이 없고, PostgreSQL 확장 설치·마이그레이션·ORM 매핑·테스트 및 운영 복구 절차가 추가된다. 현재 요구사항보다 큰 복잡도를 먼저 부담하므로 채택하지 않는다.

### 5.3. 사용자 조회마다 Kakao 장소 API로 좌표 조회

저장 좌표 없이 최신 외부 결과를 사용할 수 있지만 공개 조회의 응답 시간·가용성·쿼터·비용이 외부 서비스에 직접 종속된다. 동일 요청이 반복될 때마다 외부 호출이 발생하고, SDK나 API 장애가 저장된 맛집 탐색까지 실패시킬 수 있으므로 채택하지 않는다.

### 5.4. 브라우저가 전체 맛집을 받아 영역 필터링

서버 영역 질의가 단순해 보이지만 브라우저로 불필요한 전체 데이터를 전송하고 서버의 공개·필터·상한 정책을 우회한다. 지도와 다른 조회 계약의 일관성 및 데이터 증가 대응이 어려워 채택하지 않는다.

## 6. 결정

### 6.1. 브라우저 지도 책임

Kakao Maps JavaScript API V3는 다음 범위에서만 사용한다.

- 기본 지도 렌더링
- 지도 이동·확대·축소와 이동 완료 이벤트
- 현재 화면 경계 산출
- 서버가 반환한 최대 200개 Restaurant 마커 표시와 선택 상태 연동

장소 검색 결과를 공개 조회마다 가져오는 기능, 사용자 현재 위치 취득, 거리·반경 계산, 길찾기·경로 추천은 사용하지 않는다. Kakao SDK 타입은 프론트엔드 내부에만 머물며 서버 API 요청·응답 모델에 노출하지 않는다.

### 6.2. 좌표 저장

Restaurant에 다음 두 컬럼을 nullable로 추가한다.

| 컬럼 | 타입 | 규칙 |
|---|---|---|
| `latitude` | `numeric(9,6)` | WGS84, `-90` 이상 `90` 이하 |
| `longitude` | `numeric(9,6)` | WGS84, `-180` 이상 `180` 이하 |

두 컬럼은 함께 값이 있거나 함께 `NULL`이어야 한다. 좌표 정밀도의 자릿수 표현은 Restaurant 식별이나 동일성 기준으로 사용하지 않는다. 1차 확장에서는 PostGIS, 공간 타입과 공간 인덱스를 사용하지 않고 [인덱스 전략](../../05-specs/data/index-strategy.md)의 partial B-tree로 시작한다.

### 6.3. 기존 Restaurant와 좌표 보강

좌표 컬럼을 추가하는 V4 마이그레이션은 기존 행을 `NULL`로 유지한다. Flyway 안에서 Kakao API를 호출하거나 주소를 좌표로 임의 변환하지 않는다.

기존 Restaurant의 좌표 보강은 저장된 Kakao 장소 식별자를 기준으로 관리자가 장소 동일성과 좌표를 확인한 뒤 수행한다. 보강 작업은 같은 Restaurant에 다시 실행해도 동일한 검증 결과를 저장하는 멱등 흐름이어야 하며, 성공한 행만 값을 갱신한다. 신규 Restaurant도 관리자 장소 확인에서 유효 좌표를 확보한 경우 해당 좌표를 저장한다.

좌표가 없거나 범위·쌍 제약을 만족하지 않는 Restaurant는 지도 결과에서만 제외한다. 공개 상태와 생명주기 조건을 만족한다면 기존 일반 목록·상세에는 계속 노출한다. 좌표가 있다는 사실만으로 공개 상태를 변경하지 않는다.

### 6.4. 영역 조회 계약

서버는 `GET /api/restaurants/map-points`에서 `south`, `west`, `north`, `east`를 필수로 받고 경계선 위 좌표를 포함한다. `south < north`, `west < east`여야 하며 날짜변경선을 가로지르는 `west > east` 영역은 지원하지 않는다. 이름·자치구·음식 카테고리·유튜버 조건이 있으면 영역 조건과 AND로 적용한다.

한 영역의 결과가 200개 이하이면 전체 결과를 반환한다. 200개를 초과하면 임의 부분집합이나 클러스터를 반환하지 않고 `TOO_MANY_RESULTS`와 빈 `items`를 반환해 영역 축소 또는 조건 추가를 유도한다.

브라우저는 지도 이동 완료 뒤 300ms debounce를 적용한다. 서버는 신뢰된 프록시 경계에서 판정한 클라이언트 요청 출처를 기준으로 초당 최대 4회의 영역 조회를 허용하고, 초과 요청에는 `429 RATE_LIMIT_EXCEEDED`와 `Retry-After`를 반환한다.

### 6.5. 키, 비용과 외부 서비스 경계

- Kakao Maps JavaScript 키는 브라우저에 포함되므로 비밀키로 간주하지 않는다. 대신 환경별 허용 도메인을 Kakao 애플리케이션 설정에 제한하고, 승인하지 않은 출처에서 사용할 수 없게 한다.
- Kakao Local REST API 키는 서버 비밀정보다. JavaScript 키와 분리하고 브라우저 번들·HTML·응답·로그에 포함하지 않는다.
- 공개 지도 영역 API는 저장된 PostgreSQL 좌표만 조회하며 Kakao Local REST API를 호출하지 않는다. 서버 영역 조회의 성공 여부가 Kakao API 쿼터에 종속되지 않게 한다.
- Kakao 콘솔에서 JavaScript SDK 사용량, 쿼터와 과금 정책을 운영 전 확인하고 운영 중 감시한다. 이 ADR은 제공자가 보장하지 않은 무료 호출량이나 고정 비용을 전제하지 않는다.
- 300ms debounce와 화면 재요청 병합은 불필요한 브라우저 SDK·서버 조회를 줄이고, 서버 초당 4회 제한은 데이터베이스와 API 남용을 통제한다. Kakao 측 쿼터·비용 제한은 제공자 콘솔 설정과 사용량 감시로 별도 통제한다.

### 6.6. 개인정보와 장애 경계

브라우저 위치 권한을 요청하지 않고 `Geolocation` 등으로 사용자 현재 좌표를 취득하지 않는다. 현재 위치, 기기 식별자와 이동 이력을 서버 요청·응답·저장소·업무 로그·분석 이벤트에 포함하지 않는다. 지도 화면 bounds는 공개 Restaurant 조회 조건으로만 사용하며 회원의 현재 위치로 해석하거나 개인화 데이터와 결합하지 않는다.

다만 `/api/restaurants/map-points`의 bounds 쿼리 문자열은 위치와 유사한 일시적 탐색 조건이므로 원문을 Nginx access log, Spring 요청 로그, APM trace·span, 오류 보고와 분석 이벤트에 남기지 않는다. 관측 정보는 정규화한 경로 템플릿, `traceId`, 상태 코드, 지연, 결과 개수 또는 초과 여부로 제한한다.

브라우저가 외부 SDK를 불러오므로 Kakao는 SDK 요청 과정의 네트워크 정보를 처리할 수 있다. 애플리케이션은 회원 식별자, 이메일, 찜, 최근 기록과 현재 위치를 SDK 파라미터로 전달하지 않고 외부 SDK 사용 사실과 적용되는 제공자 정책을 사용자에게 알릴 수 있어야 한다.

Kakao Maps SDK 로딩·렌더링이 실패하면 지도 컴포넌트에 오류와 재시도 수단을 표시한다. 서버 지도 영역 API와 일반 맛집 목록·상세는 저장 데이터만 사용하므로 함께 실패시키지 않는다. 지도 화면의 접근 가능한 대체 목록과 지도 밖 공개 탐색 경로도 유지한다.

### 6.7. 좌표 동기화

등록 이후 좌표의 자동 주기 동기화, 외부 데이터 변경 감지와 자동 좌표 보정은 포함하지 않는다. 좌표 정정은 관리자가 다시 장소를 검증한 명시적 작업으로 수행한다. 자동 동기화는 호출량·충돌 해결·감사·오류 복구 정책이 필요한 별도 결정이므로 이 ADR로 암묵적으로 도입하지 않는다.

## 7. 선택 근거

- 제품 목표는 현재 화면의 공개 맛집 분포 확인이며 거리 계산이 아니다. WGS84 사각 경계는 요구사항을 직접 표현한다.
- nullable 좌표는 V1 Restaurant를 중단 없이 확장하면서 검증되지 않은 값을 만들지 않는다.
- 저장 좌표 조회는 일반 사용자 요청을 Kakao Local API의 지연·장애·쿼터와 분리한다.
- 수치 컬럼과 partial B-tree는 현재 직사각형 조회에 필요한 최소 구조이며, PostGIS 도입 판단을 실제 실행계획과 성능 측정까지 미룰 수 있다.
- 브라우저 JavaScript 키와 서버 REST 키를 분리하면 공개 식별자와 비밀정보의 보호 경계가 명확해진다.
- 사용자 현재 위치를 수집하지 않으면 위치 권한·보존·삭제·동의 흐름을 1차 확장에 추가하지 않고도 지도 탐색 가치를 제공할 수 있다.

## 8. 트레이드오프와 결과

### 8.1. 긍정적 결과

- 기존 PostgreSQL·Flyway 운영 구조 안에서 구현하며 별도 공간 확장을 운영하지 않는다.
- 외부 SDK 장애가 저장 데이터 기반 API와 다른 공개 조회로 확산되지 않는다.
- 좌표 없는 기존 Restaurant를 삭제하거나 비공개로 바꾸지 않고 단계적으로 보강할 수 있다.
- 사용자 위치를 수집하지 않아 위치 개인정보의 저장·삭제 책임을 만들지 않는다.

### 8.2. 감수하는 제약

- 좌표 보강 전까지 일부 공개 Restaurant가 지도에서 누락된다.
- 거리·반경·다각형·날짜변경선 교차 검색은 제공할 수 없다.
- 수치 범위와 B-tree는 데이터 증가나 복잡한 공간 질의에서 PostGIS보다 비효율적일 수 있다.
- 외부 SDK가 차단되거나 Kakao 정책·쿼터·비용이 바뀌면 지도 렌더링은 영향을 받는다.
- 자동 좌표 갱신이 없으므로 장소 이전이나 제공자 좌표 변경은 관리자 검증 전까지 반영되지 않는다.

## 9. 강제 규칙

- 지도에는 유효 좌표가 있는 `PUBLIC`·`ACTIVE` Restaurant만 표시한다.
- 위도·경도는 WGS84 `numeric(9,6)` nullable 쌍이며 둘 중 하나만 저장할 수 없다.
- 기존 `NULL` 좌표는 허용하고 지도에서만 제외한다.
- 지도 영역 조건과 지정된 기존 탐색 조건은 모두 AND로 적용하고 Restaurant 중복을 제거한다.
- 경계는 포함 조건이며 날짜변경선 교차 영역은 거부한다.
- 결과 상한은 200개이고, 초과 시 일부 결과를 반환하지 않는다.
- 300ms debounce와 클라이언트 요청 출처별 초당 최대 4회 서버 제한을 적용한다.
- 사용자 현재 위치·기기 식별자·이동 이력을 요청·저장·로그·분석하지 않는다.
- `/api/restaurants/map-points`의 쿼리 문자열과 bounds 원문을 Nginx·Spring·APM·분석 로그에 남기지 않는다.
- 브라우저 JavaScript 키에는 허용 도메인 제한을 적용하고 서버 REST 키는 클라이언트에 노출하지 않는다.
- Flyway와 일반 사용자 조회에서 외부 지도 API를 호출하지 않는다.
- 자동 좌표 동기화와 관리자 확인 없는 좌표 보정을 수행하지 않는다.

## 10. 구현 및 운영 영향

- V4 Flyway는 nullable 좌표, 값 범위와 null 쌍 CHECK, 지도용 partial B-tree만 추가한다. 기존 V1을 수정하지 않는다.
- Restaurant 등록·수정 흐름은 Kakao에서 동일 장소임을 관리자가 확인한 좌표만 저장해야 한다.
- 지도 영역 조회는 Restaurant가 소유하고, Kakao SDK 렌더링과 마커 상호작용은 프론트엔드가 소유한다.
- SDK와 제공자 정책 변경은 Adapter·프론트 지도 경계에서 흡수하며 API 응답에 Kakao 타입을 전파하지 않는다.
- 운영 전 허용 도메인, 키 분리, 쿼터·과금 설정과 장애 시 대체 흐름을 점검한다.
- Nginx access log와 Spring 요청 로깅은 지도 영역 경로에 대해 쿼리 문자열을 제외하고 APM·분석에는 bounds를 속성으로 추가하지 않는다.
- 사용량·비용 증가만으로 애플리케이션 캐시를 즉시 추가하지 않는다. 실제 반복 요청과 데이터베이스 부하가 병목으로 확인되면 캐시 일관성·TTL·무효화 정책을 별도 ADR에서 결정한다.

## 11. 검증 방법

- 좌표 범위, 위도·경도 null 쌍과 기존 `NULL` Restaurant의 마이그레이션 호환성을 PostgreSQL 통합 테스트로 검증한다.
- 남·서·북·동 경계 좌표 포함, 역전 영역·날짜변경선 교차 거부, 기존 필터 AND와 중복 제거를 검증한다.
- 결과 200개는 전체 반환하고 201개는 `TOO_MANY_RESULTS`와 빈 `items`를 반환하는지 검증한다.
- 좌표 없음·비공개·삭제 Restaurant는 지도에서 제외되고 일반 목록·상세에는 각 기존 공개 계약대로 남는지 검증한다.
- 300ms debounce, 초당 4회 경계, `429`와 `Retry-After`를 브라우저·API 테스트로 검증한다.
- 번들·HTML·응답·로그에 서버 REST 키가 없고 JavaScript 키의 허용 도메인이 제한됐는지 검사한다.
- 요청·응답·저장소·로그·분석 이벤트와 SDK 파라미터에 사용자 현재 위치·기기 식별자·회원 개인화 데이터가 없는지 검사한다.
- 지도 영역 요청 표본으로 Nginx·애플리케이션·APM·분석 로그를 검사해 bounds 쿼리 원문은 없고 경로 템플릿·`traceId`·상태·지연·결과 수만 남는지 검증한다.
- Kakao SDK 차단·로딩 실패에서 지도 오류·재시도가 표시되고 대체 목록과 지도 밖 공개 조회가 계속 동작하는지 검증한다.
- 운영 유사 데이터에서 지도 영역 조회의 p95 1.5초 기준과 실행계획을 확인한다.

## 12. 재검토 조건

다음 중 하나가 발생하면 별도 ADR에서 이 결정을 재검토한다.

- 현재 위치, 거리·반경·다각형 검색, 날짜변경선 교차, 길찾기 또는 경로 추천이 승인 범위에 들어온다.
- 운영 유사 데이터에서 지도 영역 조회가 p95 1.5초를 반복 초과하고 실행계획상 좌표 범위 필터가 병목으로 확인된다.
- 데이터 규모 또는 조회량 증가로 partial B-tree나 무캐시 조회가 운영 목표를 충족하지 못한다.
- Kakao Maps JavaScript API의 제공 조건·키 정책·쿼터·과금이 변경되어 현재 구조의 비용 또는 가용성을 수용할 수 없다.
- 기존 좌표 누락·오류나 장소 이동이 반복되어 관리자 수동 보강으로 데이터 품질을 유지하기 어렵다.
- 자동 좌표 동기화가 승인 범위에 들어와 동기화 주기, 충돌 우선순위, 실패 재시도, 호출 상한과 감사 기록을 결정해야 한다.

PostGIS를 재검토할 때에는 수치 B-tree 개선, 범위 분할·쿼리 최적화, 공간 타입과 GiST/SP-GiST 인덱스를 같은 운영 데이터와 실행계획으로 비교한다. 자동 좌표 동기화와 캐시는 각각 장기 운영·외부 종속성 및 일관성 트레이드오프가 있으므로 PostGIS 선택에 묶어 자동 도입하지 않는다.
