# 맛잇온 3차 확장 선행 상태 검토

## 1. 목적과 판정 범위

이 문서는 자연어 검색, AI 기반 영상 정보 추출, 동선 및 코스 추천의 범위 승인 전에 현재 저장소·운영 환경·데이터·외부 연동·성능 검증의 선행 상태를 확인한 기준선이다.

조사 당시 3차 확장은 [범위 문서](../00-overview/scope.md#53-3차-확장)에서 후보로만 분류되어 있었으므로, 이 문서는 범위나 기술을 승인하지 않았다. 이후 [3차 확장 범위와 용어 결정](third-expansion-scope-and-terminology.md)에서 초기 범위를 승인했으며, 이 문서는 당시 확인 가능한 사실·미확인 항목·후속 결정 게이트를 보존한다. 미확인 항목은 구현 가정으로 사용하지 않는다.

특히 2차 확장의 성능 검증을 3차 확장 이후로 연기한 팀 결정을 반영한다. 연기된 측정은 3차 확장 최종 완료 게이트로 승계하는 것을 이 문서의 권고로 기록하되, 실제 완료 판정은 후속 3차 확장 계획과 요구사항에서 다시 추적한다.

### 3.2. 현재 문서와 구현 상태의 차이

현재 `README.md` 첫 설명은 MVP와 1차 확장 상태, V1·V2 마이그레이션만 설명한다. 그러나 기준 커밋에는 2차 확장 V3 마이그레이션과 기능 코드가 있으며 `origin/main`에는 2차 확장 승격 계보가 있다. 이는 3차 확장 착수 전에 README의 제품 상태·마이그레이션 설명을 현재 릴리즈 기준으로 동기화해야 한다는 문서 정합성 결함이다. 이 문서에서는 범위를 넓히지 않고 후속 정합화 항목으로 남긴다.

## 4. 자연어 검색에 사용할 실제 저장 데이터

### 4.1. 현재 저장 필드와 활용 가능성

| 데이터 | 현재 저장 필드 | 3차 확장 활용 가능성 | 현재 한계 |
|---|---|---|---|
| 맛집 | 이름, 자치구, 음식 카테고리, 도로명·상세 주소, 전화번호, Kakao 장소 식별자·URL, 위도·경도, 공개·생명주기 상태 | 구조화 필터와 이름 검색의 기반 | 현재 검색은 `restaurant.name`의 부분 문자열과 지역·카테고리·유튜버 조건 조합이다. 주소·전화번호·설명에 대한 자연어 검색 인덱스는 없다. |
| 유튜버 | 채널명, URL, 프로필 이미지, 채널 소개, handle, 공개·생명주기·외부 가용 상태 | 채널 설명과 방문 관계를 검색 문맥으로 사용할 후보 | 채널 소개의 품질·언어·갱신 시점이 보장되지 않으며 검색 전용 정규화나 임베딩이 없다. |
| 영상 | 제목, 원본 URL, 썸네일 URL, 게시 시각, 게시 채널 식별자, 공개·생명주기·외부 가용 상태 | 제목·게시일·방문 관계를 검색 문맥으로 사용할 후보 | 영상 설명, 자막·전사, 구간 시각, 장소 언급, 메뉴·가격과 같은 영상 본문 정보는 저장하지 않는다. |
| 방문 관계 | 맛집·유튜버·영상의 검증된 관계와 공개·생명주기 상태 | 검색 결과의 근거 관계와 설명에 사용 | 관계가 실제 방문을 증명한다는 판정만 저장하며, AI가 참고할 장면·발화·근거 구간은 저장하지 않는다. |
| 인기·큐레이션 | 현재 찜 수 기반 인기, 관리자 큐레이션 제목·설명·순서·맛집 연결 | 검색 결과의 정렬·노출 보조 신호 후보 | 인기에는 시간 이력·조회 이벤트가 없고, 큐레이션은 관리자 편집 콘텐츠다. 둘 다 자연어 의미 검색이나 개인화 추천 점수가 아니다. |

현재 저장 데이터만으로는 `"매운 국물과 해산물 영상이 있는 강남 맛집"` 같은 질의를 신뢰성 있게 해석할 근거가 부족하다. 자연어 검색을 진행하려면 최소한 질의 해석 대상 필드, 검색 대상 데이터의 정규화, 키워드·전문 검색 또는 임베딩 저장 방식, 공개 상태 필터와 결과 근거 표시를 별도 계약으로 결정해야 한다.

### 4.2. 인기·큐레이션 데이터의 재사용 경계

- 인기 맛집은 [ADR-DATA-011](../07-adr/data/data-011-popular-restaurant-request-time-aggregation.md)에 따라 현재 `favorite` 관계를 요청 시점에 집계한다. 찜 생성·취소 이력, 기간별 순위, 조회수, 시간 감쇠 값은 없다.
- 큐레이션은 관리자가 만든 공개 콘텐츠와 수동 순서를 저장한다. 게시 큐레이션의 순서를 AI 추천 점수나 사용자 선호도 데이터로 해석하지 않는다.
- 개인 컬렉션은 회원 소유의 비공개 자원이다. 3차 확장에서 추천 신호로 사용하려면 회원 동의, 익명화·보존, 공개 결과에 대한 개인정보 경계를 먼저 승인해야 한다.
- 따라서 2차 확장의 인기·큐레이션 데이터를 3차 확장의 입력으로 사용할 수 있다는 것은 후보일 뿐이며, 재사용을 전제로 PRD·데이터 계약을 작성하지 않는다.

## 5. AI 추출 결과와 관리자 등록 흐름

### 5.1. 현재 관리자 등록 흐름

현재 관리자 기본 데이터 등록은 다음 흐름이다.

1. 관리자가 맛집·유튜버·영상을 검증 미리보기 API에 제출한다.
2. 서버가 Kakao 또는 YouTube 외부 응답, 입력값, 중복을 확인한다.
3. 관리자가 정규화된 후보 Snapshot을 확인한다.
4. `READY`인 확인 Token으로 생성 API를 호출한다.
5. 맛집·유튜버·영상이 저장된 뒤 관리자가 방문 관계를 등록한다.

이 흐름은 [관리자 기본 데이터 API](../05-specs/api/admin/reference-data-api.md)의 현재 계약이다. 자동 등록이나 관리자 확인 없는 공개 반영은 현재 범위에 없다.

### 5.2. AI 추출 결과의 현재 상태

현재 저장소에는 다음 항목이 없다.

- 영상 자막·음성 전사·OCR·장면 분석 결과 저장 테이블
- AI 모델·프롬프트·모델 버전·입출력 Token 사용량 기록
- 추출된 맛집 후보·메뉴·주소·방문 시각·근거 구간의 별도 Snapshot
- `PENDING → REVIEWED → ACCEPTED/REJECTED`와 같은 AI 결과 검수 상태
- AI 결과를 기존 맛집·유튜버·영상·Visit 생성으로 연결하는 관리자 API
- 재처리·실패·중복·비용 상한·개인정보 삭제를 위한 작업 상태와 운영 지표

따라서 기존 관리자 등록 흐름을 재사용할 수 있다는 것은 **검수 화면과 최종 확정 경계를 재사용할 수 있다**는 뜻이지, 현재 API에 AI 결과를 바로 주입할 수 있다는 뜻이 아니다. 3차 확장에서는 AI 결과를 원본 데이터와 분리된 후보·근거·검수 모델로 저장하고, 관리자가 확인한 결과만 기존 정식 Entity와 Visit에 반영하는지 먼저 결정해야 한다.

## 6. 맛집 좌표 보강률

### 6.1. 현재 계약과 구현

- `restaurant.latitude`와 `restaurant.longitude`는 `numeric(9,6)` nullable 열이며 둘 다 null이거나 둘 다 값이 있어야 한다.
- Kakao Local 검증 Adapter가 응답의 `x`·`y`를 유효 범위로 변환해 후보 Snapshot에 넣는다. 제공자가 좌표를 주지 않으면 등록은 가능하지만 두 좌표는 null로 저장된다.
- 지도 조회는 공개·활성이고 좌표가 모두 있는 맛집만 반환한다. 좌표 없는 맛집은 목록·상세에서는 유지된다.
- 현재 운영 스냅샷 기록에는 2026-07-30 기준 `restaurant` 1건이 기록되어 있지만, 그 행의 좌표 유무와 전체 좌표 보강률은 기록되어 있지 않다.

### 6.2. 측정 상태

운영 DB의 현재 보강률은 다음 읽기 전용 SQL로 확인해야 한다.

```sql
SELECT
    COUNT(*) AS total_restaurants,
    COUNT(*) FILTER (WHERE latitude IS NOT NULL AND longitude IS NOT NULL) AS restaurants_with_coordinates,
    COUNT(*) FILTER (WHERE latitude IS NULL AND longitude IS NULL) AS restaurants_without_coordinates,
    ROUND(
        100.0 * COUNT(*) FILTER (WHERE latitude IS NOT NULL AND longitude IS NOT NULL)
        / NULLIF(COUNT(*), 0),
        2
    ) AS coordinate_coverage_percent
FROM restaurant
WHERE lifecycle_status = 'ACTIVE';
```

현재 작업 환경에는 실행 중인 PostgreSQL 컨테이너가 없고, 운영 RDS의 현재 값을 직접 조회하지 않았다. 따라서 좌표 보강률은 **미확인**이다. 운영 SQL 결과 없이 3차 확장의 동선·코스 추천 가능 데이터가 충분하다고 판정하지 않는다.

성능 테스트 시드의 별도 상태도 주의한다. `perf/seed/02-restaurant.sql`은 1,000개 맛집의 `latitude`·`longitude`를 모두 null로 넣는다. 이 시드는 2차 인기·큐레이션 공개 조회 부하용이며 지도·동선·코스 추천의 좌표 기준 데이터로 사용할 수 없다. 3차 확장 성능 시드는 좌표 분포와 좌표 없는 행의 비율을 명시해야 한다.

## 7. AI·Kakao Mobility 비용과 호출 제한

### 7.1. AI 제공자

기준선 검토 시점에는 AI 제공자·모델·리전·보존 정책이 정해지지 않았고 코드나 환경 설정에도 AI 호출이 없었다. 이후 과거 검증 당시 Google Gemini API Free Tier의 `gemini-3-flash-preview`를 smoke test 후보로 사용했지만, 현재 운영 선택은 `gemini-3.5-flash-lite`이며 데이터베이스에는 통합 V4 제약으로 해당 모델만 저장한다. 실제 모델별 무료 quota와 billing 미연결 여부는 구현 전 연결 검증에서 확인한다. 무료 tier를 사용할 수 없으면 AI 기능은 호출하지 않고 기존 수동 등록으로 대체한다.

#### 7.1.1 연결 검증 기록

2026-08-10 로컬 `.env`의 API 키를 사용해 값을 기록하지 않는 최소 smoke test를 실행했다.

| 검증 항목 | 결과 | 증거 |
|---|---|---|
| 과거 후보 `gemini-3-flash-preview` 텍스트 호출 | 통과 | `generateContent` 성공, 입력 16·출력 5 Token 메타데이터 확인 |
| 공개 YouTube URL 영상 입력 | 통과 | 공개 영상 URL을 `file_data.file_uri`로 전달해 `generateContent` 성공, 입력 13,589·출력 15 Token 메타데이터 확인 |
| 구조화 출력 | 통과 | `videoAccessible`·`evidenceTimestamp` JSON 필드 파싱 성공 |
| 원문·응답 보존 | 통과 | 테스트 출력에 응답 본문·API 키를 남기지 않음 |
| Free Tier·billing 미연결 | 미확인 | API 성공만으로 tier를 판정할 수 없어 AI Studio 프로젝트 quota·billing 화면 확인 필요 |

따라서 모델·영상 입력·구조화 출력 연동은 활성화 후보로 통과했지만, **Free Tier 전용 운영 게이트는 AI Studio의 실제 프로젝트 quota와 billing 미연결 상태를 확인하기 전까지 보류**한다. 결제 연결 또는 무료 quota 미지원이 확인되면 호출을 차단하고 관리자 수동 등록 fallback을 사용한다.

3차 확장 범위 승인 전에 최소한 다음 값을 제공자와 함께 확정해야 한다.

| 결정 항목 | 필요한 값 |
|---|---|
| 현재 운영 모델 | `gemini-3.5-flash-lite`, 영상·구조화 출력 지원, Prompt `P7`, Schema `S1`; 기존 P1 평가 자산과 P2·P3·P4·P5·P6 작업은 역사적 이력으로 보존 |
| 비용 | AI·Mobility 유료 호출 금지, Free Tier quota의 80% 경보·100% hard stop |
| 호출 제한 | 시도 전체 120초, 최대 2회 재시도, 인스턴스당 Worker 1개, quota 미확인 시 호출 차단 |
| 데이터 경계 | Free Tier global endpoint, File API·context caching·원문 저장 미사용, 관리자 전용 근거 메타데이터만 보존 |
| 품질 | AI 후보 정밀도·재현율·검수 통과율 목표와 관리자 승인 전 공개 금지 |
| 운영 | 요청 예산 초과 차단, 사용량 계측, 모델 장애 시 수동 등록 fallback |

실제 제공자 호출은 위 smoke test로 확인했지만, 운영 활성화 전에는 특정 프로젝트의 Free Tier quota·billing 미연결·데이터 처리 설정을 별도로 확인해야 한다. 이 확인이 끝나기 전에는 운영 호출을 활성화하지 않는다.

### 7.2. Kakao Mobility

현재 저장소에는 Kakao Mobility 호출이 없고 Kakao Local 장소 검증만 있다. 동선·코스 추천에서 사용할 Mobility 제품과 API 형태도 아직 정해지지 않았다.

2026-08-10 공식 가격 페이지에서 확인되는 후보 길찾기 API의 기준은 다음과 같다. 일일 제공량은 변경될 수 있고, 제휴 API 사용에는 사전 제휴 계약이 필요하므로 아래 수치를 최종 계약값으로 고정하지 않는다.

| 후보 API | 공식 일일 제공량 | 무료 quota 초과 시 공식 가격표 |
|---|---:|---:|
| 자동차 길찾기 | 10,000건 | 월간 약 1,000,000건 구간에서 요청당 8원 |
| 다중 경유지 자동차 길찾기 | 5,000건 | 월간 약 500,000건 구간에서 요청당 16원 |
| 다중 출발지 자동차 길찾기 | 1,000건 | 별도 가격·계약 확인 필요 |
| 다중 목적지 자동차 길찾기 | 1,000건 | 월간 약 300,000건 구간에서 요청당 20원 |
| 미래 운행 정보 길찾기 | 5,000건 | 월간 약 1,000,000건 구간에서 요청당 8원 |

공식 문서상 자동차 길찾기는 출발지 1개·목적지 1개에 최대 5개 경유지를, 다중 경유지·다중 목적지 API는 최대 30개 지점을 다룬다. 따라서 코스 후보 수와 지점 수를 계약에서 제한하지 않으면 한 사용자 요청이 여러 Mobility 호출로 증폭될 수 있다.

3차 확장에서 Kakao Mobility를 사용하려면 다음을 별도로 결정한다.

- 요청 시점 실시간 계산인지, 관리자·배치 사전 계산인지
- 출발지·목적지·경유지 최대 개수와 후보 코스 수
- 동일 좌표 조합의 캐시 키·보존 기간·재계산 조건
- 무료 일일 quota와 월 비용 상한을 넘을 때 차단·대체 응답
- 제휴 계약과 운영 계정, 외부 장애·429·시간 초과 처리
- 실제 도로 경로 결과를 저장할지, 요청 시점에만 반환할지

공식 근거: [Kakao Mobility 쿼터 및 가격](https://developers.kakaomobility.com/price/), [Kakao Mobility 제휴 API](https://developers.kakaomobility.com/affiliate/), [길찾기 API 제품 범위](https://developers.kakaomobility.com/product/naviapi.html).

## 8. 단일 EC2와 비동기 작업 수용성

### 8.1. 현재 운용 기반

M2 운영 구성은 단일 EC2 `t4g.medium`에 Nginx·Next.js·Spring Boot·Redis 8.8 컨테이너를 함께 두고, PostgreSQL은 RDS `db.t4g.micro`를 사용하는 구성이다. [ADR-DEPLOY-002](../07-adr/platform/deploy-002-validation-deployment-before-expansion.md)에 따라 3차 확장까지 단일 인스턴스와 수동 복구를 유지한다.

현재 코드에는 다음과 같은 제한된 백그라운드 작업 기반이 있다.

- Spring `@Scheduled` 기반의 최근 조회·멱등성·알림·보존 cleanup
- 회원 Action 메일 Outbox와 PostgreSQL `FOR UPDATE SKIP LOCKED` claim
- 회원 탈퇴·세션 폐기 복구 작업과 재시도 시각
- 외부 메시지 브로커·별도 Worker·범용 비동기 이벤트 버스는 없음
- AI·전사·영상 분석·경로 계산용 `@Async` 실행기나 전용 TaskScheduler는 없음

### 8.2. 판정

현재 구조는 회원 메일, 정리 작업, 좁은 재시도 작업에는 제한적으로 사용할 수 있다. 그러나 다음을 보장하지 않는다.

- 긴 영상의 전사·추출이 웹 요청 스레드와 EC2 메모리를 고갈시키지 않는다는 보장
- AI·Mobility 호출의 동시성·rate limit을 전역으로 제어하는 보장
- 작업 중단 후 재개·중복 실행·결과 순서 보장
- 사용량과 비용 상한을 넘은 작업의 자동 차단
- 단일 인스턴스 교체 중 작업 유실 방지

따라서 3차 확장 구현 전에 `동기 관리자 요청 → 짧은 확인`과 `비동기 추출·계산 작업 → 관리자 검수`를 분리하고, 작업 저장·claim·재시도·멱등성·실패 보관·관측 지표를 계약으로 정해야 한다. 단일 EC2에서 계속 처리할 수 있는지 여부는 예상 작업량과 메모리·CPU·외부 호출 제한을 측정한 뒤 결정한다.

## 9. 2차 확장 미완료 성능 검증

### 9.1. 미측정 항목

| 항목 | 현재 상태 | 필요한 증거 |
|---|---|---|
| 정상 부하 | 동시 사용자 50명·20 RPS, 미측정 | `GET /api/restaurants/popular`, 공개 큐레이션 목록·상세의 p95 500ms 이하와 서버 오류율 1% 미만 |
| 최대 부하 | 동시 사용자 200명·80 RPS, 시나리오 미구현·미측정 | 최대 부하 시나리오, 같은 기준 데이터·환경에서 p95·오류율·자원 사용량 판정 |
| 환경 비교 | 2차 확장 실제 운영 단일 EC2 실측 없음 | 운영 동급 단일 EC2 기준 또는 배포 고도화 전환 시 비교 기준 명시 |

정상 부하 시나리오와 기준 데이터는 [2차 확장 성능 검증 결과](second-expansion-performance-verification.md)와 [ADR-PERF-001](../07-adr/quality/perf-001-k6-load-testing.md)에 준비되어 있다. 단, `perf/seed/02-restaurant.sql`의 좌표는 모두 null이므로 3차 확장 좌표·경로 성능 측정에는 그대로 사용할 수 없다.

### 9.2. 3차 확장 완료 게이트 승계 권고

3차 확장 최종 완료 전에 다음을 모두 통과시키는 것을 권고한다.

1. 2차 확장의 정상 부하 50명·20 RPS를 측정하고 p95·오류율을 판정한다.
2. 2차 확장의 최대 부하 200명·80 RPS 시나리오를 작성하고 동일한 기준으로 측정한다.
3. 두 측정을 어떤 환경에서 수행했는지 기록한다. 배포 고도화가 먼저 진행되면 단일 EC2 기준과 새 토폴로지 기준을 분리한다.
4. 기준 미달이면 인기·큐레이션 쿼리, DB 인덱스·집계 방식, 캐시 또는 배포 토폴로지의 조치와 재측정 결과를 기록한다.

이 권고는 2차 확장 성능 요구사항을 없애거나 완화하지 않는다. 3차 확장 기능의 완료 여부와 별개로, 측정 전에는 2차 성능 요구사항을 충족했다고 보고하지 않는다.

## 11. 다음 문서화 순서

선행 상태 검토 이후에는 다음 순서로 진행한다.

1. 승인된 3차 확장 범위·용어를 요구사항·PRD의 포함·제외 경계에 연결한다.
2. 자연어 검색과 AI 추출의 요구사항·PRD에서 검색 결과 근거, 관리자 검수, 개인정보·비용 상한을 정의한다.
3. 동선·코스 추천의 데이터 입력과 Kakao Mobility 호출·캐시·실패 경계를 별도 PRD와 ADR 후보로 만든다.
4. 승인된 기능만 Workstream·도메인 경계·API·데이터 계약으로 확장한다.
5. 2차 성능 측정과 좌표 보강률 조회 결과를 각 계약과 구현 Task에 연결한다.

## 12. 결론

3차 확장 초기 범위·용어와 상세 정책 계약은 승인됐다. 1·2차 확장 기능과 기본 운영 토폴로지는 존재하지만, 운영 좌표 보강률·외부 계정 quota 연결·물리 migration·범용 비동기 수용량·성능 결과는 아직 실행 증거가 필요하다.

특히 2차 확장의 정상 부하 50명·20 RPS와 최대 부하 200명·80 RPS가 미측정이므로, 이를 3차 확장 최종 완료 게이트로 승계해 측정·판정·조치 결과를 남기는 것이 현재 기준선에 맞다.
