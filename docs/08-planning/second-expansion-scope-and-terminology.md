# 맛잇온 2차 확장 범위와 용어 결정

## 1. 목적

이 문서는 [2차 확장 선행 상태 검토](second-expansion-baseline-review.md) 다음 단계로 컬렉션, 인기 맛집, 큐레이션, 제보, 신고, 사용자 알림의 의미와 초기 제공 경계를 확정한다. 기존 [프로젝트 범위](../00-overview/scope.md)는 이 기능들을 2차 확장 후보로만 분류하므로, 이 결정만으로 세부 요구사항·PRD·API·데이터 계약이 확정되지는 않는다.

결정 상태는 다음과 같이 구분한다.

- **결정**: 2차 확장 요구사항·PRD·API·데이터 계약을 작성할 때 지켜야 하는 승인된 범위다.
- **초기 제외**: 초기 범위의 복잡도를 제한하기 위해 같은 단계에서 제공하지 않기로 승인한 범위다.

## 2. 범위 요약

| 기능 | 초기 범위 | 초기 제외 | 남은 결정 |
|---|---|---|---|
| 개인 컬렉션 | **결정** — 회원이 공개 맛집을 비공개 개인 폴더로 분류 | 공개 공유, 메모·태그·대표 이미지, 직접 정렬 | 없음 |
| 인기 맛집 | **결정** — 현재 찜 관계 수를 이용한 전체 기간 상위 20개 | 상세·최근 조회를 조회수로 해석, 기간별 급상승, 추천 점수 | 없음 |
| 큐레이션 | **결정** — 관리자가 직접 편집하고 게시하는 공개 콘텐츠 | 자동 추천 알고리즘, 개인화 추천, 예약 게시 | 없음 |
| 제보 | **결정** — 회원의 신규 맛집·유튜버·영상·방문 관계 제안 | 사용자의 직접 등록·수정 권한, 첨부 파일 | 없음 |
| 신고 | **결정** — 회원의 기존 정보 오류·폐업·잘못된 연결·부적절 콘텐츠 보고 | 리뷰·평점, 회원 제재 체계, 자동 비공개 | 없음 |
| 사용자 알림 | **결정** — 서비스 내 알림으로 제보·신고 처리 상태와 결과 전달 | 이메일·웹 푸시·FCM, 실시간 전송, 마케팅·추천 알림 | 없음 |

## 3. 컬렉션

### 3.1 용어

**개인 컬렉션**은 로그인 회원이 다시 찾을 공개 맛집을 목적별로 묶는 회원 소유의 개인 폴더다. 1차 확장의 찜은 단일 관계이며, 개인 컬렉션은 이름을 가진 복수 목록이라는 점에서 별도 기능이다.

**관리자 큐레이션**은 운영자가 전체 사용자에게 공개하는 편집 콘텐츠다. 소유자, 공개 범위, 생명주기와 운영 권한이 다르므로 개인 컬렉션과 같은 도메인 모델이나 API를 공유하지 않는다.

### 3.2 초기 범위

2026-08-03 다음 범위를 승인했다.

- 로그인 회원만 자신의 컬렉션을 생성·이름 변경·삭제·조회한다.
- 컬렉션은 초기에는 비공개이며 다른 사용자에게 공유하거나 검색 노출하지 않는다.
- 공개·활성 맛집만 새 항목으로 추가할 수 있고, 비공개 전환된 맛집은 개인 목록에서 숨긴다.
- 같은 컬렉션 안의 같은 맛집은 한 번만 존재한다.
- 한 맛집은 회원이 소유한 여러 컬렉션에 포함할 수 있다.
- 컬렉션 삭제는 컬렉션과 포함 관계만 삭제하며 맛집이나 찜 관계를 변경하지 않는다.
- 회원 탈퇴 시 회원의 컬렉션과 포함 관계를 삭제한다.
- 컬렉션 목록은 최근 수정순, 컬렉션 안 맛집은 추가 최신순으로 정렬한다.
- 회원은 최대 20개 컬렉션을 만들고, 컬렉션 하나에는 맛집을 최대 100개까지 포함할 수 있다.

### 3.3 초기 제외

- 다른 사용자에게 공개하거나 링크로 공유하는 기능
- 공동 편집과 팔로우
- 항목별 메모·태그
- 대표 이미지 업로드
- 개인 컬렉션을 관리자 큐레이션으로 전환하는 기능
- 컬렉션과 컬렉션 안 맛집의 직접 순서 편집

### 3.4 결정 근거

- 비공개 개인 폴더로 제한해 공유·검색·공동 편집·공개 콘텐츠 신고 정책을 초기 범위에 추가하지 않는다.
- 같은 맛집을 여러 목적의 컬렉션에 둘 수 있게 하되 같은 컬렉션 안에서는 중복을 금지한다.
- 최근 수정순과 추가 최신순을 사용해 직접 재정렬을 위한 순번 열·재정렬 API·동시성 규칙을 만들지 않는다.
- 회원당 20개, 컬렉션당 맛집 100개를 초기 상한으로 두어 오남용을 제한하고 화면에서 관리 가능한 범위를 유지한다.

## 4. 인기 맛집

### 4.1 용어

**인기 맛집**은 승인된 사용자 행동 신호를 정해진 집계 규칙으로 계산해 전체 사용자에게 노출하는 공개 맛집 순위다. 관리자 편집 결과인 큐레이션이나 개인 취향을 예측하는 추천과 구분한다.

### 4.2 초기 범위

2026-08-03 다음 범위를 승인했다.

- 인기 신호는 현재 유지 중인 `favorite` 관계 수 하나만 사용한다.
- 전체 기간의 현재 찜 수를 내림차순으로 정렬한다.
- 찜 수가 같으면 `restaurant.id` 오름차순으로 안정 정렬한다.
- 공개·활성 맛집만 결과에 포함한다.
- 회원·맛집 복합 기본키로 동일 회원의 중복 찜을 한 건으로 제한한다.
- 로그인하지 않은 사용자는 찜을 만들 수 없으므로 비로그인 조회는 인기 신호에 포함하지 않는다.
- 찜이 한 건 이상인 맛집 중 상위 20개만 반환하고 별도 페이지는 제공하지 않는다.
- 초기에는 요청 시 PostgreSQL에서 실시간 집계하며 찜·찜 해제·탈퇴와 맛집 공개 상태 변경을 다음 요청부터 반영한다.

이 범위는 엄밀히는 “현재 많이 찜한 맛집”을 의미한다. 화면과 API가 단순히 `조회수 인기`나 `최근 급상승`으로 표현하지 않도록 지표 설명을 함께 제공한다.

### 4.3 초기 제외

- `recent_restaurant_view`를 상세 조회 횟수로 해석하지 않는다. 이 테이블은 회원·맛집별 최신 한 건이며 최신 50건 상한과 30일 정리가 적용된다.
- 반복 상세 조회, 비로그인 조회, IP·기기별 조회 이벤트를 수집하지 않는다.
- 찜·조회에 임의 가중치를 둔 복합 점수나 추천 알고리즘을 사용하지 않는다.
- 최근 7일·30일 급상승 순위를 제공하지 않는다. 현재 데이터는 찜 해제 이력과 조회 이벤트 이력을 보존하지 않아 기간별 행동량을 정확히 재현할 수 없다.

### 4.4 결정 근거

- 현재 스키마가 정확히 표현하는 행동은 유지 중인 찜 관계이므로 다른 행동 신호를 섞지 않는다.
- 전체 기간 현재 찜 수로 정의해 보존하지 않는 찜 해제 이력이나 조회 이벤트를 요구하지 않는다.
- 찜이 0개인 맛집을 제외하고 상위 20개만 반환해 인기 목록의 의미를 유지하고 별도 페이지 계약을 만들지 않는다.
- 초기 트래픽에서는 실시간 집계로 시작해 배치·캐시·Snapshot의 무효화와 운영 작업을 추가하지 않는다. 성능 기준을 충족하지 못한다는 측정이 있을 때 집계 방식을 재검토한다.

최근 순위나 조회 기반 순위를 추가하려면 행동 이벤트, 보존 기간, 비회원 식별 최소화, 중복·자동화 요청 제한과 집계 조작 대응을 별도 계약으로 먼저 승인한다.

## 5. 큐레이션

### 5.1 용어

**관리자 큐레이션**은 관리자가 주제와 설명을 작성하고 공개 맛집을 골라 순서를 편집한 뒤 전체 사용자에게 게시하는 콘텐츠다. 인기 집계나 추천 알고리즘이 자동으로 항목을 선택하지 않는다.

### 5.2 초기 범위

2026-08-03 다음 범위를 승인했다.

- 관리자 인증을 통과한 운영자만 큐레이션을 생성·수정·게시·게시 중단한다.
- 제목, 설명, 포함 맛집과 표시 순서를 관리자가 직접 편집한다.
- 공개·활성 맛집만 게시 결과에 노출한다.
- 게시 전 초안과 게시 중 상태를 구분한다.
- 메인 화면에는 게시 중인 큐레이션만 관리자가 정한 순서로 노출한다.
- 개인 컬렉션과 데이터 구조·API·권한을 공유하지 않는다.
- 메인 화면에는 큐레이션을 최대 5개까지 동시에 노출한다.
- 큐레이션 하나에는 맛집을 최대 20개까지 포함한다.
- 큐레이션과 포함 맛집의 표시 순서는 관리자가 직접 지정한다.
- 게시 중인 큐레이션의 수정은 저장 성공 뒤 사용자 화면에 즉시 반영한다.
- 포함 맛집이 비공개 또는 삭제 상태가 되면 사용자 화면에서 자동 제외하고 관리자 화면에 구성 불일치 경고를 표시한다.

### 5.3 초기 제외

- 자동 추천·개인화 추천 알고리즘
- 인기 순위의 자동 큐레이션 편입
- 공개 시작·종료 예약
- 사용자 구독과 이메일 발송

### 5.4 결정 근거

- 관리자 수동 편집으로 제한해 인기 집계·추천 알고리즘과 큐레이션의 책임을 분리한다.
- 메인 최대 5개, 큐레이션당 맛집 최대 20개로 초기 화면과 관리 작업량을 제한한다.
- 관리자가 표시 순서를 직접 정해 편집 콘텐츠의 의도를 보존한다.
- 별도 버전 발행 모델 없이 게시 중 수정을 즉시 반영해 초기 상태 전이와 API를 단순화한다.
- 비공개·삭제 맛집은 공개 경계를 우선해 자동 제외하되, 관리자가 누락을 인지하고 구성을 정정할 수 있도록 경고한다.

## 6. 제보와 신고

### 6.1 용어 분리

**제보**는 아직 서비스에 없거나 연결되지 않은 정보를 추가해 달라는 회원의 제안이다.

- 신규 맛집
- 신규 유튜버
- 신규 영상
- 기존 맛집·유튜버·영상을 잇는 방문 관계

**신고**는 이미 서비스에 공개된 정보의 오류나 운영 문제를 알리는 회원의 보고다.

- 잘못된 이름·주소·설명 등 정보 오류
- 폐업 또는 이용 불가
- 잘못 연결된 영상·유튜버·방문 관계
- 부적절하거나 정책에 맞지 않는 콘텐츠

제보와 신고는 대상, 검증 기준과 승인 결과가 다르므로 하나의 외부 용어나 단일 생성 API로 합치지 않는다. 다만 관리자 처리 화면의 공통 상태와 감사 필드는 공유 가능한지 후속 데이터 설계에서 검토할 수 있다.

### 6.2 공통 상태 흐름

```text
RECEIVED(접수) → IN_REVIEW(검토 중) → ACCEPTED(승인) → COMPLETED(처리 완료)
                                  └→ REJECTED(반려)
```

- `RECEIVED`: 회원 요청이 저장됐지만 관리자가 검토를 시작하지 않은 상태
- `IN_REVIEW`: 관리자가 근거와 중복 여부를 확인 중인 상태
- `ACCEPTED`: 요청의 타당성을 승인했지만 실제 데이터 반영이 끝나지 않은 상태
- `COMPLETED`: 승인된 변경 또는 등록이 반영된 종료 상태
- `REJECTED`: 반려 사유를 기록하고 종료한 상태

`REJECTED`는 종료 상태이므로 다시 `COMPLETED`로 전환하지 않는다. 승인과 실제 데이터 반영이 하나의 원자 작업이라면 후속 계약에서 `ACCEPTED`를 생략할 수 있지만, 상태 의미를 정하지 않은 채 두 상태를 같은 뜻으로 사용하지 않는다.

### 6.3 공통 초기 범위

2026-08-03 다음 범위를 승인했다.

- 로그인 회원만 제보·신고를 접수하고 자신의 처리 상태와 결과를 조회한다.
- 제보와 신고는 별도 데이터 모델과 API로 분리한다.
- 제보 대상은 신규 맛집·유튜버·영상·방문 관계로 제한한다.
- 신고 대상은 기존 맛집·유튜버·영상·방문 관계로 제한한다.
- 접수 정보는 설명과 근거 URL만 지원하고 첨부 파일은 받지 않는다.
- 관리자는 접수 목록을 조회하고 검토 상태·결과·회원에게 공개할 사유를 기록한다.
- 승인된 제보가 기존 관리자 등록 검증을 우회해 곧바로 공개 데이터를 만들지 않도록 한다.
- 신고 접수만으로 기존 콘텐츠를 자동 비공개 처리하지 않는다.
- 긴급 비공개가 필요하면 관리자가 근거를 확인하고 수동으로 결정한다.
- 같은 회원·대상·요청 유형의 미종결 요청은 중복 생성하지 않고 기존 요청을 안내한다.
- 회원별 제보·신고 접수는 두 기능을 합해 하루 최대 5건으로 제한한다.
- 반려·처리 완료 사유는 접수 회원에게 공개한다.
- 종료된 요청은 1년간 보관한 뒤 회원 식별 정보를 삭제한다.
- 모든 상태 전환은 처리 관리자와 시각을 감사 가능한 형태로 남긴다.
- 관리자 담당자 배정은 초기 범위에 포함하지 않는다.

### 6.4 결정 근거

- 제보와 신고는 대상 존재 여부와 처리 결과가 다르므로 외부 계약과 저장 모델을 분리한다.
- 첨부 파일을 제외해 파일 보안 검사·저장소·수명주기 범위를 추가하지 않는다.
- 같은 회원·대상·유형의 미종결 요청을 하나로 제한하고 하루 합계 5건 상한을 적용해 단순 반복 접수를 줄인다.
- 신고만으로 자동 비공개하지 않아 검증된 공개 데이터가 미확인 요청으로 즉시 사라지는 것을 막는다.
- 승인된 제보도 기존 관리자 검증 절차를 통과시켜 공개 데이터의 품질 경계를 유지한다.
- 종료 후 1년 동안 처리 근거와 분쟁 대응 이력을 유지한 뒤 회원 식별 정보를 삭제해 장기 개인정보 보관을 제한한다.

## 7. 알림

### 7.1 용어 분리

**운영 알림**은 시스템 장애와 운영 이상을 담당자에게 전달하는 CloudWatch→Slack 흐름이다. 기존 M2 운영 계약을 유지하며 2차 확장의 회원 기능으로 취급하지 않는다.

**사용자 알림**은 회원 본인의 제보·신고 처리 결과처럼 서비스 이용 상태 변화를 해당 회원에게 전달하는 제품 기능이다.

회원 가입 인증·비밀번호 재설정 메일은 보안 Action Token 전달이며, 일반 사용자 알림 채널이나 알림함으로 재분류하지 않는다.

### 7.2 초기 범위

2026-08-03 다음 범위를 승인했다.

- 사용자 알림은 서비스 내 알림함 한 채널로 시작한다.
- 1차 이벤트는 제보·신고의 검토 시작, 승인, 반려와 처리 완료다.
- 알림은 수신 회원, 유형, 제목·본문에 필요한 결과 Snapshot, 생성 시각과 읽음 시각을 가진다.
- 회원은 자신의 알림만 조회하고 읽음 처리할 수 있다.
- 개별 읽음과 전체 읽음을 지원한다.
- 같은 요청·상태 전환의 알림은 한 건만 생성한다.
- 제보·신고 처리 상태 변경과 알림 저장은 같은 데이터베이스 트랜잭션에서 수행한다.
- 알림은 생성 후 90일 또는 회원별 최근 200개 중 먼저 도달한 기준까지만 보관한다.
- 미읽음 개수는 데이터베이스에서 정확히 조회하고 화면에는 `99+`까지 표시한다.
- 실시간 전송 없이 알림 화면 진입·새로고침과 일반 화면 재조회 시 갱신한다.
- 제보·신고 처리 알림은 회원이 요청한 서비스 처리 결과이므로 별도 수신 동의·해지 대상에서 제외한다.
- 회원 탈퇴 시 알림과 회원 식별 연결을 삭제한다.

### 7.3 초기 제외

- 이메일, 웹 푸시와 FCM 동시 제공
- 마케팅·추천·인기 맛집 홍보 알림
- 실시간 전송 보장을 위한 WebSocket·SSE
- 기존 회원 Action 메일 Outbox의 재사용

서비스 내 알림은 데이터베이스 기록과 다음 조회 시 표시로 시작할 수 있어 외부 푸시 전달을 위한 FCM·기기 Token·범용 메시지 브로커를 요구하지 않는다. 푸시가 제품 요구사항으로 승인될 때만 [ADR-NOTIFY-001](../07-adr/adr-backlog.md#adr-notify-001-fcm-푸시-알림)을 활성화한다.

### 7.4 결정 근거

- 서비스 내 알림은 처리 상태와 같은 데이터베이스 트랜잭션에서 저장해 외부 전송 실패와 범용 비동기 Worker를 추가하지 않는다.
- 요청·상태별 고유성으로 같은 전환의 중복 알림을 막는다.
- 90일·최근 200개 상한으로 처리 결과 확인 기간을 제공하면서 회원별 데이터가 무제한 증가하지 않게 한다.
- 화면 조회 시 정확한 미읽음 수를 계산하고 `99+`로 표시해 별도 실시간 카운터·푸시 동기화를 만들지 않는다.
- 회원이 시작한 제보·신고 처리 결과는 서비스 수행에 필요한 고지로 한정하고 마케팅·추천 알림을 섞지 않으므로 별도 수신 해지를 제공하지 않는다.
