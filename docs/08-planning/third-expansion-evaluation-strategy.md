# 맛잇온 3차 확장 평가 주도 개발 전략

## 1. 목적과 결정 상태

이 문서는 자연어 맛집 탐색, AI 영상 정보 추출과 맛집 코스 추천에 평가 주도 개발(Eval-driven Development, EDD)을 적용하는 기준을 정의한다. 구현 뒤 품질을 확인하는 일회성 시험이 아니라, 관찰한 실패를 평가 데이터와 평가기로 고정하고 변경 전후에 반복 실행해 출시·활성화·롤백을 결정하는 절차를 만든다.

이 문서는 `approved`다. [NFR-ACCURACY-001](../01-requirements/non-functional-requirements.md#nfr-accuracy-001-자연어-검색-정확도와-평가-데이터)과 [NFR-ACCURACY-002](../01-requirements/non-functional-requirements.md#nfr-accuracy-002-ai-추출-정확도재현율자동-등록-정밀도)의 목표·데이터 분할·판정 책임을 2026-08-10 확정했다. `QUALITY-EVAL` 최종 책임자는 박진영, 기본 리뷰어는 이우람으로 배정했으며 기능별 정답·검증 책임은 [3차 확장 Workstream](../02-analysis/third-expansion-workstreams.md#8-quality-eval-교차-품질-트랙)을 따른다.

이 전략은 일반 자동화 테스트를 대체하지 않는다. 결정론적 API·상태·트랜잭션·보안·외부 장애는 기존 테스트 전략으로 검증하고, 확률적이거나 사람의 판단이 필요한 품질 차원에 고정 평가 데이터·평가기·판정 절차를 추가한다.

## 2. 적용 원칙

1. **목표와 게이트를 먼저 정의한다.** 구현·모델·Prompt 변경 전에 평가 대상, 실패 조건과 출시 차단 조건을 명시한다.
2. **실제 관찰한 오류를 평가에 반영한다.** 추상적인 종합 점수보다 오해석·오연결·근거 없음·부분 추출처럼 제품에서 발생한 실패 유형을 고정한다.
3. **평가기 하나는 품질 차원 하나만 판정한다.** 모든 결과를 하나의 점수로 합치는 종합 평가기는 두지 않는다.
4. **프로그램 검사를 우선한다.** Schema, 조건 집합, 상태 전이, 중복, 공개 경계처럼 코드로 판정 가능한 항목에 LLM 심판을 사용하지 않는다.
5. **인간은 평가와 예외 환류를 담당한다.** 정답 자체에 의견 차이가 있거나 장소·방문 사실의 위험이 큰 사례는 지정 판정자가 종결하지만, 운영 정식 등록은 자동 검증 게이트로 판정한다.
6. **좋은 사례와 나쁜 사례를 함께 둔다.** 평가 데이터에는 정상뿐 아니라 모호·충돌·근거 없음·악성·외부 실패 사례를 포함한다.
7. **시스템 전체를 평가한다.** 모델 출력뿐 아니라 정규화, 외부 검증, 상태 전이, 자동 등록·공개와 롤백 경계를 함께 본다.
8. **개인정보·저작권·비용 경계를 평가보다 우선한다.** 평가 목적이라도 승인되지 않은 원문 저장·외부 전송·유료 호출을 허용하지 않는다.

참고 방법론은 [Airbnb의 Eval-driven development](https://medium.com/airbnb-engineering/eval-driven-development-lessons-from-evaluating-genai-at-scale-e817e5ae5788)다. 다만 운영 트래픽 표본 수집과 LLM 심판은 맛잇온의 개인정보·비용 계약에 맞게 축소 적용한다.

코스 추천은 AI 생성 품질이 아니라 결정론적 입력·외부 경로 계약 문제다. LLM 심판과 통계적 종합 점수를 사용하지 않고 계약·경계·장애·성능 증거로 판정한다.

### 3.4. 공통 평가

- Prompt Injection·Schema 이탈·과대 입력이 코드·명령·외부 호출을 임의 실행하지 않는지 검사한다.
- 자연어 원문, 전체 자막·전사, 근거 본문, Prompt 전문, AI 응답 본문과 외부 인증정보가 일반 로그에 없는지 검사한다.
- AI·Mobility 비용·quota hard stop과 기존 탐색·상세·수동 등록 장애 격리를 검사한다.
- 정상 50명·20 RPS와 최대 200명·80 RPS의 성능·자원 사용량을 최종 완료 증거에 포함한다.

## 4. 골든 데이터 구성

### 4.1. 공통 원칙

- 데이터셋은 기능별로 분리하고 불변 버전으로 관리한다.
- 각 버전은 Dataset ID, 생성일, 범위, 사례 수, 정답 Schema 버전, 작성자 역할, 검증자 역할, 출처·이용 조건, 민감정보 검사 결과와 변경 내역을 가진다.
- 사례 ID는 버전이 바뀌어도 같은 원천 사례를 추적할 수 있게 유지한다. 정답 또는 입력 의미가 바뀌면 변경 이유를 기록한다.
- 중복·거의 같은 표현·같은 영상의 재편집본은 같은 그룹으로 표시하고 서로 다른 분할에 흩어지지 않게 한다.
- 정상 사례만으로 구성하지 않고 빈 결과·모호·충돌·누락·악성·부분·외부 실패 사례를 포함한다.
- 정답과 평가 데이터의 변경은 구현 변경과 구분해 리뷰하며, 목표를 맞추기 위해 실패 사례를 삭제하지 않는다.

### 4.2. 버전 규칙

논리적 Dataset ID는 다음 형식을 사용한다.

```text
nlsearch-golden-v{major}.{minor}.{patch}
aiextract-golden-v{major}.{minor}.{patch}
course-fixture-v{major}.{minor}.{patch}
```

- `major`: 정답 Schema·지원 범위·판정 의미 변경
- `minor`: 새 실패 유형·사례 추가
- `patch`: 의미를 바꾸지 않는 오탈자·메타데이터 수정

평가 보고서는 Dataset ID와 함께 자연어 규칙·parserVersion, AI 모델·Prompt·Schema 버전, 애플리케이션 커밋 식별자를 기록해야 한다.

### 4.3. 분할

모든 기능은 다음 분할을 사용한다. 동일 영상·같은 식당·문장 변형 그룹은 하나의 분할에만 둔다.

| 분할 | 비율 | 용도 | 사용 제한 |
|---|---:|---|---|
| Development | 60% | 오류 탐색, 규칙·Prompt 개선 | 반복 열람·실행 가능 |
| Calibration | 20% | 임계값·평가기·LLM 심판 보정 | 후보 선택 최종 근거로 단독 사용 금지 |
| Release holdout | 20% | 활성화·출시 최종 판정 | 변경 튜닝에 사용 금지, 판정 시에만 실행 |

동일 영상·같은 식당·문장 변형 그룹은 하나의 분할에만 둔다. Dataset major 버전이 바뀌지 않는 한 Release holdout 실패 사례를 Development로 옮기지 않는다. 운영에서 새로 발견한 실패는 다음 minor 버전의 Development에 먼저 추가하고, 독립 변형 사례를 다음 holdout에 추가한다.

### 4.4. 기능별 데이터

#### 자연어 검색

자연어 Dataset은 중복 제거 문장 240건으로 고정하고 Development 144건·Calibration 48건·Release holdout 48건으로 나눈다. 각 사례는 다음을 가진다.

- 자연어 문장과 직접 지정 필터·기대 태그 조건
- 기대 적용 조건, 태그 코드·태그 AND 결과, 직접 필터 때문에 제외할 조건과 미지원 표현
- 기대 결과 상태 `RESULT`, `EMPTY`, `UNPARSED`, `PARTIAL_UNSUPPORTED`
- 사용 표현 유형과 난이도, 동의어·오타·충돌·악성 여부
- 정답 작성·검증·판정 기록

개인정보가 없는 팀 작성 문장, 승인된 합성 문장과 공개 서비스 어휘만 사용한다. 운영 사용자 원문은 기본적으로 편입하지 않는다.

#### AI 영상 정보 추출

AI Dataset은 중복 영상 그룹을 제거한 입력 120건으로 고정하고 Development 72건·Calibration 24건·Release holdout 24건으로 나눈다. 각 사례는 다음을 가진다.

- 이용이 허용된 입력 Fixture 식별자와 원천·이용 조건
- 기대 맛집명·주소·메뉴·방문 여부 또는 `UNKNOWN`
- 후보를 뒷받침하는 최소 근거 구간과 근거 없음 판정
- 기대 결과 완전성 `COMPLETE` 또는 `PARTIAL`
- 동명 장소·허위 주소·간접 언급·미방문·복수 장소·Prompt Injection 표식
- Kakao·YouTube·Visit 검증 기대 결과
- 허용 태그 후보·근거 구간·자동 결정(`AUTO_ACCEPT/AUTO_REJECT/AUTO_MERGE`)과 최종 `VisitTag` 공개 여부
- 정답 작성·교차 검증·최종 판정 기록

YouTube 원본 영상과 전체 자막·전사를 저장소 Fixture나 운영 DB로 복제하지 않는다. 팀 작성 합성 입력과 Dataset manifest·정답·해시·라벨은 접근 통제된 private evaluation store에 저장하고 1년 뒤 삭제한다. 사용 허가된 외부 자산은 평가 실행 중에만 최소 접근하며, 내려받은 원본은 실행 종료 후 삭제한다. 일반 로그에는 URL·자막·응답 전문을 남기지 않는다.

#### 코스 추천

코스는 골든 자연어가 아니라 결정론적 Fixture 60건으로 관리하고 Development 36건·Calibration 12건·Release holdout 12건으로 나눈다. 다음 경계를 모두 포함해야 한다.

- 1·2·5·6개, 중복, 첫 출발점 변경
- 좌표 없음·비공개·삭제 맛집
- 30km 경계 이하·동일·초과
- 정상·timeout·429·5xx·부분 구간 실패·quota 차단
- 만료 직전·동일·직후
- 동일 조합 재조회와 호출 수 상한

## 5. 정답 작성과 충돌 판정

### 5.1. 필수 역할

| 역할 | 책임 | 현재 상태 |
|---|---|---|
| 평가 전략 책임자 | Dataset·평가기·보고서·게이트 변경 조율 | 박진영 |
| 자연어 정답 책임자 | 지원 조건과 사용자 표현의 기대 해석 승인 | 양성훈, 검증 이우람 |
| AI 도메인 정답 책임자 | 장소·주소·방문 근거·`UNKNOWN` 정답 승인 | 김인안, 검증 이우람·박진영 |
| 예외 보정 책임자 | 자동 차단·롤백·사후 보정 가능성·사유 검토 | 김인안, 검증 박진영 |
| Mobility 계약 책임자 | 코스 입력·외부 결과·장애 Fixture 승인 | 이우람, 검증 양성훈 |
| 최종 판정자 | 정답·임계값·출시 의견 충돌 종결 | 박진영, 범위·비용 변경은 팀 승인 |

한 사람이 여러 역할을 맡을 수 있지만 자신의 구현 결과만으로 정답과 출시를 단독 승인하지 않는다. 역할의 실명·Workstream·기본 리뷰어는 [3차 확장 Workstream과 소유권](../02-analysis/third-expansion-workstreams.md)에서 확정하며, 대리자 변경은 해당 문서의 변경 규칙을 따른다.

### 5.2. 정답 작성 절차

1. 정답 작성자가 입력과 정답, 근거, 불확실성 사유를 기록한다.
2. 검증자가 입력 출처를 확인하고 정답을 독립 검토한다.
3. 환각·오연결·검수 우회 같은 Critical 사례는 100% 교차 검토한다.
4. 그 외 사례의 교차 검토 비율은 20%로 고정한다.
5. 불일치는 합의 과정과 선택지를 기록하고 최종 판정자가 종결한다.
6. 사람이 일관되게 합의할 수 없는 사례는 자동 평가 대상에서 제외하지 않고 `AMBIGUOUS`로 분류해 제품 정책 결정 목록으로 보낸다.

정답 충돌이 해결되기 전에는 해당 사례로 모델·Prompt 또는 규칙의 우열을 판정하지 않는다.

## 6. 평가 방법의 사용 경계

### 6.1. 프로그램 평가

다음은 프로그램 평가가 유일한 기본 판정 방식이다.

- JSON·결과 Schema, 필수 필드, Enum과 버전
- 자연어 조건 집합·재현율·미지원 오적용
- 직접 필터 우선과 공개·생명주기
- AI 중복 키·상태 전이·재시도·정식 저장 0건
- 코스 개수·좌표·30km·TTL·호출 수
- timeout·429·5xx·quota와 비용 차단
- 로그 금지 데이터와 권한 경계

### 6.2. 인간 평가

사람은 다음 항목을 판정한다.

- 자연어 표현의 정답 자체가 모호한 경우
- AI 후보와 근거 구간의 의미적 충실성
- 동명 장소·간접 방문·복수 장소의 사실 판단
- 자동 차단·예외 보정 화면의 보완 가능성과 확정 불가 이유
- 자동 평가기와 정답의 불일치

인간 판정은 정답, 판정자 역할, 사유와 시각을 기록한다. 모델 이름이나 기존 점수는 가능하면 정답 판정 전에 숨겨 선호 편향을 줄인다.

### 6.3. LLM 심판

LLM 심판은 3차 확장에서는 비활성으로 확정한다. 유료 호출·외부 전송·사람 판정 대체를 하지 않으며, 필요하면 별도 범위·비용·개인정보·평가기 승인과 ADR을 먼저 만든다.

LLM 심판 결과는 품질 증거나 출시 게이트로 사용할 수 없다.

## 7. 품질 목표 확정 절차

[RV-NFR-017](../01-requirements/requirements-review.md#rv-nfr-017-자연어ai-품질-목표값)의 확정 목표는 다음 절차로 검증한다.

1. Dataset manifest와 Development·Calibration·Release holdout 분할을 승인한다.
2. 기준선 규칙 또는 모델·Prompt·Schema 버전을 고정한다.
3. Development 결과와 실행 상태를 사람이 읽고 오류 유형을 분류한다.
4. 각 오류 유형을 하나의 평가 차원과 평가기에 연결한다.
5. Calibration에서 평가기와 임계값을 조정한다.
6. Release holdout에서 초기 목표를 측정하고 Critical 실패를 별도 집계한다.
7. 목표가 지나치게 낮거나 달성 불가능하면 수치를 숨기거나 사례를 제거하지 않고 실패 분포·사용자 위험·관리자 작업량과 비용을 근거로 조정안을 작성한다.
8. 제품 책임자, 도메인 책임자, 평가 전략 책임자와 최종 판정자가 목표값을 승인한다.
9. 승인 결과를 NFR·요구사항 검토 결과·PRD 완료 조건·테스트 매트릭스에 함께 반영한다.

평균 점수가 목표를 통과해도 미지원 조건 오적용, 잘못된 장소 연결, 자동 검증 전 정식 저장, 비밀정보 노출과 비용 상한 우회가 한 건이라도 발생하면 출시할 수 없다.

## 9. 활성화와 롤백

### 9.1. 활성화

- 모든 게이트를 통과한 버전만 활성 버전으로 지정한다.
- AI 추출의 새 버전은 이전 후보를 덮어쓰지 않고 새 작업·후보를 만든다.
- 평가 데이터와 평가기만 바뀌어도 활성 버전의 재판정 필요 여부를 기록한다.
- 제공자·모델 자동 failover는 초기 범위에 없으므로 승인되지 않은 대체 모델로 조용히 전환하지 않는다.

### 9.2. 롤백 조건

다음 중 하나가 발생하면 신규 호출을 중지하고 이전 승인 버전 또는 기존 비AI 기능으로 복구한다.

- 잘못된 장소 연결, 자동 검증 전 정식 저장 또는 공개 경계 위반
- Prompt Injection·Schema 이탈로 안전 경계 우회
- 승인 목표 미달 또는 이전 활성 버전 대비 Critical 회귀
- 비용·quota hard stop 우회
- 오류율·지연·단일 EC2 자원 사용량이 승인 운영 한계 초과
- 제공자 보존·리전·계약이 승인 조건에서 변경

롤백은 이미 확정된 정식 Entity를 자동 삭제하거나 이전 후보를 덮어쓰지 않는다. 미종결 작업은 실패 종결하거나 명시적 새 버전으로 재실행하며, 작업·Snapshot·검수 이력은 1년 보존한다.

## 10. 개인정보를 침해하지 않는 운영 실패 환류

### 10.1. 기본 금지

- 자연어 검색 원문을 검색 기록·일반 로그·평가 수집함에 저장하지 않는다.
- 전체 자막·전사, 근거 본문, Prompt 전문과 AI 응답 본문을 일반 로그에 남기지 않는다.
- 운영 입력을 외부 LLM 심판으로 자동 재전송하지 않는다.
- 입력 해시만으로 원문을 복원하거나 사용자를 추적하려 하지 않는다.

### 10.2. 허용하는 관측 정보

- 요청·작업 식별자와 비가역 입력 지문
- 규칙·모델·Prompt·Schema·Dataset 버전
- 적용 조건 종류 수, 미지원·충돌 여부와 결과 상태
- AI 실행·완전성·자동 등록 상태와 정규화된 차단·폐기·보완 사유
- 외부 호출 수·Token·지연·비용과 정규화된 오류 범주
- 코스 입력 개수·좌표 누락 여부·거리 상한·호출 성공 여부

비가역 입력 지문의 알고리즘·비밀 salt 또는 HMAC 키·보존 기간은 보안·데이터 계약에서 정한다. 일반 로그와 관리자 감사 데이터는 분리한다.

### 10.3. 실패 환류 절차

1. 운영 지표에서 실패율·부분 추출·폐기 사유·외부 오류의 증가를 탐지한다.
2. 원문 없이 재현 가능한 합성 사례를 먼저 작성한다.
3. 실제 입력 확인이 꼭 필요하면 기존 관리자 권한과 승인된 보존 범위 안의 후보만 최소 열람한다.
4. 실제 사례를 평가 데이터로 편입할 때 개인정보·저작권·비밀정보를 제거하고 이용 조건을 기록한다.
5. 원문 의미를 보존해야 해 비식별화가 불가능하면 편입하지 않고 별도 개인정보·범위 변경 승인을 요청한다.
6. 새 실패 유형을 Dataset minor 버전과 평가기에 추가하고 이전 활성 버전을 포함해 회귀 평가한다.

일반 사용자의 실검색 원문 표본 수집, 동의 기반 피드백 저장 또는 운영 트래픽 자동 표본 평가는 현재 범위에 없다. 필요하면 개인정보 영향, 동의·철회, 보존·삭제와 접근 권한을 별도 범위 변경으로 승인한다.

```text
Scope
  → FR·BR·NFR
  → PRD 품질·완료 조건
  → Dataset·Evaluator
  → 자동화·인간 평가 결과
  → 모델·Prompt·규칙 활성화 결정
  → 운영 지표·새 실패 유형
  → Dataset·Evaluator 새 버전
```

[3차 확장 테스트 추적표](third-expansion-test-matrix.md)는 `EVAL-NL-*`, `EVAL-AI-*`, `EVAL-COURSE-*`를 `TST-E3-*` 테스트 묶음과 E3 Task에 연결한다. [제품 추적표](../04-product/traceability.md)는 세 PRD의 품질 완료 경로에 이 전략·테스트 매트릭스·실행 결과를 연결한다.

## 13. 문서 완료 조건

- [x] 필수 역할과 최종 판정자를 실명·Workstream에 배정한다.

- [x] 기준선 평가의 목표값을 NFR에 반영하고 Release holdout 실행을 최종 게이트로 둔다.
- [x] 프로그램·인간·LLM 심판의 평가기별 책임과 금지 경계를 승인한다.

- [x] 운영 실패 환류가 원문·자막·비밀정보 로그 금지를 우회하지 않도록 정한다.
