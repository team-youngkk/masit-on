# 배포 고도화 비용·일정 영향 검토

## 1. 이 문서의 근거와 판정 요약

[ADR-DEPLOY-002](../07-adr/platform/deploy-002-validation-deployment-before-expansion.md) 3.1절은 2026-07-28 팀 4인 전원이 배포 고도화 착수 시점을 "3차 확장 이후"로 합의했다고 기록하면서, 같은 절에서 [범위 문서 7절](../00-overview/scope.md#7-범위-변경-절차) 3항(개발 비용·데이터·외부 연동·운영 영향)과 4항(일정 영향)을 아직 수행하지 않았고 **"실제 착수는 위 두 검토를 통과한 뒤에 시작한다"**고 못박았다. 이 문서가 그 두 검토다.

같은 ADR 7절은 검토 결과가 착수를 뒤집을 수 있다고 정한다. "검토 결과 단일 인스턴스 구성이 충분하거나 비용이 예산 목표를 초과하면 착수 시점 합의를 철회한다."

| 검토 항목 | 결과 |
|---|---|
| 3항 비용 영향 | **합의된 목표 구성(ALB + ASG 다중 인스턴스 + Blue-Green)은 월 예산 목표 150,000원을 초과한다.** 상시 2대 구성이 176,900원(118%)이고, ALB 트래픽 가정을 최소로 낮춰도 169,200원(113%)이라 초과가 가정에 의존하지 않는다 |
| 3항 운영 영향 | 다중 인스턴스는 [M2 비용 산정 5.4절](m2-cost-and-sizing.md)이 채택한 **Redis 앱 EC2 동거(R1) 전제를 깨뜨린다.** 공유 Redis를 다시 세우면 비용이 218,800원(146%)까지 올라간다 |
| 4항 일정 영향 | **산정할 수 없다.** 4차 확장 기능 계획 문서가 아직 없어 "4차 이후 기능 일정에 미치는 영향"의 비교 대상이 존재하지 않는다 |

따라서 이 문서는 **합의된 범위 그대로의 착수를 권고하지 않는다.** 8절에서 범위를 좁힌 대안 하나를 제시하고, 판정은 팀에 넘긴다.

## 2. 검토 대상 범위

[ADR-DEPLOY-002](../07-adr/platform/deploy-002-validation-deployment-before-expansion.md) 2.1절이 배포 고도화 단계의 인프라를 "ALB, Blue-Green, 다중 인스턴스"로 정의했다. 세 요소를 분리해 검토한다. 한 덩어리로 두면 비용 초과의 원인이 어디인지 판별할 수 없기 때문이다.

| 요소 | 얻는 것 | 성격 |
|---|---|---|
| ALB | TLS 종단 이관, 대상 그룹 전환, 상태 검사 기반 자동 제외 | Blue-Green과 다중 인스턴스 양쪽의 선행 조건 |
| Blue-Green 배포 | 배포 중 무중단. 구·신 대상 그룹 전환과 즉시 롤백 | 배포 시점에만 두 번째 인스턴스가 필요 |
| ASG 다중 인스턴스 | 인스턴스 장애 시 무중단. [NFR-AVAILABILITY-002](../01-requirements/non-functional-requirements.md#nfr-availability-002-초기-운영-배포-가용성과-수동-복구)의 수동 복구 해소 | 상시 2대 이상이 필요 |

**"무중단 배포"와 "고가용성"은 같은 것이 아니다.** Blue-Green은 배포 중 중단만 없애고, 인스턴스가 죽었을 때의 중단은 ASG 상시 다중화로만 없앤다. 5절에서 보듯 비용 초과의 원인은 거의 전부 후자다.

## 3. 단가

ALB 단가는 이 검토에서 새로 조회했다. AWS 요금 공개 페이지에 서울 리전 표가 없어 AWS Price List API의 리전별 offer 파일(`AWSELB/current/ap-northeast-2`)에서 직접 읽었다.

| 항목 | 단가 | 등급 | 출처 |
|---|---|---|---|
| Application Load Balancer 시간 요금 | `$0.0225/hr` | 확인 | Price List API, 2026-08-17 조회 |
| ALB LCU | `$0.008/LCU-hr` | 확인 | 같음 |
| ACM 공인 인증서 (ALB 연결) | `$0` | 확인 | ALB·CloudFront에 붙이는 공인 인증서는 무료 |
| Route 53 alias 레코드 (ALB 대상) | `$0` | 확인 | AWS 자원 대상 alias 쿼리는 과금하지 않는다 |

나머지 단가는 [M2 인스턴스 사양과 월 비용 산정 6.1절](m2-cost-and-sizing.md)의 값을 그대로 인용한다. **이번 검토에서 재조회하지 않았다.**

| 항목 | 단가 | 인용 위치 |
|---|---|---|
| EC2 t4g.medium | `$0.0416/hr` | M2 비용 산정 6.1절 |
| 퍼블릭 IPv4 (Elastic IP·자동 할당 동일) | `$0.005/hr` | 같음 |
| EBS gp3 | `$0.0912/GB-월` | 같음 |
| 인터페이스 VPC 엔드포인트 | `$0.013/hr` (엔드포인트·AZ당) | 같음 |
| NAT Gateway | `$0.059/hr` + 데이터 처리 | 같음 |

계산 전제도 M2 산정과 맞춘다. **월 730시간, 1 USD = 1,470원, 예산 목표 150,000원 = `$102.04`.** 전제를 바꾸면 M2 산정과 비교할 수 없다.

LCU는 사용량 과금이라 상수가 아니다. 제한 공개 트래픽은 1 LCU(초당 신규 연결 25, 분당 활성 연결 3,000, 시간당 처리 1 GB, 초당 규칙 평가 1,000)에 크게 못 미치므로 **보수적 상한 1 LCU와 현실적 하한 0.1 LCU를 모두 제시한다.**

| 항목 | 월 USD |
|---|---:|
| EC2 t4g.medium 1대 | `$30.37` |
| EBS gp3 30 GiB | `$2.74` |
| Elastic IP 1개 | `$3.65` |
| RDS db.t4g.micro + gp3 20 GiB | `$20.87` |
| Route 53 · ECR · CloudWatch | `$3.70` |
| **합계** | **`$61.32`** (90,100원, 예산의 60%) |

## 6. 비용 외 영향

금액만으로는 드러나지 않고 착수 ADR에서 반드시 결정해야 하는 항목들이다.

### 6.1. 다중 인스턴스는 Redis 동거 전제를 깨뜨린다

[M2 비용 산정 5.4절](m2-cost-and-sizing.md)은 ElastiCache가 Redis 8.8과 AOF `everysec`을 제공하지 못한다는 두 제약 때문에 **Redis를 앱 EC2에 `127.0.0.1:6379`로 동거시켰다.** 그 판단의 근거 중 하나가 "`M2`가 단일 인스턴스 구성을 전제하므로 전용 인스턴스를 따로 두는 이점이 크지 않다"였다.

상시 2대가 되면 이 전제가 사라진다. 인스턴스마다 자기 loopback Redis를 가지므로 `auth:refresh:{adminId}`가 인스턴스별로 갈라지고, 요청이 다른 인스턴스로 가면 Refresh Token을 찾지 못한다. **고가용성을 얻으려고 세션 일관성을 잃는 교환이 된다.**

선택지는 셋이고 셋 다 대가가 있다.

| 선택지 | 대가 |
|---|---|
| 전용 Redis 인스턴스(R2) | 5.3절대로 예산 146% 이상 |
| ElastiCache | Redis 8.8·AOF 강제 규칙 위반. [기술 정책 3절](../06-architecture/technology-policy.md)과 [ADR-DATA-005](../07-adr/data/data-005-redis-refresh-token.md) 10·11절 개정 필요 |
| 앱 인스턴스 1대에 Redis를 두고 나머지가 VPC 내부로 접속 | 그 인스턴스가 죽으면 전체 인증이 죽는다. 다중화의 목적과 정면으로 충돌 |

**H2(상시 1대)에서도 완전히 사라지는 문제는 아니다.** 배포 전환 시 새 인스턴스의 Redis는 비어 있으므로 전환 순간 관리자 세션이 끊긴다. 다만 [ADR-DATA-005 12절](../07-adr/data/data-005-redis-refresh-token.md)이 Redis 장애를 fail-closed로 처리하고 재로그인을 요구하도록 이미 정했으므로, **관리자 재로그인이라는 알려진 결과로 흡수된다.** 공개 조회는 인증을 쓰지 않아 영향이 없다. 이 경우 "무중단"의 범위가 "공개 조회 무중단, 관리자 세션은 재로그인"으로 좁아진다는 사실을 착수 ADR에 명시해야 한다.

### 6.2. 퍼블릭 서브넷이 한 AZ에만 있다

[M2 자원 생성 기록 3절](m2-provisioning-record.md)에 따르면 현재 VPC의 퍼블릭 서브넷은 `ap-northeast-2a` 하나뿐이고, 사설 서브넷만 2a·2c 두 개다(RDS 서브넷 그룹 요구 때문). **ALB는 최소 두 개 AZ의 서브넷을 요구하므로 퍼블릭 서브넷을 하나 더 만들어야 한다.** 서브넷 자체에는 요금이 없어 5절 금액은 바뀌지 않지만 작업 항목이고, 만들면 M2 자원 생성 기록의 네트워크 표를 갱신해야 한다.

### 6.3. 앱 인스턴스를 사설 서브넷으로 옮길 수 없다

ALB를 앞에 두면 인스턴스를 사설 서브넷에 넣는 구성이 자연스럽지만, [M2 비용 산정 6.1절](m2-cost-and-sizing.md)이 확인한 대로 사설 서브넷 인스턴스가 ECR·Parameter Store·CloudWatch에 닿으려면 NAT Gateway(`$43.07`)나 인터페이스 VPC 엔드포인트(`$28.47`)가 필요하다. 예산의 42%·28%다.

따라서 **앱 인스턴스는 퍼블릭 서브넷에 남기고 보안 그룹 인바운드만 ALB 보안 그룹 출처로 좁히는 구성**을 전제로 5절을 계산했다. 퍼블릭 IPv4 요금이 인스턴스 수만큼 계속 붙는 이유가 이것이다.

### 6.4. TLS 종단과 라우팅 경계

현재 HTTPS 종단과 `/internal/**` 차단은 Nginx가 맡는다([ADR-WEB-003](../07-adr/platform/web-003-routing-boundary.md)). ALB로 TLS를 옮기면 ACM 인증서가 무료이고 자동 갱신되어 운영 부담이 줄지만, **경로 라우팅 책임을 ALB가 어디까지 가져갈지는 ADR-DEPLOY-002 3.1절이 이미 "확정하지 않으며 착수 시점의 별도 ADR로 결정한다"고 남겨둔 항목이다.** 이 검토에서 결정하지 않는다.

`/internal/**` 차단은 어느 쪽으로 가든 유지돼야 한다. ALB 리스너 규칙으로 옮기든 Nginx에 남기든, [NFR-AVAILABILITY-001](../01-requirements/non-functional-requirements.md#nfr-availability-001-상태-확인과-장애-구분)의 차단 요구가 전환 도중에도 끊기지 않는지를 착수 시 검증 항목으로 넣어야 한다.

### 6.5. NFR-AVAILABILITY-002 개정 범위

[NFR-AVAILABILITY-002](../01-requirements/non-functional-requirements.md#nfr-availability-002-초기-운영-배포-가용성과-수동-복구)의 적용 대상은 "M2 초기 운영 배포부터 **배포 고도화 전까지**"다. 착수하면 이 요구사항의 목표 기준("단일 EC2 인스턴스와 수동 복구를 유지")을 같은 PR에서 개정해야 한다. H2로 좁혀 착수하는 경우에는 **상시 1대가 유지되므로 이 요구사항을 개정하지 않는다.** 어느 시나리오를 고르느냐에 따라 문서 변경 범위가 달라진다.

## 7. 일정 영향

[범위 문서 7절](../00-overview/scope.md#7-범위-변경-절차) 4항은 "기존 일정 또는 다른 기능에 미치는 영향"을 요구하고, ADR-DEPLOY-002 3.1절은 이를 "고도화 작업이 4차 이후 기능 일정에 미치는 영향"으로 구체화했다.

**이 항목은 지금 완결할 수 없다.** `docs/08-planning`에 1·2·3차 확장 계획과 Task 분해는 있지만 **4차 확장 계획 문서가 없다.** 영향을 미칠 대상 일정이 아직 존재하지 않으므로, 산정하면 근거 없는 수치가 된다. 4차 범위가 확정된 뒤 이 절만 갱신한다.

대신 지금 확인할 수 있는 일정 사실 두 가지를 기록한다.

**첫째, 착수 시점 조건인 "3차 확장 이후"에 아직 도달하지 않았다.** [3차 확장 최종 게이트](third-expansion-final-gate-result.md)는 `CONDITIONAL`이고 4절의 여섯 항목이 모두 미해소다. 같은 문서 1.1절이 승격·배포는 막지 않는다고 개정했지만, **단계 완료 선언은 4절이 해소된 시점**이라고 명시했다.

**둘째, 토폴로지를 먼저 바꾸면 남은 성능 증거의 비교 기준이 끊긴다.** 게이트 4절 3번은 측정 전용 환경에서 정상 `50/20`·최대 `200/80`을 실행하도록 요구하고, [#190 운영 직접 관찰](issue-190-operational-performance-result.md)은 단일 인스턴스 운영 환경에서 수집됐다. ALB와 다중 인스턴스를 넣으면 두 측정의 대상 구성이 달라져 같은 완료 증거 묶음에 넣을 수 없다. **성능 게이트를 먼저 닫고 고도화를 시작하는 순서가 재측정 비용을 줄인다.**

## 8. 판정과 권고

### 8.1. 판정

| 시나리오 | 예산 판정 | ADR-DEPLOY-002 7절 적용 |
|---|---|---|
| H1 ALB + ASG 상시 2대 | 118% (하한 113%) | **초과 → 착수 시점 합의 철회 조건에 해당** |
| H3 H1 + 공유 Redis | 146% 이상 | 초과 |
| H2 ALB + Blue-Green만 | 82% (하한 77%) | 예산 내 |

합의된 목표 구성 그대로는 착수 조건을 통과하지 못한다.

### 8.2. 권고

**ASG 상시 다중 인스턴스를 현재 예산 목표 아래에서 착수하지 않는다.** 세 갈래 중 하나를 팀이 고른다.

1. **범위를 H2로 좁혀 착수한다.** ALB와 Blue-Green 배포 자동화만 도입하고 상시 1대를 유지한다. 예산 82%로 통과하고, 무중단 배포와 ACM 자동 갱신, 상태 검사 기반 전환을 얻는다. **얻지 못하는 것은 인스턴스 장애 가용성이며, 그 사실을 착수 ADR과 NFR-AVAILABILITY-002에 그대로 적는다.** ASG는 예산이 확보된 뒤의 후속 단계로 남긴다.
2. **월 예산 목표를 상향 승인한다.** H1이 통과하려면 목표가 최소 180,000원이어야 하고(환율 여유 포함), Redis까지 정리하려면 220,000원 이상이 필요하다. 예산 상향은 이 문서의 권한 밖이므로 팀 결정 사항이다.
3. **착수 시점 합의를 철회한다.** ADR-DEPLOY-002 7절의 "단일 인스턴스 구성이 충분하거나 비용이 예산 목표를 초과하면" 조건을 적용해 고도화를 4차 이후로 미룬다.

권고는 **1번**이다. ALB는 세 요소 중 유일하게 나머지 둘의 선행 조건이면서 단독으로도 값을 내고(TLS 종단·상태 검사·전환), 비용의 대부분은 ASG 상시 2대가 만든다. ALB를 먼저 넣어 두면 예산이 확보됐을 때 ASG를 붙이는 작업이 대상 그룹 설정 변경으로 끝난다.

### 8.3. 착수 전 남는 선행 조건

1번을 고르더라도 다음 순서를 지킨다.

1. 3차 확장 최종 게이트 4절 여섯 항목을 해소한다(7절 둘째 사실).
2. 4차 확장 범위를 확정하고 이 문서 7절의 일정 영향을 채운다.
3. 착수 ADR(ALB 토폴로지, 전환 절차, Nginx 라우팅 책임 이관 여부, Blue-Green 자동화 범위, Redis 전환 시 세션 처리)을 작성한다. ADR-DEPLOY-002 3.1절이 열거한 미확정 4항목이 그대로 이 ADR의 목차다.
4. 퍼블릭 서브넷을 두 번째 AZ에 추가하고 M2 자원 생성 기록을 갱신한다(6.2절).

## 9. 이 검토가 확인하지 않은 것

- **ALB 외 단가를 재조회하지 않았다.** EC2·EBS·퍼블릭 IPv4·VPC 엔드포인트·NAT Gateway 단가는 2026-07-28 M2 산정값을 인용했다. 착수 판정 직전에 재조회한다.
- **실제 LCU 소비량을 측정하지 않았다.** 1 LCU 상한과 0.1 LCU 하한은 제한 공개 트래픽 규모에서 추정한 값이다. H1의 예산 초과 판정은 하한에서도 성립하므로 이 추정에 의존하지 않지만, H2의 82%는 트래픽이 커지면 올라간다.
- **AWS 자원을 하나도 만들지 않았다.** 이 검토는 문서와 공개 단가만 사용했다.
- **일정 영향(범위 문서 7절 4항)을 완결하지 못했다.** 7절에 사유를 적었다. 이 항목이 비어 있는 동안 배포 고도화는 착수 조건을 완전히 충족하지 않는다.
