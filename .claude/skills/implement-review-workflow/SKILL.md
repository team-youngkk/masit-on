# Implement → Review Workflow

요구사항 하나(또는 관련된 묶음)를 **분해 → 병렬 구현 위임 → 테스트 → 독립 리뷰 → 수정·재검증**까지 한 흐름으로 마무리하는 스킬이다. `Agent` 도구로 서브에이전트를 병렬 호출한다. `Workflow` 도구는 사용자가 명시적으로 멀티에이전트 오케스트레이션을 요청한 경우에만 쓴다 — 이 스킬 자체는 그 조건과 무관하게 작동해야 하므로 기본은 `Agent`다.

이 저장소(`masit-on`)는 [CLAUDE.md](../../../CLAUDE.md)의 "문서가 계약이다" 원칙과 Workstream 소유권이 적용된다. 이 스킬의 모든 단계는 그 규칙 위에서 동작하며, 규칙과 충돌하는 지름길(임의 범위 확장, 문서 없이 계약 변경, 소유권 무시)을 택하지 않는다.

## 0단계 — 범위와 계약 확인

작업 분해 전에 반드시:

1. 요구사항 ID를 확인하고 [제품](docs/04-product/traceability.md)·[API](docs/05-specs/api-traceability.md)·[데이터](docs/05-specs/data/data-traceability.md)·[ADR](docs/07-adr/adr-traceability.md) 추적표에서 근거 문서를 찾는다.
2. 관련 PRD, API 계약, 테이블 정의, Accepted ADR을 읽는다.
3. [소유권](docs/03-team/ownership.md)에서 이 작업이 어느 Workstream(WS-01~04)에 속하는지, 공통 파일(Spring Boot/Docker, 프론트 공통 Layout, Flyway 순서, 인증 공통) 소유자와 충돌하지 않는지 확인한다.
4. 문서 간 충돌이나 범위 밖 요청(MVP 제외 기능 등)을 발견하면 **여기서 멈추고 사용자에게 확인한다.** 임의로 해석하거나 범위를 넓히지 않는다.

이 단계에서 얻은 근거 문서 경로는 이후 위임 프롬프트에 그대로 포함시킨다 — 서브에이전트는 이 대화의 맥락을 모르므로 자체적으로 문서를 찾게 하지 않는다.

## 1단계 — 작업 분해

요구사항을 **서로 파일이 겹치지 않는 독립 단위**로 나눈다. 이 저장소의 계층형 도메인 경계([패키지 구조](docs/06-architecture/package-structure.md))를 분해 기준으로 쓴다:

- 도메인별(`restaurant`/`creator`/`video`/`visit`/`orchestration`/`security`) 또는 계층별(`presentation`/`application`/`domain`/`infrastructure`)로 나눈다.
- 같은 파일이나 같은 공통 소유 파일을 두 하위 작업이 동시에 건드리게 만들지 않는다 — 겹치면 순차 처리로 바꾸거나 한 위임에 합친다.
- 각 하위 작업에 대해: 대상 파일/패키지, 참조해야 할 계약 문서, 완료 기준(무엇이 통과하면 끝인지)을 명시한다.
- 하위 작업이 하나뿐이거나 서로 의존한다면 병렬 위임 없이 2단계를 순차로 진행한다 — 억지로 나누지 않는다.

분해 결과를 짧게 사용자에게 보여준다 (`[하위작업] → [담당 에이전트] → [완료 기준]` 형태). 범위가 명확하면 승인 없이 바로 진행해도 된다.

## 2단계 — 병렬 구현 위임

독립적인 하위 작업들을 **하나의 메시지에서 여러 `Agent` 호출**로 동시에 위임한다. 이 저장소의 `.claude/agents/`에 있는 전문 에이전트를 도메인에 맞게 고른다:

| 하위 작업 성격 | 에이전트 |
|---|---|
| Spring Boot 백엔드 로직/도메인/API | `spring-boot-engineer` |
| Next.js 프론트엔드 | `nextjs-developer` |
| PostgreSQL 스키마·쿼리·인덱스 | `postgres-pro` |
| Docker Compose·컨테이너 설정 | `docker-expert` |
| 위 범주에 없는 일반 구현 | `general-purpose` |

각 위임 프롬프트에는 다음을 반드시 포함한다:
- 0단계에서 찾은 근거 문서 경로와 핵심 제약(요구사항 ID, API/데이터 계약 요약).
- [구현 컨벤션](docs/06-architecture/implementation-conventions.md)과 [의존성 규칙](docs/06-architecture/dependency-rules.md) 중 이 작업에 해당하는 부분 — 특히 "Application은 자신의 `port.out`만 호출", "다른 도메인 Entity 직접 참조 금지", "Entity를 API에 노출 금지" 등.
- 작업 범위 밖 리팩터링·라이브러리 추가·API/DB 변경을 하지 말라는 명시적 제약 (CLAUDE.md 3절).
- 대상 파일·패키지 경로 (다른 하위 작업과 겹치지 않음을 다시 확인).

모든 위임이 끝나면 각 에이전트가 실제로 변경한 파일을 diff로 확인한다 — 에이전트의 완료 보고를 그대로 신뢰하지 않는다.

## 3단계 — 테스트

구현이 끝나면 컴파일·테스트를 실행한다. **검증하지 못한 항목은 완료로 보고하지 않는다.**

1. 필요하면 `test-automator`에게 위임해 [테스트 규칙](docs/07-adr/quality/test-001-automation-strategy.md)에 맞는 테스트를 작성/보완하게 한다 — 클래스명 `XxxTest`/`XxxIntegrationTest`/`XxxApiTest`, 메서드명 `행위_조건_기대결과`, Given-When-Then, `Thread.sleep()` 금지, 실제 Kakao/YouTube API 호출 금지.
2. 의존 서비스를 띄우고 빌드한다.
   ```bash
   docker compose up -d postgres redis wiremock
   ./gradlew clean build
   ```
3. 실패한 테스트나 컴파일 오류는 해당 하위 작업 담당 에이전트(또는 직접)에게 되돌려 고치고, 통과할 때까지 이 단계를 반복한다.
4. 실패가 남아 있다면 그대로 보고하고 다음 단계로 넘어가지 않는다.

## 4단계 — 독립 리뷰 (교차 검증)

빌드·테스트를 통과한 변경분에 대해 **서로 다른 관점의 리뷰어를 병렬로** 붙인다. 각 리뷰 에이전트는 구현 위임 시 오간 대화를 모르는 새 세션이므로 자연히 "독립적"이다 — 리뷰 프롬프트에 "이미 통과했다", "문제 없을 것이다" 같은 선입견을 주입하지 않는다.

한 메시지에서 병렬로 호출한다:
- `code-reviewer` — 코드 품질, 버그, 보안, 컨벤션 위반.
- `architect-reviewer` — 계층 경계·의존성 규칙·도메인 경계 위반 (`orchestration` 오용, 다른 도메인 Entity 직접 참조 등).
- `security-auditor` — 인증 경계, 비밀키/개인정보 노출, `/api/admin` 보호 여부.

각 리뷰 프롬프트에는 diff 범위, 관련 계약 문서 경로, 그리고 "확신 없는 지적은 하지 말고 실제로 재현 가능한 문제만 보고하라"는 지시를 포함한다.

리뷰 결과를 취합해 다음 기준으로 분류한다:
- **CONFIRMED**: 구체적인 실패 시나리오(입력→결과)가 있는 지적.
- **의견/스타일**: 재현 시나리오 없이 취향에 가까운 지적 — 수정하지 않고 기록만 한다.

교차된 지적(두 리뷰어가 같은 지점을 다른 이유로 지적)은 우선순위를 올린다.

## 5단계 — 수정·재검증

1. CONFIRMED findings만 최소 범위로 수정한다. 리뷰에서 나온 스타일 의견이나 범위 밖 개선 제안은 적용하지 않고 사용자에게 알린다 (karpathy-guidelines: surgical changes).
2. 수정 후 3단계(빌드·테스트)를 다시 실행한다.
3. 수정된 파일만 대상으로 4단계 리뷰를 한 번 더 돌린다 (최대 2회 반복). 2회 반복 후에도 남은 CONFIRMED 항목이 있으면 자동 반복을 멈추고 사용자에게 판단을 넘긴다 — 무한 루프를 만들지 않는다.
4. API 계약, DB 스키마, 라이브러리 버전을 바꿔야 하는 지적이 나오면 **자동으로 고치지 않는다** — CLAUDE.md 7절에 따라 소유자 합의가 먼저다. 지적 내용과 영향 범위만 보고한다.

## 종료 보고

다음을 한 번에 요약한다:
- 무엇을 구현했고 어느 하위 작업이 어느 에이전트에게 갔는지.
- 빌드/테스트 결과 (통과/실패, 실패 시 원인).
- 리뷰에서 나온 CONFIRMED 항목 중 수정된 것/스킵한 것과 이유.
- 계약 변경이 필요해 보류한 지적(있다면).
- 문서 동기화가 필요한지 (코드와 문서가 달라졌다면 같은 PR에서 갱신 필요 — CLAUDE.md 3절).
- 커밋/PR은 사용자가 명시적으로 요청할 때만 진행하고, [CLAUDE.md](../../../CLAUDE.md) 9절(Git 협업) 규칙(브랜치명, Conventional Commits, `Closes #이슈`, AI 생성 표기 금지, 최소 2인 승인)을 따른다.
